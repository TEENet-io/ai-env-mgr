# AI Env Mgr 操作手册

> 面向：客户 IT 管理员
> 配套：`README.md`（快速上手）、`dist/部署说明.md`（部署步骤）、`架构说明.md`（架构决策）、**`OSS布局.md`（OSS 结构与权限的唯一权威来源）**

---

## 1. 方案概述

在多台阿里云无影共享型云电脑上，让员工使用受控的 AI 工具，同时满足：

| 目标 | 手段 |
|---|---|
| 统一安装 AI 工具 | 模板机装好后制作镜像，所有云电脑从镜像创建 |
| 员工不能用浏览器访问外部 AI 网站 | 浏览器企业策略（HKLM）+ AppLocker |
| 员工不知道 AI 账户密码 | 管理员代为登录，凭据经 OSS 下发 |
| 策略能随时调整 | OSS 作配置中心，agent 定时拉取 |
| 管理员能看到全局状况 | 每台机器上报状态，`admin status` 汇总 |

---

## 2. OSS 配置中心详解

这是整套系统的枢纽。本节把 Bucket、密钥、权限讲清楚。

### 2.1 为什么需要 OSS

多台云电脑文件系统互相隔离，又没有 AD 域可用来集中下发。OSS 承担配置中心的角色：

- 管理员改一次策略 → 所有机器自动拉取
- 管理员代员工登录一次 → 凭据自动分发到对应机器
- 每台机器上报状态 → 管理员一屏看全

### 2.2 创建 Bucket

在阿里云 OSS 控制台创建，关键设置：

| 项 | 取值 | 原因 |
|---|---|---|
| 读写权限 | **私有** | 绝不能设为公共读，凭据会泄露 |
| 存储类型 | 标准存储 | 数据量小、访问频繁 |
| 地域 | **与云电脑同地域** | 走内网免流量费、延迟低 |
| 版本控制 | 建议开启 | 误删配置可恢复 |

Bucket 名建议带用途，例如 `ai-collect-sg`。

### 2.3 目录结构

两个顶级目录，**平级**：

```
ai-collect-sg/
├── admin/               员工名单，agent 完全够不到
│   └── users.json
└── agent_workdir/       agent 的全部活动范围
    ├── policy.json      封禁策略，全局一份，与员工无关
    ├── _bindings/       机器归属（按主机名），agent 只读
    ├── _status/         机器上报（按主机名），agent 只写
    ├── work1/           一个员工一个目录
    │   ├── credentials.zip
    │   └── data_collect/    会话采集，已实现，默认关闭（见 §2.5）
    └── work2/
        └── ...
```

agent 那一侧全部收在 `agent_workdir/` 下，Bucket 可以另作他用互不干扰。目录都是自动生成的，不用手工创建。

> **完整结构、每个对象的格式与字段，以 `OSS布局.md` 为准**，本手册不重复描述。

### 2.4 创建两个 RAM 用户

**必须建两个**，权限差别很大。

#### 管理员用户

用于 `admin.exe`，权限最大，只在管理员的电脑上使用。

1. RAM 控制台 → 用户 → 创建用户
2. 授权：给该用户添加自定义策略

```json
{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["oss:*"],
      "Resource": [
        "acs:oss:*:*:ai-collect-sg",
        "acs:oss:*:*:ai-collect-sg/admin/*",
        "acs:oss:*:*:ai-collect-sg/agent_workdir/*"
      ]
    }
  ]
}
```

把 `ai-collect-sg` 换成你的 Bucket 名。**三行都要**：第一行是 Bucket 本身（列举对象需要），后两行是两个目录里的对象。

3. 再给这个用户加上系统策略 **`AliyunECDReadOnlyAccess`**。控制台用它查询云电脑状态，才能把"休眠"和"agent 挂了"分开（见 §3.2.9）。不加也能用，只是安静的机器一律显示"离线"
4. 记下 **AccessKeyId** 和 **AccessKeySecret**。Secret 只显示一次，务必保存。

> **这个 ECD 权限只能给管理员用户，绝不能给 agent 用户。** agent 的密钥明文躺在每台员工云电脑上，给它加 ECD 权限等于让任意一台机器都能枚举全公司的云电脑和人机对应关系。

#### Agent 用户

用于 `agent.exe`，装进镜像分发到所有云电脑，权限必须收紧。

1. 创建用户
2. 授权：使用交付包里的 `ram-policy-agent.json`

```json
{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["oss:GetObject"],
      "Resource": [
        "acs:oss:*:*:ai-collect-sg/agent_workdir/policy.json",
        "acs:oss:*:*:ai-collect-sg/agent_workdir/_bindings/*",
        "acs:oss:*:*:ai-collect-sg/agent_workdir/*/credentials.zip"
      ]
    },
    {
      "Effect": "Allow",
      "Action": ["oss:PutObject"],
      "Resource": ["acs:oss:*:*:ai-collect-sg/agent_workdir/_status/*"]
    }
  ]
}
```

**这个策略允许什么**：读全局的 `policy.json`、读 `agent_workdir/_bindings/`、读各员工目录下的 `credentials.zip`、写 `agent_workdir/_status/`。

**明确不允许**：写任何策略或凭据、删除任何对象、列举 Bucket、以及碰 `agent_workdir/` 以外的任何东西——**包括 `admin/` 下的员工名单，那个路径压根没出现在授权里**。

> 完整的权限对照表见 `OSS布局.md` §5。

## 3. 命令详解

两个程序:`agent.exe` 装在云电脑上,`admin.exe` 留在管理员自己的机器上。

---

### 3.1 `agent.exe` — 云电脑上的服务

| 命令 | 作用 | 需要管理员身份 |
|---|---|---|
| `setup` | 一条命令装好:复制到位、收紧权限、注册服务、启动、验证 | 是 |
| `sync` | 立即执行一次完整同步 | 是 |
| `status` | 打印本机当前状态,**只读** | 否 |
| `install` / `uninstall` | 单独注册/卸载服务 | 是 |
| `start` / `stop` | 启停服务 | 是 |
| `run` | 服务本体,由服务管理器调用 | — |
| `version` | 版本号 | 否 |

#### `setup` —— 装机只用这一条

```powershell
.\agent.exe setup
```

复制到位、收紧权限、注册并启动服务、跑一次同步验证——**只在模板机上跑一次**,注册信息随镜像走。

#### 日志

`C:\ProgramData\AIEnvMgr\agent.log`,超过 4MB 自动滚动,上一代留在 `agent.log.1`。

```powershell
Get-Content C:\ProgramData\AIEnvMgr\agent.log -Tail 30
Get-Content C:\ProgramData\AIEnvMgr\agent.log -Tail 20 -Wait   # 实时跟
Get-Service AIEnvMgrAgent                                        # 服务在不在跑
```

**远程看日志(不用上机器)**:agent 每个完整同步周期会把日志**尾部(最近约 64KB)**推到 OSS 的 `_logs/{主机名}.log`,管理员在自己机器上就能拉:

```powershell
.\admin.exe log <主机名>          # 打印该机器上传的日志尾部
```

前提:agent 的 RAM 策略要有 `_logs/*` 的 **PutObject** 写权限(`dist/ram-policy-agent.json` 已含)。这只是最近尾部,完整日志仍在机器本地的 `agent.log`。

#### 服务每轮做什么

一次**完整同步**:

1. 拉全局 `policy.json` → 写入浏览器封禁策略。**无条件执行**,不看有没有绑定
2. 用主机名查绑定文件 → 得知服务哪个员工
3. 拉该员工的 `credentials.zip` → 投递到其 profile。ETag 没变就不下载
4. 采集(若已开启)→ 上传员工会话文件到 `data_collect/`
5. 自更新(若 policy 指定了别的版本)→ 下载校验 → 换 exe 重启
6. 按主机名写状态文件上报,并把日志尾部推到 `_logs/`

**触发时机**:服务启动时、休眠唤醒时、距上次完整同步超过间隔时。

**心跳**:两次完整同步之间,循环**每分钟**会轻量地刷新一次"最近露面"时间(不拉策略、不动员工的工具)。所以同步间隔可以设得长(省流量),而 控制台的存活判断仍是分钟级实时——这也是为什么静默几分钟就能判"离线"。

**关机/休眠上报**:agent 收到系统的关机/休眠通知时,会赶在断网前上报一次状态(`stopped`/`suspend`),让 admin 区分"正常离开"和"崩溃"。关机走 **PreShutdown**(系统拆网络前先通知,窗口约 180 秒),大概率成功;真·休眠挂起是尽力而为;硬断电收不到通知,靠时间窗口兜底(见 §5.4)。

注意区分:**休眠唤醒**是事件触发,1 分钟内响应;而管理员在 OSS 上改了东西**没有推送通道**,机器要等到下一个同步周期才发现。急用就跑 `agent.exe sync`。

### 3.2 `admin.exe` — 管理控制台

不带参数直接运行,它就在本机开一个控制台:

```powershell
.\admin.exe                      # 监听 127.0.0.1:8080
```

浏览器打开 `http://127.0.0.1:8080`,用 OSS 的 AccessKey 登录即可。

**密钥在运行时由你在浏览器里输入**,只存在于进程内存:不写磁盘、不进 cookie、不进日志,cookie 里只有一个随机 ID。**关掉程序就等于全部退出登录**——机器上没有任何东西留给别人翻。程序里编译进去的只有 bucket 名、endpoint 和区域,**没有任何密钥**。

部署成常驻服务(团队共用、带域名和 HTTPS)见 [Web控制台部署.md](Web控制台部署.md)。

> **命令行和 TUI 已移除。** 曾经有过一套等价的终端命令,但同一批操作维护两个前端,两边会各自漂移——机器状态的判定、OAuth 回调的解析、下载实现都出现过两份不一致的实现,而每一次分歧都是没人察觉的 bug,直到有人撞上。现在只有控制台一个入口。

控制台左侧导航的顺序,就是下面各节的顺序。

#### 3.2.1 机器

机器的总览。顶部一条状态条给出机队构成(正常 / 待处理 / 异常),下面是每台机器一行。

各列:

- **主机名** —— agent 自己上报的 Windows 计算机名,不用你事先知道。机器开机后自己会出现,显示为"未分配"
- **员工** —— 绑定给谁
- **状态** —— 一词概括这台机器要不要你处理,取值见 §5.4
- **最后同步** —— 相对时间("50 分钟前"),悬停可看精确时间戳。活着的 agent **每分钟**心跳一次,所以这列是"agent 是否活着"的实时证据
- **版本** —— 该机器上 agent 的版本。**各机器之间比对**,升级后能看谁还停在旧版

每行末尾有**日志**和**解绑**。日志页会先分开列出该机器的**错误**和**提示**,再显示日志原文,不必在几百行同步记录里翻找。

**绑定机器**:填主机名、从下拉里选员工。员工必须先在名单里。换人直接重新绑定覆盖即可。

**注销机器**:删除该机器的绑定和状态上报,它从列表里消失。要求**把主机名原样输一遍确认**——这个操作不可撤销。

> 解绑和注销的区别:解绑只解除分配,机器还在列表里(显示"未分配");注销把状态上报也删了,机器**从列表消失**。机器还开着的话,注销后它下个同步周期又会冒出来——**注销是给真正下线的机器用的**。

#### 3.2.2 员工

登记、停用、启用员工。邮箱栏**仅作管理员备注**,程序不用它登录任何东西。同名再新增一次是更新,不会重复(账户名不区分大小写,`Work1` 和 `work1` 是同一个人)。

**"停用"是真的吊销,不只是改个标志位**:

它会删除 OSS 上该员工的 `credentials.zip`。agent 读到**明确的 404** 时,会删掉该员工 profile 里的本地凭据文件并结束 AI 工具进程。

这里的设计要点是**区分"确实没了"和"够不着"**——只有服务端真的返回 404 才算吊销,网络超时之类一律不动。否则一次网络抖动就会把所有机器的登录态一起抹掉。

> 停用之后再启用,**不会**把凭据找回来。要恢复得重新做一次代员工登录。这是吊销该有的样子。

> **别忘了 OSS 之外的一步**:本方案能删掉机器上的登录态,删不掉 AI 账户本身。真正的离职流程还应该去 OpenAI / Anthropic 后台改密码或吊销该账户的会话。

#### 3.2.3 代员工登录

**员工全程不知道账户密码**,这是整套方案的核心。OAuth 结果在内存里打包直接传 OSS,**不落管理员本地磁盘**。

选员工、选工具(Codex 或 Claude),点开始。页面会给出一个授权地址:

1. 在浏览器里打开它,用**该员工的账号**登录
2. 把浏览器给出的内容粘回页面
3. 提交,凭证即发布

两个工具粘的东西不一样:

**Codex** —— 登录后浏览器会跳 `http://localhost:1455/auth/callback?code=...&state=...`,**显示连接失败是正常的**,地址栏里带着 code。复制**整个地址栏 URL**。

> 为什么不自动接收:1455 是 Codex CLI 自己占用的端口,而且管理员的浏览器通常和运行控制台的机器不是同一台。粘贴对两种情况都成立。

**Claude** —— 登录后页面直接显示一串授权码,格式是 `code#state`。**整段都要粘**,包括 `#` 后面的部分——`state` 是唯一能证明这个 code 属于本次登录的东西。

如果 `state` 和本次登录对不上(比如粘了上一次没做完的回调),会直接拒绝让你重来。

一次做一个工具。两个都要就做完一个再做另一个。有效期 15 分钟。

代员工登录产出四个文件里的三个:

| 文件 | 落到员工 profile |
|---|---|
| `codex/auth.json` | `.codex\auth.json` |
| `claude/.credentials.json` | `.claude\.credentials.json` |
| `claude.json` | `.claude.json` |

**`claude.json` 不能少**:Claude Code 的登录身份记在这里,只给 `.credentials.json` 的话令牌到位了、员工打开还是会被要求登录。agent 投递它时是**合并写入**——那个文件里还有员工自己的项目历史和 MCP 配置,不能覆盖掉。

只登录了其中一个工具时,zip 里只有那部分,agent 投递时会与已有文件合并,不会把另一个工具的凭据抹掉。

#### 3.2.4 封禁策略

增删封禁域名、总开关。

策略是**全局一份**,与员工名单无关。改一次所有机器都生效,包括**还没分配给任何人的机器**。

域名可以一次填多个(换行、逗号、空格分隔都认),会自动去重、排序、转小写,`Foo.com` 和 ` foo.com ` 算同一个。

**"临时全局关闭"是给管理员自己临时访问用的**:它会让 agent **删除**注册表里的封禁键(而不是写一个空清单)——键不存在是三个浏览器都明确当作"不管控"的唯一状态。用完记得恢复。

#### 3.2.5 会话采集

同步间隔和采集开关都在这里。

**同步间隔**限制在 **1–1440 分钟**,超出自动钳到边界。防止误设成 0 让 agent 疯狂轮询,或设成几天导致机器实际失联。

> 新间隔要机器**先同步一次**才知道。调试时用 1 分钟很方便,**正式上线建议调回 5–10 分钟**。

**采集**打开后,agent 会把 AI 会话原始文件上传到 OSS 的 `data_collect/{用户}/` 下,供后续归集/挖掘:

- **按机器上的每个用户各采各的**(不跟绑定走):一台机器上有几个真人账户(排除 Administrator/系统),就各自采到 `data_collect/{该用户}/`。共享云电脑上多人用 AI 时,**每个人都会被采到**,不只绑定那一个
- **默认关闭**,而且 agent 对 `data_collect` 的**只写**权限是在你打开这个功能时才补的(通配用户 `agent_workdir/*/data_collect/*`)
- **起始日期**只采该日期(UTC)之后的会话,留空采全部历史;**静默秒数**是去抖(文件停止变动多少秒后才上传),留空默认 60

页面下方的统计**按 OSS 里实际有数据的用户列**(含不在员工名册里的账户),用来核对"谁在产出、传了多少"。

#### 3.2.6 文件传输

上传文件、生成下载链接。

**云电脑上不需要任何密钥**——链接自带授权(预签名 URL)。这是把文件弄上云电脑最省事的方式,比控制台文件传输快。

默认 24 小时有效,可调。**链接是 bearer token,谁拿到谁能下载**——所以别把链接贴到聊天记录里长期留着。

文件存在 `admin/files/`,**不在 `agent_workdir/` 下**。agent 的授权里没有这条路径,所以员工机器上的密钥下载不了这些文件,只有管理员签出来的链接能。

上传上限 64 MB。更大的东西(比如 Codex 安装包)走 §3.2.7 的 URL 方式。

#### 3.2.7 发布更新

agent 和 Codex 桌面版的发布都在这一页。

**这是整个系统里最危险的操作**:发布会让**每一台机器**下载并执行一个二进制。所以它要求**把版本号原样再输一遍**才生效,并且每次都写审计日志(记真实客户端 IP,不记 token 和凭证)。

**发布 agent**

上传文件,或填一个 release 地址让服务器自己去拉(私有仓库要填 GitHub token,**每次发布现场输入,服务器不存**)。

发布后:agent 每轮比对版本 → 下载 `_agent/agent.exe` → **校验 SHA-256** → 换文件(旧的留 `agent.exe.old`)→ 重启服务。

- **policy 是全局的:agent 发布一次就是全体一起更新,没有灰度、没有自动回滚**。务必先在**一台机器**上验证新 exe 能跑(见 §4.7)
- 校验不过不换;同一目标只试一次,不会反复重启;"清除目标"是急停开关
- 需要 agent 的 RAM 策略有 `_agent/*` 的 **GetObject** 读权限(`dist/ram-policy-agent.json` 已含)

**发布 Codex**

和 agent 类似,但多两件事:

- **有灰度**。默认只发 **10%**。这个包是对上游 Codex 的重打包,补丁会随上游版本漂移,构建通过只证明补丁应用成功,**不证明 ChatGPT 入口真的消失**——那只有 Windows 真机能验。确认无误后再调到 100%
- **用 URL,不要上传**。安装包约 700 MB,浏览器上传会被 CDN 的体积限制挡下;让服务器直接拉取更快也更稳

版本比对**按相等,不是"只升不降"**:把目标改回旧版本就是回滚。

agent 侧三条保护:校验和不符**拒绝安装**;同一版本**只尝试一次**(失败不会每周期重下 700 MB);Codex 正在运行或磁盘不足则**推迟**,不把应用从员工手里抽走。

发布是**后台任务**:提交后页面立刻返回,自己每 5 秒刷新显示进度,可以直接关掉页面。同时只允许一个发布在跑——两个并发会抢着写同一份策略,后完成的那个会悄悄覆盖先前的。

页面下方的机队现状能一眼看出**发布了什么 vs 各台机器实际装到了什么**。

#### 3.2.8 策略总览

只读汇总:每台机器同步时读到的就是这一份。

#### 3.2.9 云电脑状态查询

控制台还会向阿里云无影查询云电脑状态,用来回答一个 agent 答不了的问题:**一台安静的机器,是睡着了还是挂了**。

无影是在**虚拟化层**挂起整台机器的,客户机 Windows 收不到任何电源事件,agent 也就没有机会说"我要睡了"(实测确认:休眠前后既没有生命周期日志,也没有唤醒同步,只有两次定时同步之间的一段空白)。平台是唯一知情者。

- **只在需要时查**:仅对已经安静下来的机器发起查询。机队都正常上报时,一次 API 调用都不会发生;结果缓存 1 分钟
- 用的就是**你登录时输入的那把密钥**,不需要第二把,发布物里也就没有任何密钥可泄。前提是这把密钥所属的 RAM 用户带 `AliyunECDReadOnlyAccess`
- **不能用 agent 的那把密钥**。那把明文躺在每台员工云电脑上,给它加 ECD 权限等于让任意一台机器都能枚举全公司的云电脑和人机对应关系
- 查询因此**只在有人登录时发生**。这不损失什么:查询的唯一用途是渲染这个页面,没人登录就是没人在看
- 没有该权限时查询会失败(记日志),安静的机器仍显示"离线",其余一切照常

判定见 §5.4。

## 4. 标准流程

### 4.1 首次部署

控制台 → **封禁策略**:确认开关是"拦截中",并核对域名清单。

**镜像做出去之后再改就是逐台的事了**，第 6 步别省。

### 4.2 新员工入职

入职从**无影控制台**开始：先给员工开一台云电脑、建好 Windows 账户，再回到 `admin` 登记、代登录、绑定。

#### 第 1 步：在无影控制台创建云电脑

用**公司自定义镜像**（§4.1 第 8 步做好的那个）给新员工开一台云电脑。镜像里 agent 已随开机自启，浏览器封禁与 AppLocker 也都就位，开机即生效。

> **机器什么时候出现在控制台里**：agent 是 **SYSTEM 服务、开机自启**，**不必等任何人登录**——云电脑一开机、agent 完成首次 sync，这台就出现在**机器**页（第 6 步据此找它绑定）。登录只影响 `work1` 在不在 `LocalUsers` 里，即"缺少用户" → "正常"。
>
> 若你们的云电脑是**连接时才开机**（会话式/按需），它会在**首次被拉起（通常即员工首次连接）之后**才出现在 status；想在员工到岗前就绑定，先自己连一次把这台开起来即可。

#### 第 2 步：创建 Windows 标准用户

在这台云电脑上给员工建一个**标准用户**（非管理员），例如 `work1`。

> ⚠️ 一定是**标准用户**。标准用户无权删除 HKLM 里的浏览器封禁策略——这正是"员工绕不过封禁"的前提；管理员则能自行卸掉封禁。

#### 第 3 步：员工首次登录（创建 profile）

Windows 用户**首次登录才会生成 profile**，凭据得有这个目录才能投递。让员工（或你代为）用 `work1` 登录一次。

> 若这一步晚于绑定也没关系：员工首登后，**下一个同步周期**凭据就会投递到位；在此之前控制台会把这台标记为"缺少用户"。

#### 第 4 步：登记员工（admin）

在管理员电脑上裸跑 `admin.exe`，浏览器打开 `http://127.0.0.1:8080` 登录，之后：

```
菜单 2 员工管理 → 2 新增
  员工名: work1
  codex 邮箱(备注,可空): ai-work1@company.com
  claude 邮箱(备注,可空): ai-work1@company.com
```

邮箱仅作管理员备注（见 §3.2 员工管理）。

#### 第 5 步：代员工登录（admin）

```
菜单 3 代员工登录
  员工名: work1
  工具 codex/claude/all [all]: all
```

浏览器完成授权，OAuth 结果直接进 OSS、**不落管理员本地磁盘**（粘贴方式见 §3.2.3）。

#### 第 6 步：找到这台机器并绑定

机器开机后 agent 会自动上报，在**机器**页显示为"未分配"：

```
控制台 → **机器**:看哪台显示"未分配"

菜单 4 机器管理 → 2 绑定
  主机名: <主机名>
  员工名: work1
  备注(可空): 研发部-张三
```

主机名不用事先知道，从机器状态里认——表格下方会列出该机器上有哪些本地账户，据此判断是哪台。

#### 第 7 步：等一个同步周期（或手动催一次）

绑定后 agent 会在**下一个同步周期**（默认 30 分钟，改频率用 `admin set-interval`，见 §3.2 封禁策略）拉配置、把 `work1` 的凭据投递到位。要立刻生效，在那台机器上跑一次 `agent.exe sync`。

完成后员工打开 Codex / Claude Code 即为已登录状态，浏览器访问 AI 网站被封。

### 4.3 凭据过期

控制台 → **代员工登录**:选员工、选工具,按页面提示完成。

重新授权一次，各机器下个同步周期自动更新。

**员工那边会有一次打断**：新凭据投递时 agent 会结束正在运行的 Codex / Claude 进程（这两个工具把令牌读在内存里，不重启不会重新加载）。所以尽量别在员工正干活时做。

### 4.4 员工离职

- 控制台 → **员工**:对该员工点"停用"(停用并吊销凭据)
- 控制台 → **机器**:对该机器点"解绑"(机器要转给别人用时)

**停用**会删除 OSS 上该员工的 `credentials.zip`。这才是真正起作用的一步：agent 读不到凭据对象（明确的 404）时，会把该员工 profile 里的本地凭据文件一并删掉，并结束正在运行的 AI 工具进程。

生效时间同样是**下一个同步周期**。要立刻吊销就去那台机器上跑 `agent.exe sync`。

> **别忘了 OSS 之外的一步**：本方案能删掉机器上的登录态，但删不掉 AI 账户本身。真正的离职流程还应该在 OpenAI / Anthropic 后台改密码或吊销该账户的会话——否则员工在自己设备上仍是登录状态。

未解绑的机器会在**机器**页显示 **已离职**，提醒你这台机器还挂在一个已停用的人名下，需要重新分配或下线。

### 4.5 管理员临时需要访问 AI 网站

控制台 → **封禁策略** → "临时全局关闭"。

### 4.6 调整封禁清单

控制台 → **封禁策略**:在"增删域名"里填写,新增和移除都可以一次提交多个。

### 4.7 升级 agent

控制台 → **文件传输**:上传 `agent.exe`,页面会给出下载链接。

机器多的话建议直接重做镜像、重开机器，比逐台替换省事。

改动会写入所有启用员工的目录，各机器下次同步生效。

#### 自动升级（`admin agent`）

不想逐台重跑 setup，可以让 agent 自更新：发布一次，所有机器下个同步周期自己换。

控制台 → **文件传输**:上传 `agent.exe`,页面会给出下载链接。

**agent 侧**：每周期比对 policy 里的目标版本与自身版本，不同就下载 `_agent/agent.exe`、**校验 SHA-256**、换文件（旧的留成 `agent.exe.old`）、重启服务。校验不过不换，并在 status 报错；同一目标只试一次，坏包不会反复重启。

**前置**：agent 的 RAM 策略要有 `_agent/*` 的 **GetObject** 读权限（`dist/ram-policy-agent.json` 已含）。结构见 `OSS布局.md` §7。

**风险（务必知道）**：

- **全体一起更新**，无灰度 → 所以第 2 步"先在一台上验证"不能省。
- **无自动回滚**：新版起不来就得人工上机器（控制台/RDP），把 `C:\Program Files\AIEnvMgr\agent.exe.old` 换回 `agent.exe` 再启动服务。
- 只有**已经带自更新功能的 agent** 才会响应发布——第一版带此功能的 agent 仍要手动装（上面的 setup 方式）一次作为起点。

## 5. 故障排查

### 5.1 机器显示"从未上报"

已绑定但从未上报。按顺序查：

```powershell
# 1. 服务在跑吗
Get-Service AIEnvMgrAgent

# 2. 手动同步看报错
.\agent.exe sync

# 3. 看日志
Get-Content C:\ProgramData\AIEnvMgr\agent.log -Tail 30
```

常见原因：
- **打进镜像的 agent.exe 没填配置** —— `agent.exe status` 第一行若是 `config=config file`，说明这个 exe 是空的，填法见 `dist/部署说明.md`
- endpoint 填错（内网/公网搞反，或地域不对）
- AK/SK 错误或已被禁用
- 云电脑无法访问 OSS（安全组或网络策略拦截）

### 5.2 显示"未分配"

机器上报了但还没分配。正常现象，绑定即可：

控制台 → **机器** → 绑定机器。

表格下方会列出该机器上有哪些账户，据此判断该绑给谁。

### 5.3 显示"缺少用户"

绑定的员工在该机器上没有 profile。两种原因：

- **绑错名字** —— 在**机器**页看绑的是谁,重新绑定即可
- **该用户从未登录过** —— Windows 用户首次登录才会创建 profile。让员工登录一次即可

### 5.4 机器安静了:休眠、关机、还是挂了

活着的 agent 大约每分钟刷新一次上报(心跳),所以"多久没上报"是很强的信号。但云电脑会在下班、周末休眠或关机,这种静默是**正常**的。把每天休眠的机器都报成故障,红灯很快就没人看了。

判定分两层:**先看 agent 自己说了什么,它说不出来时再问平台**。

| 状态 | 判据 | 要不要管 |
|---|---|---|
| **正常** | **10 分钟**内有上报 | 否 |
| **休眠中** | agent 报了"我要睡了",或平台说它处于 `Hibernated` | 否,预期内 |
| **已关机** | agent 报了"我被停止/关机了",或平台说它 `Stopped` | 否,已知状态 |
| **离线** | 静默 10 分钟以上,且**没能问到平台** | 否,预期内 |
| **agent 无响应** | 平台说这台**开着**(`Running`),但 agent 一声不吭 | **是,要排查** |
| **云端已删除** | 查了平台,没有这台云电脑 | 是(该注销了) |
| **长期失联** | 静默**超过 3 天**,且问不到平台 | **是,要排查** |

两条时间线的由来:

- **10 分钟(正常↔离线)**:活着的 agent 每分钟心跳一次,静默 10 分钟 = 10 次心跳都没了。这条线远比同步间隔短,停机/关机几分钟内就能看出来,而且够宽,能吸收一次网络抖动
- **3 天(离线↔长期失联)**:休眠/关机的机器一两天内会醒;真挂了的 agent 不会自己醒

#### 为什么需要问平台

**无影的"休眠"是在虚拟化层把整台机器冻住的,客户机 Windows 收不到任何电源事件。**

这一点是实测确认的:让一台云电脑休眠再唤醒,本地日志里既没有生命周期记录、也没有唤醒同步,只有两次定时同步之间的一段空白——**agent 从头到尾没被通知过**,它没有任何机会留下"遗言"。

所以在无影上,单靠 agent 无法区分"睡着了"和"挂了":两者都表现为一模一样的静默。控制台因此会向阿里云查询云电脑状态,把一种沉默拆成四种答案(见 §3.2.9)。

其中最有价值的是 **agent 无响应**:机器开着、平台够得着,它却不说话。在能问到平台之前,这种情况和"下班关机"长得完全一样,**是看不见的**。

> 休眠时平台返回的 `DesktopStatus` 是 `Stopped`,休眠标记在 `ManagementFlags` 里。只看状态字段会把休眠报成关机——正好又把要区分的两件事合并回去。

#### agent 自己的"遗言"仍然有用

agent 的休眠/停止上报没有白做,它在**真正的 Windows 电源事件**下是有效的,各场景可靠性:

- **停服务**(`sc stop`,系统继续运行)→ 网络在,**可靠**报出"已关机"
- **关机 / 重启** → agent 注册了 **PreShutdown**,在系统拆网络**之前**就收到通知(窗口约 180 秒),**大概率**报得出去
- **无影的平台级休眠** → **收不到通知,报不出去**,由平台查询兜底
- **强制断电 / 控制台硬关机** → 操作系统也收不到通知,等同崩溃 → 靠时间线和平台查询兜底

agent 自己报出来的优先于平台查询:它更及时,而且能说明是"主动"离开的。

#### 处理建议

- 看到 **agent 无响应**:机器是开着的,去看它的日志(**机器 → 日志**),多半是服务停了或 agent 崩了
- 看到 **长期失联**:按 §5.1 排查
- **休眠中 / 已关机 / 离线不计入"需要关注"**,顶部的机队状态条不会因为下班而一片红
- 登录用的密钥没有 `AliyunECDReadOnlyAccess` 时,平台查询会失败,安静的机器统一显示"离线"——不算错,只是少了一层信息

### 5.5 显示"已离职"

机器还绑定着一个已停用的员工。凭据已经吊销，但机器本身还在运行、还在上报，没人负责。

控制台 → **机器** → 注销机器(需把主机名原样输一遍确认)。

### 5.6 一台机器有多个用户

这是**允许的、不再报警**。控制台会把这台上的账户都列出来,但不再因此标 `EXTRA USERS`——共享云电脑本就可能多人各有账户。采集也会**每个用户各采各的**(见 §2.5)。如果你怀疑某个账户不该存在(有人私建绕管控),从账户列表里认出来,上机器核查即可。

### 5.7 封禁不生效

```powershell
# 确认策略已下发到本机
.\agent.exe status          # 看 block 和 domains

# 确认注册表已写入
Get-ItemProperty "HKLM:\SOFTWARE\Policies\Google\Chrome\URLBlocklist"
```

- **注册表有值但浏览器仍能访问** → 浏览器没重启。重启浏览器，或在 `chrome://policy` 点"重新加载政策"
- **注册表没值** → agent 没同步成功，按 §5.1 查
- **换了个浏览器就能访问** → 只覆盖 Chrome/Edge/Firefox，其他浏览器要靠 AppLocker 拦

### 5.8 绿色版浏览器能绕过

绿色版不读系统策略，必须靠 AppLocker 拦截运行。

```powershell
.\agent.exe status          # 看 applocker 字段（只读，随便跑）
```

- 显示 **Audit** → 仍是审计模式，只记录不拦截。需在模板机切到强制模式后重做镜像
- 显示 **None** → AppLocker 未启用。检查 Windows 版本（需企业版/教育版/Server）和 AppIDSvc 服务

### 5.9 员工打开 AI 工具仍要求登录

```powershell
.\agent.exe status          # 只读，看 "AI credentials in place for:" 那行
.\agent.exe sync            # 要看同步过程的错误就跑这条
```

按现象分：

- **`status` 里该员工不在 "credentials in place" 列表里** → 文件根本没落地。跑 `sync` 看报错，常见是 OSS 里没有该员工的 `credentials.zip`（管理员还没执行 `login`），错误会写 `no credentials published for "xxx" yet`
- **文件在，但打开工具仍要求登录** → 分两种：
  - **Claude** → 多半是 `.claude.json` 的问题，它记着登录身份，只有 `.credentials.json` 是不够的。确认 `C:\Users\<员工>\.claude.json` 存在且含 `hasCompletedOnboarding` 与 `oauthAccount`
  - **两个都要求登录** → 令牌过期了，管理员重新 `login`
- **`sync` 报 `credentials written but not readable by <员工>`** → ACL 授权失败，文件写了但员工读不到。看具体错误，通常是 profile 权限异常

## 6. 安全边界

**能做到**：

- 阻止员工用受管浏览器访问外部 AI 网站
- 阻止运行绿色版浏览器等未授权程序（AppLocker 强制模式下）
- 员工不知道 AI 账户密码
- 员工（标准用户）无法自行解除管控
- Agent 密钥泄露也读不到员工名单、改不了策略、碰不到 `agent_workdir/` 以外的东西
- **还没分配给任何人的机器同样被封禁** —— 策略是全局的，不依赖绑定
- 离职后能远程吊销：删掉 OSS 上的凭据，机器下次同步就清掉本地登录态

**做不到**：

- 阻止员工用手机拍摄屏幕
- 阻止员工用个人设备访问 AI
- 阻止拥有本地管理员权限的人解除管控
- 阻止有管理员权限者读取 agent 密钥（密钥是明文编译在 exe 里的，`strings` 就能翻出来）
- **删掉 AI 账户本身** —— 只能删机器上的登录态，账户还得去 OpenAI / Anthropic 后台处理

**必要前提**：

- 员工账户必须是**标准用户**
- 严格控制本地管理员权限的授予
- OSS Bucket 必须是**私有**

## 7. 卸载与复原

**单台机器移除 agent**：

```powershell
cd "C:\Program Files\AIEnvMgr"
.\agent.exe stop
```
