## 先认识几个词

| 词 | 意思 |
|---|---|
| 云电脑 | 阿里云"无影"共享型云电脑，员工在上面工作。阿里云接口里叫 ECD。 |
| 模板机、镜像 | 先在一台云电脑（模板机）上装好所有软件，再把它做成镜像。之后的云电脑都从镜像创建，开出来就是装好的。 |
| agent（`agent.exe`） | 装在每台云电脑上的后台服务。它定时拉取策略和凭据、写入本机、上报机器状态。 |
| 控制台（`admin.exe`） | 管理员用的网页后台。所有管理操作都在这里做。 |
| OSS、Bucket | 阿里云的云存储。Bucket 是其中的一个存储空间，相当于一个大文件夹。本方案把它当作"配置中心"。 |
| RAM 用户 | 阿里云的子账号。每个子账号可以单独设置能做什么。 |
| AK/SK（AccessKey） | RAM 用户的密钥，由 AccessKeyId 和 AccessKeySecret 两部分组成，程序用它访问阿里云。 |
| 凭据 | 员工登录 AI 工具所需的登录信息，打包成 `credentials.zip`。 |
| 绑定 | 把一台云电脑分配给某个员工。agent 靠绑定知道这台机器给谁用。 |
| 同步周期 | agent 每隔一段时间做一次完整同步，这个间隔就是同步周期。 |
| profile | Windows 用户的个人目录。用户第一次登录时才会生成。 |
| HKLM | Windows 注册表里对整台机器生效的部分。普通用户（标准用户）不能改。 |
| AppLocker | Windows 自带的程序白名单。不在名单里的程序不能运行。 |
| 网关（LiteLLM） | 员工调用 AI 模型时经过的中转服务。员工的令牌和额度在这里管。 |
| 令牌 | 员工调用模型的通行凭证。 |
| 渠道 | 模型背后实际提供服务的供应商线路，例如 AWS、Google、Azure。 |
| CI | 自动构建安装包并上传的流程，跑在 GitHub 上。 |
| SHA-256 | 文件的"指纹"。指纹对得上，说明文件没被换掉或损坏。 |
| 灰度 | 新版本先发给一部分机器试用，再推给全部。本方案**没有**灰度。 |
| 审计 | 控制台记录的操作日志：谁、什么时候、做了什么。 |

## 1. 方案概述

本方案让员工在多台阿里云无影共享型云电脑上使用受控的 AI 工具。要达成的目标和对应做法如下：

| 目标 | 做法 |
|---|---|
| 统一安装 AI 工具 | 在模板机上装好后做成镜像，所有云电脑都从镜像创建 |
| 员工不能用浏览器访问外部 AI 网站 | 浏览器企业策略（写在 HKLM）+ AppLocker |
| 员工不知道 AI 账户密码 | 管理员代为登录，凭据通过 OSS 发到机器上 |
| 策略能随时调整 | OSS 作配置中心，agent 定时拉取 |
| 管理员能看到全局状况 | 每台机器上报状态，控制台**总览**页汇总 |

## 2. OSS 配置中心

OSS 是整套系统的中枢。本节说明怎么建 Bucket、建密钥、配权限。

### 2.1 为什么需要 OSS

多台云电脑的文件系统互相隔离，也没有 AD 域（Windows 的集中管理服务）可以统一下发配置。所以用 OSS 当配置中心：

- 管理员改一次策略，所有机器自动拉取。
- 管理员给员工签发一次凭据，自动发到对应的机器。
- 每台机器上报状态，管理员在一个页面上就能看全。

### 2.2 创建 Bucket

在阿里云 OSS 控制台创建。关键设置：

| 设置项 | 取值 | 原因 |
|---|---|---|
| 读写权限 | **私有** | 绝不能设为"公共读"，否则凭据会泄露 |
| 存储类型 | 标准存储 | 数据量小、访问频繁 |
| 地域 | **和云电脑同一个地域** | 走内网，不收流量费，延迟低 |
| 版本控制 | 建议开启 | 误删配置后可以恢复 |

Bucket 名建议能看出用途，例如 `ai-collect-sg`。

### 2.3 目录结构

Bucket 下有两个**同级**的顶层目录：

```
ai-collect-sg/
├── admin/               员工名单，agent 完全够不到
│   └── users.json
└── agent_workdir/       agent 的全部活动范围
    ├── policy.json      封禁策略，全局一份，与员工无关
    ├── _bindings/       机器归属（按主机名），agent 只读
    ├── _status/         机器上报（按主机名），agent 只写
    ├── work1/           一个员工一个目录
    │   ├── credentials.zip
    │   └── data_collect/    会话采集，已实现，默认关闭（见 §3.2.4）
    └── work2/
        └── ...
```

- agent 用到的东西全在 `agent_workdir/` 下面。所以这个 Bucket 还可以放别的东西，互不影响。
- 这些目录都会自动生成，不用手工创建。

> **完整的目录结构、每个文件的格式和字段，以 `OSS布局.md` 为准**，本手册不重复。

### 2.4 创建 RAM 用户

**管理员用户和 Agent 用户必须分开建**，两者权限差别很大。

> 2026-09-25 起，新版 agent 只通过控制台通信，不再带 OSS 密钥，**新部署不用再建 Agent 用户**。下面的 Agent 用户一节只适用于还在运行旧版 agent 的环境。

#### 管理员用户

给 `admin.exe` 用。权限最大，只在管理员自己的电脑上使用。

1. 打开 RAM 控制台 → 用户 → 创建用户。
2. 给这个用户添加自定义授权策略：

```json
{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["oss:*"],
      "Resource": [
        "acs:oss:*:*:ai-collect-sg",
        "acs:oss:*:*:ai-collect-sg/admin/*",
        "acs:oss:*:*:ai-collect-sg/agent_workdir/*"
      ]
    }
  ]
}
```

   把 `ai-collect-sg` 换成你的 Bucket 名。**`Resource` 里三行都要有**：
   - 第一行是 Bucket 本身，列出文件时要用。
   - 后两行分别对应两个目录里的文件。

3. 再给这个用户加上系统策略 **`AliyunECDReadOnlyAccess`**（只读查询云电脑的权限）。
   - 加了以后，控制台能查到云电脑的状态，从而分清机器是"休眠了"还是"agent 挂了"（见 §3.2.6）。
   - 不加也能用，只是没有上报的机器一律显示"离线"。
4. 记下 **AccessKeyId** 和 **AccessKeySecret**。Secret 只显示一次，务必保存好。

> **`AliyunECDReadOnlyAccess` 只能给管理员用户，绝不能给 Agent 用户。** 原因：agent 的密钥以明文存放在每台员工云电脑上。如果它有这个权限，任何一台机器都能查出全公司有哪些云电脑、分别是谁在用。

#### Agent 用户

给 `agent.exe` 用。它会装进镜像，分发到所有云电脑上，所以权限必须收紧。

1. 创建用户。
2. 授权时使用交付包里的 `ram-policy-agent.json`：

```json
{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["oss:GetObject"],
      "Resource": [
        "acs:oss:*:*:ai-collect-sg/agent_workdir/policy.json",
        "acs:oss:*:*:ai-collect-sg/agent_workdir/_bindings/*",
        "acs:oss:*:*:ai-collect-sg/agent_workdir/*/credentials.zip"
      ]
    },
    {
      "Effect": "Allow",
      "Action": ["oss:PutObject"],
      "Resource": ["acs:oss:*:*:ai-collect-sg/agent_workdir/_status/*"]
    }
  ]
}
```

**这个策略允许：**
- 读全局的 `policy.json`；
- 读 `agent_workdir/_bindings/`；
- 读各员工目录下的 `credentials.zip`；
- 写 `agent_workdir/_status/`。

**明确不允许：**
- 写任何策略或凭据；
- 删除任何文件；
- 列出 Bucket 里的文件；
- 碰 `agent_workdir/` 以外的任何东西，**包括 `admin/` 下的员工名单——授权里根本没有这个路径**。

> 完整的权限对照表见 `OSS布局.md` §5。

#### CI 用户（2026-09-19 起，发布流程用）

CI 构建完成后，直接把安装包放进 OSS 上的版本库位置。控制台只做登记，不经手安装包。

> 2026-09-25 起的变化：
> - Agent 已改为只通过控制台的接口通信，不再内置或使用 OSS 的 AK/SK。
> - 发布上传优先使用独立的 `OSS_CI_*` Secrets。
> - 现有的 `AGENT_OSS_*` 只是暂时给 CI 上传兜底，不会编译进 Agent。等独立的 CI 密钥配好后，可以删掉这些旧 Secrets。

原先的建议是**不要复用 agent 的密钥**（只对还在运行旧版 agent 的环境有意义）。原因：那把密钥存放在每台员工云电脑上。如果给它写 `_agent/*`、`_codex/*` 的权限，任何一台机器都能往里放一个程序，而所有机器都会去执行它。

1. 创建用户 `ci-release`（只用 AccessKey 登录）。
2. 授权使用交付包里的 `ram-policy-ci.json`。它只有 `PutObject`（上传）权限，而且只能写下面两种路径：

```
agent_workdir/_agent/<版本>/agent.exe
agent_workdir/_codex/codex-setup-<版本>.exe
```

   - 它不能读、不能删、不能列出文件，也写不了策略和凭据。
   - 就算密钥泄露，最多是被多传几个包。有两道防线挡住"换包"：版本库规定同一版本号不能换包；agent 下载后会校验 SHA-256。
3. 把 AccessKey 放进 GitHub 仓库的 Secrets。`ai-env-mgr` 和 `codex-kiosk` 两个仓库各设四项：
   - `OSS_CI_ACCESS_KEY_ID`
   - `OSS_CI_ACCESS_KEY_SECRET`
   - `OSS_CI_BUCKET`（Bucket 名）
   - `OSS_CI_ENDPOINT`（`oss-ap-southeast-1.aliyuncs.com`）
4. 在 workflow（GitHub 自动化流程）的上传步骤里，先用 `stat` 确认目标路径还不存在，再用 `cp` 上传。版本号已被占用时直接失败，不覆盖。
   - `ai-env-mgr` 的 `.github/workflows/release.yml` 已经有这一步。
   - `codex-kiosk` 照抄即可。

## 3. 两个程序的用法

- `agent.exe`：装在云电脑上。
- `admin.exe`：留在管理员自己的电脑上。

---

### 3.1 `agent.exe`：云电脑上的服务

| 命令 | 作用 | 需要管理员身份 |
|---|---|---|
| `setup` | 一条命令装好：复制到位、收紧权限、注册服务、启动、验证 | 是 |
| `prepare-image` | 停止服务，清理模板机的设备身份和临时同步标记，用于制作可复用的镜像 | 是 |
| `sync` | 立即执行一次完整同步 | 是 |
| `status` | 打印本机当前状态，**只读** | 否 |
| `install` / `uninstall` | 单独注册/卸载服务 | 是 |
| `start` / `stop` | 启动/停止服务 | 是 |
| `run` | 服务本体，由 Windows 服务管理器调用，不用手动跑 | — |
| `version` | 显示版本号 | 否 |

#### `setup`：装机只用这一条

```powershell
.\agent.exe setup
```

这条命令会复制文件、收紧权限、注册并启动服务，再跑一次同步验证。

注意：模板机的设备身份不能被复制到克隆出来的机器上。所以制作镜像前，要以管理员身份执行：

```powershell
.\agent.exe prepare-image
```

这条命令会：

1. 停止 Agent 服务。
2. 删除以下内容：
   - `C:\ProgramData\AIEnvMgr\device.token`（本机的设备身份）；
   - 临时同步标记；
   - Codex 的失败/下载标记；
   - 本机各用户配置目录里由 Agent 下发的 AI 凭据。
3. 保留 Windows 服务注册。

然后：

1. 关机，制作镜像。
2. 每台克隆机第一次启动时，会按自己的主机名重新注册。
3. 新机器出现在后台后，再执行"允许注册"并绑定员工。

#### 日志

日志文件是 `C:\ProgramData\AIEnvMgr\agent.log`。超过 4MB 会自动换新文件，上一份改名为 `agent.log.1`。

```powershell
Get-Content C:\ProgramData\AIEnvMgr\agent.log -Tail 30
Get-Content C:\ProgramData\AIEnvMgr\agent.log -Tail 20 -Wait   # 实时跟
Get-Service AIEnvMgrAgent                                        # 服务在不在跑
```

**不上机器，远程看日志：** agent 每完成一次完整同步，会把日志**末尾最近约 64KB** 上传到 OSS 的 `_logs/{主机名}.log`。管理员在控制台的**机器详情 → 日志**里就能查看（原来的 `admin.exe log` 命令已随命令行工具一起移除）。

- 这里只有最近的一段。完整日志仍在机器本地的 `agent.log`。

#### 服务每轮做什么

一次**完整同步**依次做这些事：

1. 拉取全局 `policy.json`，写入浏览器封禁策略。这一步**一定执行**，不管机器有没有绑定员工。
2. 用主机名查绑定文件，得知这台机器给哪个员工用。
3. 拉取这个员工的 `credentials.zip`，放进他的 profile。文件没变（ETag，即 OSS 给文件的版本标记，没变）就不重新下载。
4. 采集（如果已开启）：把员工的会话文件上传到 `data_collect/`。
5. 自动更新（如果 policy 指定了别的版本）：下载、校验，然后替换 exe 并重启。
6. 按主机名写状态文件上报，并把日志末尾传到 `_logs/`。

**什么时候触发完整同步：**
- 服务启动时；
- 机器从休眠中唤醒时；
- 距上次完整同步超过了设定的间隔时。

**心跳：** 两次完整同步之间，agent **每分钟**会刷新一次"最近露面"时间。这一步很轻：不拉策略，也不动员工的工具。
- 所以同步间隔可以设得长一些，省流量。
- 控制台判断机器是否在线，仍然是按分钟实时的。这也是为什么机器安静几分钟就会被判为"离线"。

**关机/休眠时的上报：** agent 收到系统的关机或休眠通知时，会赶在断网前上报一次状态（`stopped` 或 `suspend`）。这样管理员能分清机器是"正常离开"还是"崩溃了"。
- 关机：走 **PreShutdown** 通知。系统在断开网络前先通知 agent，留出约 180 秒，大概率能报出去。
- 真正的休眠挂起：尽力而为。
- 直接断电：收不到通知，靠时间判断兜底（见 §5.4）。

注意区分两件事：
- **休眠唤醒**是事件触发的，1 分钟内响应。
- 管理员在 OSS 上改了东西，**没有办法主动推给机器**。机器要等到下一个同步周期才知道。着急的话，在机器上跑 `agent.exe sync`。

### 3.2 `admin.exe`：管理控制台

不带参数直接运行，它会在本机开一个控制台网页：

```powershell
.\admin.exe                      # 监听 127.0.0.1:8080
```

用浏览器打开 `http://127.0.0.1:8080`，输入 OSS 的 AccessKey 登录即可。

**密钥是你运行时在浏览器里输入的，只存在程序内存里：**
- 不写磁盘、不存 cookie、不进日志。cookie 里只有一个随机 ID。
- **关掉程序就等于所有人都退出登录**，机器上不会留下任何能被别人翻到的东西。
- 程序里编译进去的只有 Bucket 名、endpoint（OSS 访问地址）和地域，**没有任何密钥**。

如果要部署成常驻服务（团队共用，带域名和 HTTPS），见 [Web控制台部署.md](Web控制台部署.md)。

> **命令行和 TUI（终端界面）已经移除，现在只有控制台网页一个入口。** 以前有一套功能相同的终端命令。但同一批操作维护两套界面，两边会慢慢变得不一致。机器状态的判定、OAuth 登录回调的解析、下载功能，都出现过两套不一致的实现。每一处不一致都是没人发现的 bug，直到有人碰上。

**控制台左侧导航有七组：**
- 总览
- 员工账号
- 发布（版本库）
- 用量（按月汇总 / 调用明细）
- 告警（告警 / 后台任务）
- 审计
- 设置（常规 / 封禁策略 / 告警与轮换 / 通知渠道 / 管理员）

旧地址都还能打开：`/logs`、`/tasks`、`/sites`、`/admins`、`/rollouts`。其中 `/rollouts` 不再出现在导航里。下面各节按这个顺序介绍。

**后台账号的角色**（在"设置 › 管理员"里建账号时选择，对应《ai工作间流程》§2）：

| 角色 | 对应流程里的角色 | 能做什么 |
|---|---|---|
| `admin` | 平台管理员 | 全部操作，包括：封禁策略、设置页的所有修改、发布页的"设为全局 / 清除全局"、删除员工账号、管理后台账号 |
| `operator` | 平台运营 | 日常操作：开户、关户、改预算、改可用模型、重发令牌、绑定/解绑/注销机器、立即同步、关闭 Codex、"指定给机器"、改版本说明、处理告警 |
| `viewer` / `security` | 对账、审计等只看不改的人 | 所有页面只读 |

- 运营角色打开设置页和封禁策略页时，整页只读，并注明原因。
- 运营角色看不到发布页的"设为全局"和员工页的"删除账号"按钮。
- 服务端按同一张权限表拒绝越权请求（代码在 `adminweb/roles.go`）。页面隐藏按钮只是表面，真正的拦截在服务端。

#### 3.2.1 总览

登录后的第一页。一屏显示三块内容：机队（所有机器）、当前策略、模型网关。

**机队状态条**在最上面，显示机器构成：正常 / 待处理 / 异常各有多少台。

**当前策略**一行列出：同步间隔、网站拦截、会话采集、两个目标版本。每台机器同步时读到的就是这一份。每一项都链接到可以修改它的页面，这里只能看。

**模型网关**一块：
- 显示网关地址。
- 配了日志项目时，旁边还会显示最近 60 分钟的探测结果（判断方法和日志页相同）。
- 展开「可用模型」，能看到网关自己报出的模型清单。控制台本身不维护模型清单。令牌和额度在**员工账号**页管理。
- 连不上网关时，这一块显示「网关不可达」，页面其他部分不受影响。

**机器表**在下面，每台机器一行。各列含义：

- **主机名**：agent 自己上报的 Windows 计算机名，你不用事先知道。机器开机后会自己出现，显示为"未分配"。
- **员工**：绑定给了谁。
- **状态**：一个词说明这台机器需不需要你处理。取值见 §5.4。
- **最后同步**：相对时间（如"50 分钟前"），鼠标悬停可看精确时间。活着的 agent **每分钟**心跳一次，所以这一列能实时反映 agent 是否还活着。
- **版本**：这台机器上 agent 的版本。**和其他机器对比着看**，升级后能看出谁还停在旧版。

每行末尾有**日志**和**解绑**两个按钮。日志页会先分别列出这台机器的**错误**和**提示**，再显示日志原文，不用在几百行同步记录里翻找。

**绑定机器：** 填主机名，从下拉框里选员工。
- 员工必须先在名单里。
- 要换人，直接重新绑定，会覆盖原来的。

**注销机器：** 删除这台机器的绑定记录和状态上报，它会从列表里消失。这个操作不能撤销，所以要求**把主机名原样输一遍确认**。

> 解绑和注销的区别：
> - 解绑：只取消分配。机器还在列表里，显示"未分配"。
> - 注销：连状态上报也删掉，机器**从列表消失**。
> - 如果机器还开着，注销后它下个同步周期又会出现。所以**注销只用于真正下线的机器**。

#### 3.2.2 员工账号

在这里登记、停用、启用员工。

**开户必须填邮箱**（2026-09-24 起，对应《ai工作间流程》§7）：
- 员工用这个邮箱接收云电脑的登录验证码。
- 开通邮件由阿里云发送。控制台只记录邮箱，不往里发信。
- 列表里，邮箱显示在姓名下面。已有员工的邮箱在详情页"基本信息"里补填。
- 同一个名字再新增一次，算更新，不会重复建。账户名不区分大小写，`Work1` 和 `work1` 是同一个人。

**额度只有月预算**（2026-09-24 起）：
- 员工只受每月花费上限约束，每月 1 号（UTC 时间）重置。
- 请求数、token 数、并发数都不限。
- 网关没法清除已经设过的限制，所以"不限"的做法是写一个实际用不到的固定值：每分钟 100 万次请求、100 亿 token、并发 1000。开户和改预算时会自动带上，页面上不显示。
- 以前的员工已经用 `ai-env-migrate lift-rate-limits` 一次性改过来了。这条命令只改在职员工，保留各自的预算，重复运行不会再有变化。

**"停用"会真正吊销凭据，不只是改个标记：**

1. 控制台删除 OSS 上这个员工的 `credentials.zip`。
2. agent 去取这个文件，收到**明确的 404**（服务器回复"文件不存在"）。
3. agent 删除这个员工 profile 里的本地凭据文件，并结束他的 AI 工具进程。

这里的关键是**分清"文件确实没了"和"暂时连不上"**：
- 只有服务器真的返回 404，才算吊销。
- 网络超时之类的情况，一律不动。
- 否则一次网络波动，就会把所有机器上的登录状态一起清掉。

> 停用后再启用，**不会**恢复凭据，要重新签发一次。吊销本来就应该这样。

> **别忘了 OSS 之外的一步：** 本方案只能删掉机器上的登录状态，删不掉 AI 账户本身。正式的离职流程还要去 OpenAI / Anthropic 后台改密码，或吊销这个账户的登录会话。

#### 3.2.3 封禁策略

在这里增删要封禁的域名，以及控制总开关。

策略**全局只有一份**，和员工名单无关。改一次，所有机器都生效，包括**还没分配给任何人的机器**。

域名可以一次填多个：
- 用换行、逗号、空格分隔都可以。
- 会自动去重、排序、转小写。`Foo.com` 和 ` foo.com ` 算同一个。

**"临时全局关闭"是给管理员自己临时访问用的。**
- 打开后，agent 会**删除**注册表里的封禁项，而不是写一个空清单。
- 原因：三种浏览器都只把"封禁项不存在"明确当作"不管控"。
- 用完记得恢复。

#### 3.2.4 会话采集

同步间隔和采集开关都在这里设置。

**同步间隔**只能设在 **1–1440 分钟**之间，超出范围会自动改成最近的边界值。这样可以防止两种误操作：
- 设成 0，agent 不停地轮询；
- 设成好几天，机器实际上等于失联。

> 机器要**先同步一次**，才会拿到新的间隔。调试时设成 1 分钟很方便，**正式上线建议改回 5–10 分钟**。

**采集**打开后，agent 会把 AI 会话的原始文件上传到 OSS 的 `data_collect/{用户}/` 下，供以后汇总和分析。规则如下：

- **按机器上的每个用户分别采集，和绑定无关。** 一台机器上有几个真人账户（不算 Administrator 和系统账户），就分别采到各自的 `data_collect/{该用户}/`。共享云电脑上有多人用 AI 时，**每个人都会被采集**，不只是绑定的那一个。
- **默认关闭。** agent 对 `data_collect` 的**只写**权限，是你打开这个功能时才补上的（通配所有用户：`agent_workdir/*/data_collect/*`）。
- **起始日期：** 只采集这个日期（UTC）之后的会话。留空表示采集全部历史。
- **静默秒数：** 文件停止变化多少秒后才上传，避免文件还在写就传上去。留空默认 60 秒。

页面下方的统计**按 OSS 里实际有数据的用户列出**（包括不在员工名单里的账户），用来核对"谁在产生数据、传了多少"。

#### 3.2.5 发布更新

agent 和 Codex 桌面版都在这一页发布。

**这是整个系统里最危险的操作**：发布会让**每一台机器**下载并运行一个程序。所以：
- 要求**把版本号原样再输一遍**才生效；
- 每次都写审计日志，记录真实的客户端 IP，不记录 token 和凭证。

**发布 agent**

有两种方式：
- 上传文件；
- 填一个 release 地址，让服务器自己去下载。私有仓库要填 GitHub token，**每次发布时现场输入，服务器不保存**。

发布后，每台机器上的 agent 会：

1. 每轮对比版本。
2. 下载 `_agent/agent.exe`。
3. **校验 SHA-256**。
4. 替换文件（旧文件保留为 `agent.exe.old`）。
5. 重启服务。

注意：
- **policy 是全局的。agent 发布一次就是所有机器一起更新，没有灰度，也没有自动回滚。** 务必先在**一台机器**上验证新 exe 能正常运行（见 §4.7）。
- 校验不通过就不替换。同一个目标版本只尝试一次，不会反复重启。"清除目标"是紧急停止按钮。
- agent 的 RAM 策略要有 `_agent/*` 的 **GetObject**（读取）权限。`dist/ram-policy-agent.json` 里已经包含。

**发布 Codex**

和 agent 类似，但有两点不同：

- **发布就是所有机器一起安装，和 agent 一样没有灰度。**
  - 这个安装包是对上游（OpenAI 官方）Codex 重新打包的，我们的补丁要跟着上游版本调整。
  - 构建通过，只能说明补丁打上了，**不能证明 ChatGPT 入口真的消失了**。这只有在 Windows 真机上才能验证。
  - 所以顺序是：**先在一台真机上装好、验收，再发布**。发布是最后一步，不是用来测试的。

  > 以前这里有一个"按主机名哈希抽一定比例机器"的灰度功能，后来取消了。原因：机器数量少，发 10% 经常一台都抽不中；而它想带来的把握，本来就要靠真机验收，灰度给不了。

- **用 URL 方式，不要上传。** 安装包约 700 MB，浏览器上传会被 CDN 的文件大小限制挡住。让服务器直接下载更快、更稳。

**版本号填什么：** 把 codex-kiosk 的 release tag 去掉 `offline-v` 前缀。例如 tag 是 `offline-v26.803.81509-b1`，就填 `26.803.81509-b1`。

- 前面的 `26.803.81509` 就是**应用"关于"面板里显示的版本号**。员工报给你的版本号和你填的能对上。
- 后面的 `-b1` 表示**我们第几次重新打包这个上游版本**。补丁改了重新构建，会变成 `-b2`。正是这个变化让所有机器重新安装。没有这个后缀，每台机器都会认为自己已经是最新版而跳过安装。
- release 名字括号里的 `MSIX 26.803.10989.0` 是上游原始包的版本，只用来追溯来源，**不要填它**。机器上根本没有这个版本号。

版本对比**看是否相等，不是"只升不降"**。所以把目标改回旧版本，就是回滚。

agent 这边有三条保护：
- 校验和对不上，**拒绝安装**。
- 同一个版本**只尝试一次**。失败后不会每个周期都重新下载 700 MB。
- Codex 正在运行或磁盘空间不足时，**推迟安装**，不会把正在用的应用从员工手里抢走。

发布是**后台任务**：
- 提交后页面立刻返回，每 5 秒自动刷新显示进度。可以直接关掉页面。
- 同一时间只允许一个发布在运行。原因：两个同时运行会抢着写同一份策略，后完成的会悄悄覆盖先完成的。

页面下方的机队现状，能一眼看出**发布了什么版本，以及每台机器实际装上了什么版本**。

#### 3.2.6 云电脑状态查询

控制台还会向阿里云无影查询云电脑的状态。目的是回答一个 agent 自己答不了的问题：**一台没有上报的机器，是睡着了还是挂了。**

为什么 agent 答不了：无影是在**虚拟化层**（云电脑底下的平台层）把整台机器挂起的。云电脑里的 Windows 收不到任何电源事件，agent 也就没机会说"我要睡了"。这一点实测确认过：休眠前后既没有生命周期日志，也没有唤醒后的同步，只有两次定时同步之间的一段空白。只有平台知道机器的真实状态。

查询规则：

- **只在需要时查。** 只对已经没有上报的机器发起查询。所有机器都正常上报时，一次查询都不会发生。查询结果缓存 1 分钟。
- **用的就是你登录时输入的那把密钥**，不需要第二把。所以发布的程序里没有任何密钥可以泄露。前提是这把密钥所属的 RAM 用户有 `AliyunECDReadOnlyAccess` 权限。
- **不能用 agent 的那把密钥。** 那把密钥明文存放在每台员工云电脑上。给它加这个权限，任何一台机器都能查出全公司有哪些云电脑、分别是谁在用。
- 因此，**只有有人登录控制台时才会查询**。这不会少什么：查询结果只用来显示这个页面，没人登录就没人看。
- 没有这个权限时，查询会失败（会记日志）。没上报的机器仍显示"离线"，其他功能照常。

状态怎么判定，见 §5.4。

## 4. 标准流程

### 4.1 首次部署

完整命令见 `dist/部署说明.md` 第一、二节。按这个顺序做：

1. 建 OSS Bucket 和 RAM 用户（见 §2）。
2. 控制台 → **封禁策略**：确认开关是"拦截中"，并核对域名清单。
3. 在模板机上（管理员身份）安装 AI 工具，再用 `02-Manage-AIAccess.ps1 -Init` 配置 AppLocker（先用审计模式）。
4. 把填好配置的 `agent.exe` 装成服务，执行一次同步。
5. 逐条核对同步输出，再用浏览器实际打开 chatgpt.com，确认被拦截。
6. 把 AppLocker 切到强制模式。
7. 执行 `agent.exe prepare-image` 清理模板机身份（见 §3.1），关机，制作自定义镜像。

**镜像发出去以后再改，就只能一台一台改了**，所以第 5 步别省。

### 4.2 新员工入职

入职从**无影控制台**开始：先给员工开一台云电脑、建好 Windows 账户，再回到 `admin` 登记和绑定。

#### 第 1 步：在无影控制台创建云电脑

用**公司自定义镜像**（§4.1 第 7 步做好的那个）给新员工开一台云电脑。镜像里 agent 已设为开机自启，浏览器封禁和 AppLocker 也都配好了，开机就生效。

> **机器什么时候出现在控制台里：**
> - agent 是**开机自启的系统服务（以 SYSTEM 身份运行）**，**不用等任何人登录**。云电脑一开机，agent 完成第一次同步，这台机器就会出现在**总览**页。第 5 步要靠它来找机器绑定。
> - 登录只影响 `work1` 是否出现在 `LocalUsers`（本机用户列表）里，也就是状态从"缺少用户"变成"正常"。
> - 如果你们的云电脑是**连接时才开机**（按需开机），它要在**第一次被启动（通常就是员工第一次连接）之后**才会出现在 status 里。想在员工到岗前就绑定，你先自己连一次，把它开起来即可。

#### 第 2 步：创建 Windows 标准用户

在这台云电脑上给员工建一个**标准用户**（不是管理员），例如 `work1`。

> ⚠️ 一定要是**标准用户**。标准用户无权删除 HKLM 里的浏览器封禁策略，这正是"员工绕不过封禁"的前提。管理员账户则可以自己删掉封禁。

#### 第 3 步：员工第一次登录（生成 profile）

Windows 用户**第一次登录时才会生成 profile**，而凭据必须放进这个目录。所以让员工（或你代他）用 `work1` 登录一次。

> 这一步晚于绑定也没关系。员工第一次登录后，**下一个同步周期**凭据就会放到位。在这之前，控制台会把这台机器标为"缺少用户"。

#### 第 4 步：登记员工（admin）

在管理员电脑上直接运行 `admin.exe`（不带参数），浏览器打开 `http://127.0.0.1:8080` 登录。然后：

```
导航 2 员工账号 → 新增
  员工名: work1
  codex 邮箱(备注,可空): ai-work1@company.com
```

邮箱只作为管理员的备注（见 §3.2.2 员工账号）。

#### 第 5 步：找到这台机器并绑定

机器开机后 agent 会自动上报，在**总览**页的机器表里显示为"未分配"：

```
导航 1 总览:看哪台显示"未分配",再用下面的「绑定机器」
  主机名: <主机名>
  员工名: work1
  备注(可空): 研发部-张三
```

主机名不用事先知道，从机器状态里认：表格下方会列出这台机器上有哪些本地账户，据此判断是哪一台。

#### 第 6 步：等一个同步周期（或手动触发一次）

绑定后，agent 会在**下一个同步周期**拉取配置，把 `work1` 的凭据放到位。
- 默认周期是 30 分钟，正式上线建议改成 5–10 分钟。在控制台的"设置 → 同步间隔"里改，见 §3.2.4。
- 要立刻生效，就在那台机器上跑一次 `agent.exe sync`。

完成后，员工打开 Codex 就已经是登录状态；用浏览器访问 AI 网站会被拦截。

### 4.3 凭据过期

控制台 → **员工账号**：对这个员工点"重新签发"。各台机器在下个同步周期会自动更新。

**配置更新什么时候生效、会不会打断员工：**
- 只有模型目录变了：新版 agent 把目录写到磁盘，不结束当前任务，员工下次启动 Codex 时加载。被移除的模型，网关会立即禁止调用。
- 令牌或其他受管配置变了：配置放到位后，仍会结束这个员工的工具进程。管理员必须提前通知员工保存工作。
- 吊销不等本地同步。
- 以上规则需要部署对应的新版 agent。旧版 agent 仍可能因为目录变化而结束进程。

**失败时怎么处理：**
- 员工原来能用的模型全部下架时，补发令牌会停止。先在"可用模型"里明确选好模型，再补发。
- 读取旧凭据包时超时、没有权限或包已损坏，系统不会覆盖原包。先恢复读取，或者用核对过的备份修好这个包，再重试。
- 模型权限更新分三步：用户、令牌、目录。后一步失败，不代表前面几步已经撤回。按错误提示，用相同的选择重试。失败的尝试会保留在审计记录里。

反过来，**重发一个内容完全相同的包，不会打断任何人**。判断依据是写到磁盘上的内容有没有变，而不是"有没有发过一次"。

只结束**这个员工**的进程（`taskkill /FI "USERNAME eq <员工>"`），同一台机器上其他人的会话不受影响。员工当时没开 Codex 也正常，不会报错。

### 4.4 员工离职

- 控制台 → **员工**：对这个员工点"停用"（停用并吊销凭据）。
- 控制台 → **总览**：对他的机器点"解绑"（机器要转给别人用时才需要）。

**真正起作用的是"停用"：**

1. 停用会删除 OSS 上这个员工的 `credentials.zip`。
2. agent 读不到凭据文件（收到明确的 404）时，会删掉这个员工 profile 里的本地凭据文件。
3. 同时结束这个员工会话里正在运行的 AI 工具进程。原因：只删文件不关进程的话，内存里的令牌还能继续用。

生效时间同样是**下一个同步周期**。要立刻吊销，就去那台机器上跑 `agent.exe sync`。

> **别忘了 OSS 之外的一步：** 本方案能删掉机器上的登录状态，但删不掉 AI 账户本身。正式的离职流程还要去 OpenAI / Anthropic 后台改密码，或吊销这个账户的登录会话。否则员工在自己的设备上仍然是登录状态。

没解绑的机器会在**总览**页显示**已离职**。意思是这台机器还挂在一个已停用的人名下，需要重新分配或下线。

**离职满 7 天的清理提醒**（2026-09-24 起）：

- 关户满 7 天后，如果员工名下还有没注销的机器，告警页会出现"<员工> 已离职 N 天，待清理"，并写明是哪几台机器。天数可以在"设置 › 告警与轮换"里改。
- 处理方法：
  1. 按《ai工作间流程》§8 删除阿里云账号、释放实例并删除数据。
  2. 到机器页点「注销」。
  3. 注销后，下一轮规则检查（10 分钟内）会自动关闭这条提醒。
- 关户时**不会解绑**机器。原因有两个：
  - 吊销要靠绑定关系才能送到机器上；
  - 保留绑定，离职员工的机器关机时也不会触发离线告警。

### 4.4b 关闭员工的 Codex

**按钮在哪：**
- 控制台 → **总览** → 机器表里这台机器那一行，「日志 · 解绑」旁边的「关闭 Codex」。
- 员工详情页（**员工账号** → 点开某人）的令牌一栏也有一个，写作「关闭 <主机名> 上的 Codex」，作用完全一样。刚给人重发完令牌时，不用再跳回总览。
- 只有**已绑定**的机器才有这个按钮。没绑人，就没有会话可关。

**什么时候用：**
- 员工的 Codex 卡住了，要重开；
- 机器要转给别人，先清干净；
- 你改了什么，想让他立刻重新加载。

日常的令牌轮换和关户**不用**按，原因见本节最后一段。

**什么时候生效：** 按下后，**机器上不会马上有反应**。
- 指令写进这台机器的绑定记录，agent 下个同步周期（默认 30 分钟，见 §3.2.4）读到后才执行。
- 页面顶部的提示条会写明当前的同步间隔。
- 要立刻生效，就去那台机器上跑一次 `agent.exe sync`。

**怎么看结果：** 看同一行下方的小字。

- **关闭 Codex：待执行（下个同步周期）**：指令已下发，agent 还没读到。
- **已关闭 3 分钟前 · killed 1 process**：已执行，关掉了 1 个进程。如果显示 `no process`，意思是当时这个员工没开 Codex，也算成功。
- **待执行 · no bound user profile**：绑定的员工在这台机器上还没有用户目录（从没登录过）。指令会一直等，直到他登录后第一次同步时才执行。

**按两次**会下发两条指令，执行两次。但同一条指令只执行一次：agent 记得自己处理过的指令编号，之后每个周期重新读绑定时，不会再关一遍。

**和"凭据变化时自动关闭"是什么关系：** 两者是同一件事的两种触发方式。
- 凭据包有变化或被删除时，agent 自己就会关（§4.3、§4.4），**不需要**再按这个按钮。
- 这个按钮是给"凭据没变，但就是想关一次"的情况用的。
- 给机器换绑员工时，没执行的指令会被清掉，不会落到新员工头上。

### 4.5 管理员临时需要访问 AI 网站

控制台 → **封禁策略** → "临时全局关闭"。

### 4.6 调整封禁清单

控制台 → **封禁策略**：在"增删域名"里填写。新增和移除都可以一次提交多个。

### 4.6b 模型上架、下架后的下发（2026-09-24 起）

对应《ai工作间流程》§3 第 5~6 步、§4 第 3~4 步。

员工的 Codex 配置和模型选择清单（`config.toml`、`models.json`）是按网关当时的模型生成的。网关上新增或停用了模型后，**要下发一次**，员工才能看到变化。

1. 平台管理员在 LiteLLM 上完成上架或下架，确认调用正常。
2. 打开"员工账号 › 模型与渠道"页的"模型下发"。它会对比网关现在的模型和上次全部下发时的模型，写明新增了哪些、下架了哪些，或者显示"模型信息有改动"。
3. **先测试**：选一个测试员工，点"先发给他"。等下面的表显示他的机器"已收到"，让他重启 Codex，确认新模型能用（或下架的模型已经消失）。这一步代替流程里的"测试环境"。
4. **全部下发**：点"全部下发"。表格逐台显示进度：生成中 → 等待同步（在线/离线）→ 已收到。生成失败、同步出错会标红并写明原因。1.3.0 版 agent 的机器几秒内就能收到；旧版 agent 要等同步间隔。
5. 看到"已收到"，就可以通知这个员工：当前请求完成后重启 Codex。

**下发时 Codex 会不会被关掉**（agent 1.3.1 起）：
- 只有**令牌或网关地址**变了，agent 才会关闭正在运行的 Codex，例如重发令牌、令牌轮换。
- 模型下发、改可用模型，只更新文件。员工重启 Codex 后生效，正在跑的任务不受影响。
- 员工在 Codex 里自己选的模型会保留。只有这个模型被下架时，才改回默认模型。
- 更早版本的 agent：员工切换过模型的，下发时 Codex 会被关闭。

**本机配置不再自动修复**（agent 1.3.1 起）：
- Codex 运行时会改写自己的 `config.toml`。所以 agent 不再每轮把这个文件"改回去"。
- agent 只在控制台下发新内容时写入，即开户、改模型、重发令牌、模型下发这几种情况。员工第一次登录后的第一次写入仍然自动完成。
- 员工把配置弄坏了，就到员工页点"重发令牌"，或在"模型与渠道"页用"模型下发"给他重发一次。

其他说明：
- 下发只重新生成配置，不换令牌，也不改员工能用哪些模型。
- 某个员工能用的模型全部被下架时，他那一行会显示"生成失败"，要到员工页给他换模型。
- 平台运营（operator）就可以操作。

### 4.6c 渠道：一键暂停某家供应商（2026-09-25 起）

"员工账号 › 模型与渠道"页的"渠道"表，按供应商列出网关上的模型。总览页只显示一行概况，被暂停的渠道会标出来。供应商有三家：
- AWS Bedrock
- Google Vertex
- Azure OpenAI（Azure 的模型在网关里走 OpenAI 兼容接口，控制台靠 `*.azure.com` 地址认出它）

某家供应商出故障、欠费或要停用时：

1. 管理员在那一行填写原因（可选），输入渠道代号（如 `google`）确认，点"暂停"。
2. 控制台随即做两件事：
   - 给所有员工重新生成模型清单，去掉这个渠道的模型。进度在"模型下发"里看。agent 1.3.1 起不会打断正在运行的 Codex，员工重启后生效。
   - 勾了"全部模型"的员工，在网关上改为只能调用其他渠道的模型。对暂停渠道的调用会被直接拒绝。
3. 其他渠道也提供的同名模型不受影响。例如 qwen3-coder、gpt-oss 在 AWS 和 Google 上都有部署，暂停 Google 后照常可用。
4. 恢复时点"恢复"。模型回到选择清单里，勾了"全部模型"的员工在网关上恢复不限。

其他说明：
- 只有 admin 角色能暂停和恢复。每次操作都记审计（`gateway.channel_pause` / `gateway.channel_resume`）。
- 员工有明确的可用模型列表时，网关上的列表不变，但选择清单里照样隐藏暂停渠道的模型。
- 如果他列表里的模型全在暂停的渠道上，他那一行下发会"生成失败"，要到员工页给他换模型。
- 模型属于哪个渠道，可以在网关模型的 `model_info` 里写 `channel` 来明确指定。

### 4.7 发布 Agent 与 Codex（数据库模式；2026-09-24 简化）

只有两种下发方式：
- **设为全局**：所有跟随全局的机器一起更新。
- **给机器单独指定版本**。

没有登记、验收这两道手续。

1. **出包：**
   - agent：打 `v<版本>` tag。
   - Codex：在 codex-kiosk 跑 `push-codex-to-oss`。
   - CI 把包传到 OSS：agent 到 `_agent/<版本>/agent.exe`，Codex 到 `_codex/codex-setup-<版本>.exe`。
   - 控制台每天扫描一次 OSS，扫到的版本自动出现在"发布"页。刚传完的话，点"立即扫描 OSS"。
   - 一个版本号只对应一个包。重新构建要换版本号。
2. **设为全局：** 在那个版本的一行输入版本号确认，点"设为全局"。
   - 所有跟随全局的机器都会更新到这个版本。1.3.0 起，在线的机器几秒内开始更新。
   - "清除全局"是紧急停止：还没更新的机器停止尝试，已经装上的不回退。
3. **单独指定：** 两个入口，效果相同。
   - "发布"页那一行点"指定给机器…"，勾选几台；
   - 机器页"版本"一栏的下拉框，选"指定 x.y.z"或"跟随全局"，保存。

   被指定的机器不再跟随全局，直到在机器页改回"跟随全局"。想先试新版，就先指定给一台，用一天后再设为全局。
4. **看结果：**
   - 总览的 AGENT 列：版本没到位时显示"→ 应装版本"。
   - 机器页"版本"一栏：写着当前版本、应装版本，以及是跟随全局还是单独指定。
   - 机器页"版本记录"：每次指定的结果（成功、失败原因、延后原因）。
5. **停用：** 有问题的版本点"停用"，它就不能再被设为全局或指定给机器。已经装上的不受影响。当前的全局版本不能停用，要先把别的版本设为全局。
6. **旧 agent（低于 1.2.16）：** 不支持单独指定，只能跟随全局，机器页会写明。现有 3 台 1.2.14 的机器要升到 1.3.0，只能用"设为全局"。

如果 Codex 依赖新版 agent，先把 agent 发好，再发 Codex。

### 4.8 用量、告警、令牌轮换（数据库模式，2026-09-21 起）

**用量**（导航 4，页签"按月汇总"；"调用明细"就是原来的日志页）：
- 每天 UTC 0:30，后台程序（Worker）从日志服务取出前三天的网关调用记录，按员工、模型汇总存进数据库。按 `event_id` 去重。日志过期后，这里的数据仍然保留。
- 页面按月查看，分员工、模型、日期三张表，可以导出 CSV。员工详情页能看最近 30 天。
- "立即重算最近三天"按钮，是给刚改完日志采集设置时用的。
- 日志里的令牌别名对应不上员工的记录，单独列在"未关联到员工"里。

**告警**（导航 5；"后台任务"页签就是原来的任务页）：
- 每 10 分钟检查五条规则：
  - 绑定的机器超过 N 小时没上报；
  - 机器最近一次安装失败；
  - 网关上的令牌和控制台记录不一致；
  - 员工预算用到 N% / 100%；
  - 任务重试次数用完。
- 条件消失后，告警自动关闭。人工可以点"确认"（表示有人在处理）或"关闭"。
- 每条告警只通知一次。通知失败会重试，最多 10 次，并把错误写在这一行上。
- 阈值在"设置 › 告警与轮换"里设。通知渠道在"设置 › 通知渠道"里设，有两种：
  - webhook：支持通用 JSON、钉钉机器人、飞书机器人。签名密钥加密后存进数据库。
  - 邮件（SMTP）：465 端口直接走 TLS 加密，其他端口用 STARTTLS 升级加密；没有加密就不发送密码。
  - 两种渠道各有"发送测试"按钮。
- 刚配好通知渠道时，之前已经存在的告警不会补发通知。

**令牌轮换：**
- 默认关闭，在"设置 › 告警与轮换"里打开。
- 打开后，每天 UTC 1:00，把使用天数超过上限（默认 90 天）的员工令牌重发一遍。效果和详情页的"重发"完全一样：旧令牌吊销，新令牌下发，员工感觉不到。
- 每天最多处理 N 人。
- 最近 24 小时没同步过的机器会跳过，写在任务备注里，等它重新上线再处理。
- 员工列表的"令牌"列显示签发日期、已用天数和"待轮换"标记。
- 审计里的动作名是 `account.rotate`，操作者显示为 `rotation`。

### 4.9 设备通道：agent 直连控制台（agent 1.3.0 起）

**注册：**
- agent 1.3.0 启动时，如果本机没有设备令牌，就向控制台报上主机名，申请一个。不需要任何预先配置的密钥。
- **控制台没见过的主机名**，会成为一台"未分配"机器，和以前第一次上报时一样。
- **见过、但从没绑定过员工**的机器，也能自己注册。
- 以上两种情况，机器都只能拿到策略（封禁域名、AppLocker、采集开关、目标版本）和安装包，拿不到任何凭据。凭据只在"绑定"后才下发。
- 自己注册、但 7 天内没被绑定的机器，每天会被自动清除。

**控制台认识的机器，要先放行才能注册：**
- 绑定过员工、持有过令牌、或被注销过的主机名来注册，一律拒绝（返回 409 错误）。否则任何人只要报出这个主机名，就能领走对应员工的凭据。
- **在把现有机器升级到 1.3.0 之前，先到每台的机器页点"允许注册（24 小时）"。**
- 重装系统、丢了令牌文件，也是同样的操作。
- 放行期间，机器一注册成功，放行就自动关闭。

**控制台地址：**
- 写死在 `.github/workflows/release.yml` 的 `AGENT_CONSOLE_URL` 里（`https://windows-control.teenet.app`），构建时编译进 agent.exe。
- 要换地址，就改这一行再出新版本，必须走代码提交。
- 地址不是纯粹的 `https://主机[:端口]` 格式时，构建直接失败。
- agent 也会拒绝非 https 的地址（只放行本机回环地址，供本地测试）。拒绝时记一条日志，继续走 OSS。
- 正式构建的 agent 不读 `agent.config.json` 里的地址。所以在机器上改这个文件，改不了它连接哪个控制台。

**吊销令牌：**
- 在机器页点"吊销令牌"，同时会放行这台机器一小时。
- 它下一次请求会被拒绝，然后自己重新注册。所以这不是锁定；要锁定，用"注销机器"。

**限制来源 IP：** 在"设置 › 设备通道"里可以填"允许注册的 IP 段"。拿到无影云电脑的出口 IP 后填上。

**过渡期：**
- "设置 › 设备通道"里有两个开关："继续写 OSS 命令对象"和"继续从 OSS 导入状态"，默认都开着。
- 等总览页"通道"一列全部变成 API 后，把两个开关都关掉。之后 OSS 里只剩安装包、采集归档和备份。
- 对走 API 通道的机器，日志页显示 agent 直接送来的日志末尾。

### 4.10 换主密钥与其他密钥

主密钥文件是 `/etc/ai-env-mgr/master.key`（文件权限 600）。数据库里的员工令牌、管理员验证器种子、告警渠道的密码，都是用它加密的。

换主密钥不用停服务，分四步：

```
# 1. 加一把新钥并设为 current(旧钥留着)
umask 077
python3 - <<'PY'
import json,os,base64
p='/etc/ai-env-mgr/master.key'; f=json.load(open(p))
f['keys']['k2']=base64.b64encode(os.urandom(32)).decode(); f['current']='k2'
json.dump(f,open(p,'w'))
PY
# 2. 重启控制台,让它用新钥密封新值
systemctl restart ai-env-mgr-console
# 3. 把所有活跃密文重新密封到新钥(可先 -dry-run 看数量;中断了再跑一次即可)
ai-env-migrate -master-key /etc/ai-env-mgr/master.key rekey
# 4. 库里没有任何行再引用旧钥时,把旧钥从文件里删掉(原文件备份为 master.key.bak)
ai-env-migrate -master-key /etc/ai-env-mgr/master.key rekey -prune-unused
```

- `rekey` 只处理仍在使用的记录。已退役的凭据版本仍然指向旧钥。所以只要这些记录还在，第 4 步就会保留旧钥，并说明原因。不需要历史加密数据的话，可以先删掉这些退役记录。
- 换钥不影响管理员登录和凭据导出，换完照常使用。

其他几把密钥不在数据库里，要手工轮换：

| 密钥 | 怎么换 |
|---|---|
| 网关管理密钥（`AIENVMGR_GATEWAY_ADMIN_KEY`） | 先在网关上换新密钥，改环境文件，重启控制台，再在网关上作废旧密钥。 |
| 控制台的 OSS AK（`AIENVMGR_OSS_ACCESS_KEY_ID/SECRET`） | 在 RAM 里给同一个用户建第二把 AK，改环境文件，重启，确认状态导入和策略导出正常，再禁用旧 AK。 |
| CI 的 OSS AK（`OSS_CI_*` Secrets） | 同样先建新的，再删旧的。 |
| agent 的 OSS AK | 新版 agent 不再使用 OSS 密钥（见 §2.4），不用轮换。以下只适用于旧版 agent：通过策略下发。改了策略，所有机器下次同步就会换上。等全部机器都上报新版后，再禁用旧 AK。 |

换任何一把，出了问题都能在审计和任务页看到：导出失败、导入停滞、网关任务失败，都会立刻变成"任务失败"告警。

## 5. 故障排查

### 5.1 机器显示"从未上报"

意思是机器已绑定，但从来没上报过。按顺序检查：

```powershell
# 1. 服务在跑吗
Get-Service AIEnvMgrAgent

# 2. 手动同步看报错
.\agent.exe sync

# 3. 看日志
Get-Content C:\ProgramData\AIEnvMgr\agent.log -Tail 30
```

常见原因：
- **打进镜像的 agent.exe 没填配置。** 如果 `agent.exe status` 第一行是 `config=config file`，说明这个 exe 是空的，没填配置。填法见 `dist/部署说明.md`。
- （仅旧版 agent）endpoint（OSS 访问地址）填错：内网和公网地址搞反了，或者地域不对。
- （仅旧版 agent）AK/SK 错误，或者已被禁用。新版 agent 不带 OSS 密钥，不会有这个原因。
- 云电脑访问不了 OSS：被安全组或网络策略拦住了。

### 5.2 显示"未分配"

机器已经上报，但还没分配给员工。这是正常现象，绑定即可：

控制台 → **总览** → 绑定机器。

表格下方会列出这台机器上有哪些账户，据此判断该绑给谁。

### 5.3 显示"缺少用户"

绑定的员工在这台机器上没有 profile。有两种可能：

- **绑错了名字**：在**总览**页看绑的是谁，重新绑定即可。
- **这个用户从没登录过**：Windows 用户第一次登录才会生成 profile。让员工登录一次即可。

### 5.4 机器没动静了：休眠、关机，还是挂了

活着的 agent 大约每分钟上报一次心跳，所以"多久没上报"是很可靠的信号。

但云电脑会在下班、周末休眠或关机，这时没有上报是**正常**的。如果把每天休眠的机器都报成故障，告警很快就没人看了。

所以判断分两层：**先看 agent 自己报了什么；它报不出来时，再问阿里云平台。**

| 状态 | 怎么判断 | 要不要处理 |
|---|---|---|
| **正常** | **10 分钟**内有上报 | 不用 |
| **休眠中** | agent 报了"我要睡了"，或平台说它处于 `Hibernated`（休眠） | 不用，属于预期 |
| **已关机** | agent 报了"我被停止/关机了"，或平台说它是 `Stopped`（已停止） | 不用，状态已知 |
| **离线** | 超过 10 分钟没上报，而且**没能问到平台** | 不用，属于预期 |
| **agent 无响应** | 平台说这台机器**开着**（`Running`），但 agent 没有任何上报 | **要，需要排查** |
| **云端已删除** | 问了平台，平台上没有这台云电脑 | 要（该注销了） |
| **长期失联** | 超过 **3 天**没上报，而且问不到平台 | **要，需要排查** |

两个时间界限是怎么定的：

- **10 分钟（正常 ↔ 离线）：** 活着的 agent 每分钟心跳一次，10 分钟没上报就是连续 10 次心跳都没了。这个界限比同步间隔短得多，停服务或关机几分钟内就能看出来；又留有余量，一次网络波动不会误报。
- **3 天（离线 ↔ 长期失联）：** 休眠或关机的机器，一两天内会被唤醒；真挂了的 agent 不会自己恢复。

#### 为什么要问平台

**无影的"休眠"是在虚拟化层把整台机器冻住，云电脑里的 Windows 收不到任何电源事件。**

这一点实测确认过：让一台云电脑休眠再唤醒，本地日志里既没有生命周期记录，也没有唤醒后的同步，只有两次定时同步之间的一段空白。**agent 从头到尾没收到通知**，没有任何机会留下"最后一句话"。

所以在无影上，只靠 agent 分不清"睡着了"和"挂了"，两者看起来都是一样的没有上报。因此控制台会向阿里云查询云电脑状态，把"没有上报"细分成四种情况（见 §3.2.6）。

其中最有价值的是 **agent 无响应**：机器开着，平台也能查到，但 agent 就是不上报。如果不问平台，这种情况和"下班关机"看起来一模一样，**根本发现不了**。

> 注意：机器休眠时，平台返回的 `DesktopStatus`（云电脑状态字段）是 `Stopped`，休眠标记放在 `ManagementFlags` 字段里。如果只看状态字段，会把休眠误判成关机，又把要区分的两种情况混在一起了。

#### agent 自己的上报仍然有用

agent 在休眠或停止前上报状态，这个功能没有白做。遇到**真正的 Windows 电源事件**时，它是有效的。各种场景下的可靠程度：

- **停止服务**（`sc stop`，系统继续运行）：网络还在，**能可靠地**报出"已关机"。
- **关机 / 重启**：agent 注册了 **PreShutdown** 通知，系统断开网络**之前**就会收到（留出约 180 秒），**大概率**能报出去。
- **无影平台层面的休眠**：**收不到通知，报不出去**，靠查询平台兜底。
- **强制断电 / 从控制台硬关机**：操作系统也收不到通知，相当于崩溃，靠时间界限和查询平台兜底。

agent 自己报的状态优先于平台查询结果：它更及时，而且能说明机器是"主动"离开的。

#### 处理建议

- 看到 **agent 无响应**：机器是开着的。去看它的日志（**机器 → 日志**），多半是服务停了或 agent 崩溃了。
- 看到 **长期失联**：按 §5.1 排查。
- **休眠中、已关机、离线不算"需要关注"**。所以下班后，顶部的机队状态条不会一片红。
- 登录用的密钥没有 `AliyunECDReadOnlyAccess` 权限时，平台查询会失败，没上报的机器统一显示"离线"。这不算错，只是少了一层信息。

### 5.5 显示"已离职"

机器还绑定着一个已停用的员工。凭据已经吊销，但机器本身还在运行、还在上报，却没人负责。

控制台 → **总览** → 注销机器（需要把主机名原样输一遍确认）。

### 5.6 一台机器有多个用户

这是**允许的，不再报警**。
- 控制台会把这台机器上的账户都列出来，但不再标 `EXTRA USERS`（多余用户）。共享云电脑本来就可能有多人各自的账户。
- 采集也会**按用户分别采集**（见 §3.2.4）。
- 如果你怀疑某个账户不该存在（比如有人私自建账户想绕过管控），从账户列表里找出来，上机器核实即可。

### 5.7 封禁不生效

```powershell
# 确认策略已下发到本机
.\agent.exe status          # 看 block 和 domains

# 确认注册表已写入
Get-ItemProperty "HKLM:\SOFTWARE\Policies\Google\Chrome\URLBlocklist"
```

- **注册表里有值，但浏览器仍能访问**：浏览器没重启。重启浏览器，或在 `chrome://policy` 页面点"重新加载政策"。
- **注册表里没有值**：agent 没同步成功，按 §5.1 排查。
- **换个浏览器就能访问**：封禁策略只覆盖 Chrome、Edge、Firefox，其他浏览器要靠 AppLocker 拦截。

### 5.8 绿色版浏览器能绕过封禁

绿色版（免安装版）浏览器不读系统策略，只能靠 AppLocker 禁止它运行。

```powershell
.\agent.exe status          # 看 applocker 字段（只读，随便跑）
```

- 显示 **Audit**：AppLocker 还是审计模式，只记录、不拦截。需要在模板机上切换到强制模式，然后重新做镜像。
- 显示 **None**：AppLocker 没启用。检查 Windows 版本（需要企业版、教育版或 Server 版）和 AppIDSvc 服务（AppLocker 依赖的系统服务）。

### 5.9 员工打开 AI 工具仍要求登录

```powershell
.\agent.exe status          # 只读，看 "AI credentials in place for:" 那行
.\agent.exe sync            # 要看同步过程的错误就跑这条
```

`AI credentials in place for:` 这一行列出凭据已经放到位的员工。按现象分：

- **`status` 里这个员工不在 "credentials in place" 列表里**：凭据文件根本没放到机器上。跑 `sync` 看报错。常见原因是还没有为这个员工签发凭据，报错会是 `no credentials published for "xxx" yet`（还没有为 xxx 发布凭据）。
- **文件在，但打开工具仍要求登录**：令牌过期了。在控制台 → **员工账号**里对这个员工点"重新签发"（见 §4.3）。
- **`sync` 报 `credentials written but not readable by <员工>`**：意思是凭据文件写进去了，但这个员工读不到。原因是 ACL（Windows 文件权限）授权失败。看具体错误，通常是 profile 的权限异常。

## 6. 安全边界

**能做到：**

- 阻止员工用受管浏览器访问外部 AI 网站。
- 阻止运行绿色版浏览器等未授权程序（需 AppLocker 处于强制模式）。
- 员工不知道 AI 账户密码。
- 员工（标准用户）无法自己解除管控。
- 新版 agent 不带 OSS 密钥。旧版 agent 的密钥泄露了，也读不到员工名单、改不了策略、碰不到 `agent_workdir/` 以外的东西。
- **还没分配给任何人的机器同样被封禁**：策略是全局的，不依赖绑定。
- 员工离职后能远程吊销：删掉 OSS 上的凭据，机器下次同步时就会清掉本地登录状态。

**做不到：**

- 阻止员工用手机拍屏幕。
- 阻止员工用个人设备访问 AI。
- 阻止有本地管理员权限的人解除管控。
- （旧版 agent）阻止有管理员权限的人读出 agent 的密钥。旧版的密钥是明文编译在 exe 里的，用 `strings` 命令就能翻出来。
- **删掉 AI 账户本身**：只能删机器上的登录状态，账户还得去 OpenAI / Anthropic 后台处理。

**必要前提：**

- 员工账户必须是**标准用户**。
- 严格控制本地管理员权限的授予。
- OSS Bucket 必须是**私有**的。

## 7. 卸载与复原

**从单台机器移除 agent：**

```powershell
cd "C:\Program Files\AIEnvMgr"
.\agent.exe stop
.\agent.exe uninstall
Remove-Item "C:\Program Files\AIEnvMgr" -Recurse -Force
Remove-Item "C:\ProgramData\AIEnvMgr" -Recurse -Force   # 日志与同步标记
```

**清除封禁策略**（卸载 agent 后，封禁策略仍留在注册表里）：

```powershell
Remove-Item "HKLM:\SOFTWARE\Policies\Google\Chrome\URLBlocklist" -Recurse -Force
Remove-Item "HKLM:\SOFTWARE\Policies\Microsoft\Edge\URLBlocklist" -Recurse -Force
Remove-Item "HKLM:\SOFTWARE\Policies\Mozilla\Firefox\WebsiteFilter\Block" -Recurse -Force
```

**或者在控制台全局解除封禁**（保留 agent，只是不再封禁）：

控制台 → **封禁策略** → "临时全局关闭"。

**完全停用整套系统：**

1. 停掉控制台，并禁用 RAM 用户的 AK/SK（旧版 agent 直连 OSS，靠禁用 AK/SK 断开）。各台机器的 agent 会失联，但已经生效的本地配置不受影响。
2. 再逐台卸载服务、清除注册表。
