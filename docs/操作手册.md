# AI Env Mgr 操作手册

> 面向：客户 IT 管理员
> 配套：`README.md`（快速上手）、`dist/部署说明.md`（部署步骤）、`架构说明.md`（架构决策）、**`OSS布局.md`（OSS 结构与权限的唯一权威来源）**

---

## 1. 方案概述

在多台阿里云无影共享型云电脑上，让员工使用受控的 AI 工具，同时满足：

| 目标 | 手段 |
|---|---|
| 统一安装 AI 工具 | 模板机装好后制作镜像，所有云电脑从镜像创建 |
| 员工不能用浏览器访问外部 AI 网站 | 浏览器企业策略（HKLM）+ AppLocker |
| 员工不知道 AI 账户密码 | 管理员代为登录，凭据经 OSS 下发 |
| 策略能随时调整 | OSS 作配置中心，agent 定时拉取 |
| 管理员能看到全局状况 | 每台机器上报状态，`admin status` 汇总 |

---

## 2. OSS 配置中心详解

这是整套系统的枢纽。本节把 Bucket、密钥、权限讲清楚。

### 2.1 为什么需要 OSS

多台云电脑文件系统互相隔离，又没有 AD 域可用来集中下发。OSS 承担配置中心的角色：

- 管理员改一次策略 → 所有机器自动拉取
- 管理员代员工登录一次 → 凭据自动分发到对应机器
- 每台机器上报状态 → 管理员一屏看全

### 2.2 创建 Bucket

在阿里云 OSS 控制台创建，关键设置：

| 项 | 取值 | 原因 |
|---|---|---|
| 读写权限 | **私有** | 绝不能设为公共读，凭据会泄露 |
| 存储类型 | 标准存储 | 数据量小、访问频繁 |
| 地域 | **与云电脑同地域** | 走内网免流量费、延迟低 |
| 版本控制 | 建议开启 | 误删配置可恢复 |

Bucket 名建议带用途，例如 `ai-collect-sg`。

### 2.3 目录结构

两个顶级目录，**平级**：

```
ai-collect-sg/
├── admin/               员工名单，agent 完全够不到
│   └── users.json
└── agent_workdir/       agent 的全部活动范围
    ├── policy.json      封禁策略，全局一份，与员工无关
    ├── _bindings/       机器归属（按主机名），agent 只读
    ├── _status/         机器上报（按主机名），agent 只写
    ├── work1/           一个员工一个目录
    │   ├── credentials.zip
    │   └── data_collect/    会话采集，已实现，默认关闭（见 §2.5）
    └── work2/
        └── ...
```

agent 那一侧全部收在 `agent_workdir/` 下，Bucket 可以另作他用互不干扰。目录都是自动生成的，不用手工创建。

> **完整结构、每个对象的格式与字段，以 `OSS布局.md` 为准**，本手册不重复描述。

### 2.4 创建两个 RAM 用户

**必须建两个**，权限差别很大。

#### 管理员用户

用于 `admin.exe`，权限最大，只在管理员的电脑上使用。

1. RAM 控制台 → 用户 → 创建用户
2. 授权：给该用户添加自定义策略

```json
{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["oss:*"],
      "Resource": [
        "acs:oss:*:*:ai-collect-sg",
        "acs:oss:*:*:ai-collect-sg/admin/*",
        "acs:oss:*:*:ai-collect-sg/agent_workdir/*"
      ]
    }
  ]
}
```

把 `ai-collect-sg` 换成你的 Bucket 名。**三行都要**：第一行是 Bucket 本身（列举对象需要），后两行是两个目录里的对象。

3. 记下 **AccessKeyId** 和 **AccessKeySecret**。Secret 只显示一次，务必保存。

#### Agent 用户

用于 `agent.exe`，装进镜像分发到所有云电脑，权限必须收紧。

1. 创建用户
2. 授权：使用交付包里的 `ram-policy-agent.json`

```json
{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["oss:GetObject"],
      "Resource": [
        "acs:oss:*:*:ai-collect-sg/agent_workdir/policy.json",
        "acs:oss:*:*:ai-collect-sg/agent_workdir/_bindings/*",
        "acs:oss:*:*:ai-collect-sg/agent_workdir/*/credentials.zip"
      ]
    },
    {
      "Effect": "Allow",
      "Action": ["oss:PutObject"],
      "Resource": ["acs:oss:*:*:ai-collect-sg/agent_workdir/_status/*"]
    }
  ]
}
```

**这个策略允许什么**：读全局的 `policy.json`、读 `agent_workdir/_bindings/`、读各员工目录下的 `credentials.zip`、写 `agent_workdir/_status/`。

**明确不允许**：写任何策略或凭据、删除任何对象、列举 Bucket、以及碰 `agent_workdir/` 以外的任何东西——**包括 `admin/` 下的员工名单，那个路径压根没出现在授权里**。

> 完整的权限对照表见 `OSS布局.md` §5。

## 3. 命令详解

两个程序:`agent.exe` 装在云电脑上,`admin.exe` 留在管理员自己的机器上。

---

### 3.1 `agent.exe` — 云电脑上的服务

| 命令 | 作用 | 需要管理员身份 |
|---|---|---|
| `setup` | 一条命令装好:复制到位、收紧权限、注册服务、启动、验证 | 是 |
| `sync` | 立即执行一次完整同步 | 是 |
| `status` | 打印本机当前状态,**只读** | 否 |
| `install` / `uninstall` | 单独注册/卸载服务 | 是 |
| `start` / `stop` | 启停服务 | 是 |
| `run` | 服务本体,由服务管理器调用 | — |
| `version` | 版本号 | 否 |

#### `setup` —— 装机只用这一条

```powershell
.\agent.exe setup
```

复制到位、收紧权限、注册并启动服务、跑一次同步验证——**只在模板机上跑一次**,注册信息随镜像走。

#### 日志

`C:\ProgramData\AIEnvMgr\agent.log`,超过 4MB 自动滚动,上一代留在 `agent.log.1`。

```powershell
Get-Content C:\ProgramData\AIEnvMgr\agent.log -Tail 30
Get-Content C:\ProgramData\AIEnvMgr\agent.log -Tail 20 -Wait   # 实时跟
Get-Service AIEnvMgrAgent                                        # 服务在不在跑
```

**远程看日志(不用上机器)**:agent 每个完整同步周期会把日志**尾部(最近约 64KB)**推到 OSS 的 `_logs/{主机名}.log`,管理员在自己机器上就能拉:

```powershell
.\admin.exe log <主机名>          # 打印该机器上传的日志尾部
```

前提:agent 的 RAM 策略要有 `_logs/*` 的 **PutObject** 写权限(`dist/ram-policy-agent.json` 已含)。这只是最近尾部,完整日志仍在机器本地的 `agent.log`。

#### 服务每轮做什么

一次**完整同步**:

1. 拉全局 `policy.json` → 写入浏览器封禁策略。**无条件执行**,不看有没有绑定
2. 用主机名查绑定文件 → 得知服务哪个员工
3. 拉该员工的 `credentials.zip` → 投递到其 profile。ETag 没变就不下载
4. 采集(若已开启)→ 上传员工会话文件到 `data_collect/`
5. 自更新(若 policy 指定了别的版本)→ 下载校验 → 换 exe 重启
6. 按主机名写状态文件上报,并把日志尾部推到 `_logs/`

**触发时机**:服务启动时、休眠唤醒时、距上次完整同步超过间隔时。

**心跳**:两次完整同步之间,循环**每分钟**会轻量地刷新一次"最近露面"时间(不拉策略、不动员工的工具)。所以同步间隔可以设得长(省流量),而 `admin status` 的存活判断仍是分钟级实时——这也是为什么静默几分钟就能判 OFFLINE。

**关机/休眠上报**:agent 收到系统的关机/休眠通知时,会赶在断网前上报一次状态(`stopped`/`suspend`),让 admin 区分"正常离开"和"崩溃"。关机走 **PreShutdown**(系统拆网络前先通知,窗口约 180 秒),大概率成功;真·休眠挂起是尽力而为;硬断电收不到通知,靠时间窗口兜底(见 §5.4)。

注意区分:**休眠唤醒**是事件触发,1 分钟内响应;而管理员在 OSS 上改了东西**没有推送通道**,机器要等到下一个同步周期才发现。急用就跑 `agent.exe sync`。

### 3.2 `admin.exe` — 管理员工具（TUI + CLI）

**这个程序里编译着全 Bucket 读写的密钥**,只应该待在管理员自己的机器上,不要留在云电脑里,更不能进镜像。

两种用法,**底层是同一套逻辑**:

- **TUI 菜单(推荐日常用)**——在终端里**不带任何参数**直接运行 `admin.exe`(或 `admin.exe tui`)就进菜单。进门只需输一次 AK/SK(bucket/endpoint 若已编译进去就只问密钥),之后选数字执行,**凭据不落盘、退出即忘**。
- **CLI 命令(适合脚本/自动化)**——下面每个小节讲的就是这些命令;TUI 每个菜单项调用的就是它们,不存在第二份逻辑。

```
==== AI Env Mgr · <bucket> ====
  1) 机器状态      → status
  2) 员工管理      → user add / disable / enable / list
  3) 代员工登录    → login
  4) 机器管理      → machine bind / unbind / forget / list、log
  5) 封禁策略      → add-site / remove-site / list-sites / enable-block / disable-block / set-interval
  6) 会话采集      → collect enable / disable / stat
  7) 文件传输      → file put / link / list / rm
  8) agent 更新    → agent publish / cancel / status
  q) 退出
```

> 非终端环境(管道 / CI)不会进菜单,而是打印用法——脚本里请直接用下面的 CLI 命令。

下面按功能分组,逐条讲这些命令(也就是 TUI 菜单背后做的事)。

#### 员工管理

| 命令 | 作用 |
|---|---|
| `user add <名> [--codex 邮箱] [--claude 邮箱]` | 登记员工 |
| `user disable <名>` | 停用**并吊销凭据** |
| `user enable <名>` | 重新启用 |
| `user list` | 查看名单 |

```powershell
.\admin.exe user add work1 --codex ai-work1@company.com --claude ai-work1@company.com
```

邮箱**仅作管理员备注**,程序不用它登录任何东西。同名再 add 一次是更新,不会重复(账户名不区分大小写,`Work1` 和 `work1` 是同一个人)。

**`user disable` 是真的吊销,不只是改个标志位**:

它会删除 OSS 上该员工的 `credentials.zip`。agent 读到**明确的 404** 时,会删掉该员工 profile 里的本地凭据文件并结束 AI 工具进程。

这里的设计要点是**区分"确实没了"和"够不着"**——只有服务端真的返回 404 才算吊销,网络超时之类一律不动。否则一次网络抖动就会把所有机器的登录态一起抹掉。

> `disable` 之后 `enable` 不会把凭据找回来。要恢复得重新跑一次 `login`。这是吊销该有的样子。

> **别忘了 OSS 之外的一步**:本方案能删掉机器上的登录态,删不掉 AI 账户本身。真正的离职流程还应该去 OpenAI / Anthropic 后台改密码或吊销该账户的会话。

#### `login` —— 代员工登录

```powershell
.\admin.exe login --user work1 --tool all      # 或 --tool codex / --tool claude
```

**员工全程不知道账户密码**,这是整套方案的核心。OAuth 结果在内存里打包直接传 OSS,**不落管理员本地磁盘**。

两个工具都是**粘贴式**的,但粘的东西不一样:

**Codex** —— 登录后浏览器会跳 `http://localhost:1455/auth/callback?code=...&state=...`,**显示连接失败是正常的**,地址栏里带着 code。复制**整个地址栏 URL**粘回来。

> 为什么不自动接收:1455 是 Codex CLI 自己占用的端口,而且管理员的浏览器通常和运行 admin 的机器不是同一台。粘贴对两种情况都成立。

**Claude** —— 登录后页面直接显示一串授权码,复制那串码粘回来。

粘贴内容宽容处理:完整 URL 或裸 code 都认。如果 URL 里的 `state` 和本次登录对不上(比如粘了上一次没做完的回调),会直接拒绝让你重来。

`login` 产出四个文件里的三个:

| 文件 | 落到员工 profile |
|---|---|
| `codex/auth.json` | `.codex\auth.json` |
| `claude/.credentials.json` | `.claude\.credentials.json` |
| `claude.json` | `.claude.json` |

**`claude.json` 不能少**:Claude Code 的登录身份记在这里,只给 `.credentials.json` 的话令牌到位了、员工打开还是会被要求登录。agent 投递它时是**合并写入**——那个文件里还有员工自己的项目历史和 MCP 配置,不能覆盖掉。

只登录了其中一个工具时,zip 里只有那部分,agent 投递时会与已有文件合并,不会把另一个工具的凭据抹掉。

#### 机器管理

| 命令 | 作用 |
|---|---|
| `machine bind <主机名> --user <名> [--note 备注]` | 把机器分配给员工 |
| `machine unbind <主机名>` | 解除分配（机器仍在 `status` 里,只是变未绑定） |
| `machine forget <主机名>` | **彻底删除**已下线的机器（绑定 + 状态上报一起删,从 `status` 消失） |
| `machine list` | 查看**已绑定**的机器名册,含存活状态 |

`machine list` 输出(比旧版多一列 **STATE**,和 `admin.exe status` 同一套存活判定):

```
MACHINE          USER     BOUND AT              NOTE       STATE
2541uggezhgkon0  weipeng  2026-08-11T08:12:03Z  研发-张三   OK
DESKTOP-B        work2    2026-08-10T02:00:00Z  -          OFFLINE
```

- 只列**已绑定**的机器(它是"分配名册",未绑定但已上报的机器去 `status` 看)。
- STATE 取值与含义同 `status` 的 STATE 列(见下方和 §5.4):`OK` / `STOPPED` / `SLEEPING` / `OFFLINE` / `STALE` / `NO REPORT` 等。员工关机上报后这里也能直接看到 `STOPPED`,不用切到 `status`。

> `unbind` 和 `forget` 的区别:`unbind` 只解绑,机器还在 `admin.exe status` 里(显示 UNBOUND);`forget` 把它的 `_status/` 上报也删了,机器**从列表里消失**。机器还开着的话 `forget` 后它下个 sync 又会冒出来——**forget 是给真正下线的机器用的**。

```powershell
.\admin.exe machine bind iZt4n2up5vmbxv0bvvnp1oZ --user work1 --note "研发部-张三"
```

**员工必须先在名单里**,否则报 `user not found in roster`。

主机名不用你事先知道——机器开机后 agent 会自己上报,在 `admin.exe status` 里就能看到,显示为 `UNBOUND`。

换人直接重新 `bind` 覆盖即可。

#### 文件传输

| 命令 | 作用 |
|---|---|
| `file put <路径> [--as <名字>] [--expires <小时>]` | 上传并给出下载链接 |
| `file link <名字> [--expires <小时>]` | 重新签发链接 |
| `file list` | 查看已暂存 |
| `file rm <名字>` | 删除 |

```powershell
.\admin.exe file put .\agent.exe --expires 24
```

它会直接打印可粘贴的 PowerShell 命令:

```powershell
Invoke-WebRequest -Uri 'https://...' -OutFile 'agent.exe'
```

**云电脑上不需要任何密钥**——链接自带授权(预签名 URL)。这是把 agent.exe 弄上云电脑最省事的方式,比控制台文件传输快。

默认 6 小时有效,`--expires` 可调,上限 7 天。**链接是 bearer token,谁拿到谁能下载**,而 agent.exe 里有密钥——所以别把链接贴到聊天记录里长期留着。

文件存在 `admin/files/`,**不在 `agent_workdir/` 下**。agent 的授权里没有这条路径,所以员工机器上的密钥下载不了这些文件,只有管理员签出来的链接能。

#### 封禁策略

| 命令 | 作用 |
|---|---|
| `add-site <域名>...` | 增加封禁网站 |
| `remove-site <域名>...` | 移除封禁网站 |
| `list-sites` | 查看当前清单 |
| `enable-block` / `disable-block` | 封禁总开关 |
| `set-interval <分钟>` | 调整同步频率 |

```powershell
.\admin.exe add-site gemini.google.com x.ai      # 可以一次多个
.\admin.exe remove-site x.ai
```

策略是**全局一份**,与员工名单无关。改一次所有机器都生效,包括**还没分配给任何人的机器**。

域名会自动去重、排序、转小写,`Foo.com` 和 ` foo.com ` 算同一个。

**`disable-block` 是临时开放用的**:它会让 agent **删除**注册表里的封禁键(而不是写一个空清单)——键不存在是三个浏览器都明确当作"不管控"的唯一状态。用完记得 `enable-block` 恢复。

`set-interval` 限制在 **1–1440 分钟**,超出自动钳到边界。防止误设成 0 让 agent 疯狂轮询,或设成几天导致机器实际失联。

> 新间隔要机器**先同步一次**才知道。想立刻切换,去那台机器上跑一次 `agent.exe sync`。
>
> 调试时用 1 分钟很方便,**正式上线建议调回 5–10 分钟**。

#### `status` —— 全局视图

```powershell
.\admin.exe status
```

```
MACHINE          USER     LOCAL USERS      AGENT    LAST SYNC  POLICY    BLOCK  APPLOCKER  STATE
iZt4n2up5vmbxv0bvvnp1oZ  work1    Administrator,work1  1.2.3  1m ago     C9AC50A2  on     Enforce    OK
DESKTOP-B        work2    Administrator    1.2.3    5m ago     C9AC50A2  on     Enforce    USER MISSING
DESKTOP-C        -        Administrator    1.2.3    1m ago     C9AC50A2  on     Audit      UNBOUND
DESKTOP-D        work4    -                -        never      -         -      -          NO REPORT
```

各列含义:

- **USER / LOCAL USERS** —— 绑定的员工 / 机器上实际存在的账户 profile。两者对不上就会在下方给出提示
- **AGENT** —— 该机器上 agent 的版本(agent 自己上报的)。**各机器之间比对**,升级/自更新后能看谁还停在旧版
- **LAST SYNC** —— 机器最后一次上报的时间。活着的 agent **每分钟**都会刷新一次(心跳),所以这列是"agent 是否活着"的实时证据
- **POLICY** —— 已应用策略的 ETag 前 8 位。**各机器之间比对**,不一致说明有机器还没拉到最新
- **BLOCK / APPLOCKER** —— 该机器实际生效的封禁开关和 AppLocker 模式
- **STATE** —— 一词概括这台机器要不要你处理,取值:

| STATE | 含义 | 要处理? |
|---|---|---|
| `OK` | 10 分钟内正常上报 | 否 |
| `SLEEPING` | agent 报了"即将休眠" | 否(预期) |
| `STOPPED` | agent 报了"停止/关机" | 否(预期) |
| `OFFLINE` | 静默几分钟~3 天,多半下班/休眠/关机 | 否(预期) |
| `STALE` | 静默 > 3 天,或说要睡却没醒 | **是** |
| `NO REPORT` | 已绑定但从未上报 | **是** |
| `UNBOUND` | 上报了但还没分配员工 | 是(绑定即可) |
| `DISABLED USER` | 绑定的员工已停用 | **是** |
| `USER MISSING` | 绑定的员工在机器上没有 profile | **是** |
| `EXTRA USERS` | 机器上有计划外的账户 | 看情况 |

表格下方会列出每台机器的具体异常和处理建议;末行汇总"N 台需要关注"(上表标"是"的才计入)。存活状态(OK/OFFLINE/SLEEPING/STOPPED/STALE)的详细原理见 §5.4。

#### `log` —— 远程看某台机器的日志

```powershell
.\admin.exe log <主机名>
```

打印这台机器 agent 上传到 OSS 的**日志尾部**(最近约 64KB)。不用上机器,在管理端就能看。

- agent 每个**完整同步周期**推一次 `_logs/{主机名}.log`,所以看到的是"最近尾部",不是实时流;完整日志仍在机器本地 `C:\ProgramData\AIEnvMgr\agent.log`。
- 报 `no log for X yet`:那台机器还没跑带日志上传的新 agent,或 agent 的 RAM 策略缺 `_logs/*` 的 **PutObject** 写权限。

#### 会话采集(默认关闭)

| 命令 | 作用 |
|---|---|
| `collect enable [--since <YYYY-MM-DD>] [--quiet <秒>]` | 打开采集 |
| `collect disable` | 关闭采集 |
| `collect stat` | 按员工统计已上传的会话文件数 |

```powershell
.\admin.exe collect enable --since 2026-01-01 --quiet 60
.\admin.exe collect stat
```

打开后,agent 会把员工的 AI 会话原始文件上传到 OSS 的 `data_collect/{员工}/` 下,供后续归集/挖掘。要点:

- **默认关闭**,而且 agent 对 `data_collect` 的**只写**权限是在你打开这个功能时才补的(见 §2.5)。
- `--since` 只采该日期(UTC)之后的会话,留空采全部历史;`--quiet` 是去抖秒数(文件停止变动多少秒后才上传),留空默认 60。
- `collect stat` 读 `data_collect/` 下各员工目录的对象数,用来核对"谁在产出、传了多少"。

#### agent 自更新

| 命令 | 作用 |
|---|---|
| `agent publish <本地路径>\|--url <地址> --version <版本> [--token <PAT>]` | 发布新 agent 给全体,让它们下轮自更新 |
| `agent cancel` | 清除更新目标(**急停开关**) |
| `agent status` | 查看当前的更新目标版本 |

```powershell
# 本地文件发布：
.\admin.exe agent publish .\agent-1.2.4.exe --version 1.2.4
# 或直接从 GitHub release URL 下载再推(私有仓库要带 token,也可用 GITHUB_TOKEN 环境变量)：
.\admin.exe agent publish --url https://github.com/TEENet-io/ai-env-mgr/releases/download/v1.2.4/agent.exe --version 1.2.4 --token <PAT>
```

发布后:agent 每轮比对版本 → 下载 `_agent/agent.exe` → **校验 SHA-256** → 换文件(旧的留 `agent.exe.old`)→ 重启服务。

- **policy 是全局的:一发布就是全体一起更新,没有灰度、没有自动回滚**。务必先在**一台机器**上验证新 exe 能跑(见 §4.7)。
- 校验不过不换;同一目标只试一次,不会反复重启;出问题用 `agent cancel` 急停。
- 需要 agent 的 RAM 策略有 `_agent/*` 的 **GetObject** 读权限(`dist/ram-policy-agent.json` 已含)。
- `--url` 形式下,admin 自己把二进制下载下来再推到 OSS;404/401 且没带 token 时会提示可能是私有 release。

|---|---|
| `tui` | 进入菜单式界面(不带参数运行 `admin.exe` 也会进,见本节开头) |
| `version` | 打印版本号 |

## 4. 标准流程

### 4.1 首次部署

```powershell
# 1. 建 OSS Bucket，创建两个 RAM 用户（见 §2）

# 2. 填密钥、编译两个 exe（填法见 `dist/部署说明.md`）
cd go && make all

# 3. 初始化封禁策略 —— 这步不能跳过
#    新 Bucket 没有 policy.json，agent 拉不到就不写注册表，机器不设防
.\admin.exe enable-block
.\admin.exe list-sites

# 4. 把 agent.exe 传到模板机
.\admin.exe file put .\agent.exe --expires 24
#    在模板机上执行它打印出来的 Invoke-WebRequest

# 5. 模板机上（管理员身份）
Unblock-File .\agent.exe          # 解除下载文件的 Internet 标记
.\scripts\01-Install-AITools.ps1   # 装 AI 工具
.\scripts\02-Manage-AIAccess.ps1 -Init   # 配 AppLocker（先审计模式）
.\agent.exe setup                 # 装服务并验证

# 6. 逐条核对 setup 的输出，浏览器实测 chatgpt.com 打不开
# 7. AppLocker 切强制模式
# 8. 制作自定义镜像
```

**镜像做出去之后再改就是逐台的事了**，第 6 步别省。

### 4.2 新员工入职

入职从**无影控制台**开始：先给员工开一台云电脑、建好 Windows 账户，再回到 `admin` 登记、代登录、绑定。

#### 第 1 步：在无影控制台创建云电脑

用**公司自定义镜像**（§4.1 第 8 步做好的那个）给新员工开一台云电脑。镜像里 agent 已随开机自启，浏览器封禁与 AppLocker 也都就位，开机即生效。

> **机器什么时候出现在 `admin status`**：agent 是 **SYSTEM 服务、开机自启**，**不必等任何人登录**——云电脑一开机、agent 完成首次 sync，这台就出现在 `admin status`（第 6 步据此找它绑定）。登录只影响 `work1` 在不在 `LocalUsers` 里，即 `USER MISSING` → `OK`。
>
> 若你们的云电脑是**连接时才开机**（会话式/按需），它会在**首次被拉起（通常即员工首次连接）之后**才出现在 status；想在员工到岗前就绑定，先自己连一次把这台开起来即可。

#### 第 2 步：创建 Windows 标准用户

在这台云电脑上给员工建一个**标准用户**（非管理员），例如 `work1`。

> ⚠️ 一定是**标准用户**。标准用户无权删除 HKLM 里的浏览器封禁策略——这正是"员工绕不过封禁"的前提；管理员则能自行卸掉封禁。

#### 第 3 步：员工首次登录（创建 profile）

Windows 用户**首次登录才会生成 profile**，凭据得有这个目录才能投递。让员工（或你代为）用 `work1` 登录一次。

> 若这一步晚于绑定也没关系：员工首登后，**下一个同步周期**凭据就会投递到位；在此之前 `admin status` 会把这台标记为 `USER MISSING`。

#### 第 4 步：登记员工（admin）

在管理员电脑上裸跑 `admin.exe` 进 TUI 菜单，之后：

```
菜单 2 员工管理 → 2 新增
  员工名: work1
  codex 邮箱(备注,可空): ai-work1@company.com
  claude 邮箱(备注,可空): ai-work1@company.com
```

邮箱仅作管理员备注（见 §3.2 员工管理）。

#### 第 5 步：代员工登录（admin）

```
菜单 3 代员工登录
  员工名: work1
  工具 codex/claude/all [all]: all
```

浏览器完成授权，OAuth 结果直接进 OSS、**不落管理员本地磁盘**（粘贴方式见 §3.2 `login`）。

#### 第 6 步：找到这台机器并绑定

机器开机后 agent 会自动上报，在机器状态里显示为 `UNBOUND`：

```
菜单 1 机器状态                     # 看哪台在等分配（UNBOUND）

菜单 4 机器管理 → 2 绑定
  主机名: <主机名>
  员工名: work1
  备注(可空): 研发部-张三
```

主机名不用事先知道，从机器状态里认——表格下方会列出该机器上有哪些本地账户，据此判断是哪台。

#### 第 7 步：等一个同步周期（或手动催一次）

绑定后 agent 会在**下一个同步周期**（默认 30 分钟，改频率用 `admin set-interval`，见 §3.2 封禁策略）拉配置、把 `work1` 的凭据投递到位。要立刻生效，在那台机器上跑一次 `agent.exe sync`。

完成后员工打开 Codex / Claude Code 即为已登录状态，浏览器访问 AI 网站被封。

### 4.3 凭据过期

```powershell
admin.exe login --user work1 --tool all
```

重新授权一次，各机器下个同步周期自动更新。

**员工那边会有一次打断**：新凭据投递时 agent 会结束正在运行的 Codex / Claude 进程（这两个工具把令牌读在内存里，不重启不会重新加载）。所以尽量别在员工正干活时做。

### 4.4 员工离职

```powershell
admin.exe user disable work1              # 停用并吊销凭据
admin.exe machine unbind <主机名>          # 解除机器绑定（机器转给别人用）
# 若这台机器也一并下线（不再用）：
admin.exe machine forget <主机名>          # 从 status 里彻底删掉
```

`user disable` 会**删除 OSS 上该员工的 `credentials.zip`**。这才是真正起作用的一步：agent 读不到凭据对象（明确的 404）时，会把该员工 profile 里的本地凭据文件一并删掉，并结束正在运行的 AI 工具进程。

生效时间同样是**下一个同步周期**。要立刻吊销就去那台机器上跑 `agent.exe sync`。

> **别忘了 OSS 之外的一步**：本方案能删掉机器上的登录态，但删不掉 AI 账户本身。真正的离职流程还应该在 OpenAI / Anthropic 后台改密码或吊销该账户的会话——否则员工在自己设备上仍是登录状态。

未解绑的机器会在 `admin.exe status` 里显示 **DISABLED USER**，提醒你这台机器还挂在一个已停用的人名下，需要重新分配或下线。

### 4.5 管理员临时需要访问 AI 网站

```powershell
admin.exe disable-block     # 全局解封
# ...使用（需重启浏览器）...
admin.exe enable-block      # 立即恢复
```

### 4.6 调整封禁清单

```powershell
admin.exe add-site gemini.google.com
admin.exe remove-site x.ai
admin.exe list-sites
```

### 4.7 升级 agent

```powershell
# 1. 改完代码重新编译
cd go && make agent

# 2. 传上去
.\admin.exe file put ..\dist\agent.exe --expires 24

# 3. 在每台机器上下载并重跑 setup（会自动停服务、换文件、重启）
Invoke-WebRequest -Uri '<链接>' -OutFile 'agent.exe'
Unblock-File .\agent.exe
.\agent.exe setup
```

机器多的话建议直接重做镜像、重开机器，比逐台替换省事。

改动会写入所有启用员工的目录，各机器下次同步生效。

#### 自动升级（`admin agent`）

不想逐台重跑 setup，可以让 agent 自更新：发布一次，所有机器下个同步周期自己换。

```powershell
# 1. 编新版（版本号会编进二进制，agent 靠它判断要不要更新）
cd go && make agent VERSION=1.2.4

# 2. 【重要】先在一台机器上手动验证这个新 agent.exe 能跑（file put 到一台、换上、看 status 正常）
#    policy 是全局的：一发布就是全体一起更新，没有灰度，也没有自动回滚。

# 3. 发布给全体 —— 本地文件:
.\admin.exe agent publish ..\dist\agent.exe --version 1.2.4
#    或直接从 URL 下载再推(省去手动下载)。私有 GitHub release 要带 token:
.\admin.exe agent publish --url https://github.com/TEENet-io/ai-env-mgr/releases/download/v1.2.4/agent.exe --version 1.2.4 --token <GitHub PAT>
#    （token 也可放 GITHUB_TOKEN 环境变量,免得进命令历史;PAT 需 repo 权限）
# 4. 看进度：admin status 的 AGENT 列一台台翻成新版本
.\admin.exe agent status      # 当前目标版本
.\admin.exe agent cancel      # 急停：清掉目标，没更新的机器停手
```

**agent 侧**：每周期比对 policy 里的目标版本与自身版本，不同就下载 `_agent/agent.exe`、**校验 SHA-256**、换文件（旧的留成 `agent.exe.old`）、重启服务。校验不过不换，并在 status 报错；同一目标只试一次，坏包不会反复重启。

**前置**：agent 的 RAM 策略要有 `_agent/*` 的 **GetObject** 读权限（`dist/ram-policy-agent.json` 已含）。结构见 `OSS布局.md` §7。

**风险（务必知道）**：

- **全体一起更新**，无灰度 → 所以第 2 步"先在一台上验证"不能省。
- **无自动回滚**：新版起不来就得人工上机器（控制台/RDP），把 `C:\Program Files\AIEnvMgr\agent.exe.old` 换回 `agent.exe` 再启动服务。
- 只有**已经带自更新功能的 agent** 才会响应发布——第一版带此功能的 agent 仍要手动装（上面的 setup 方式）一次作为起点。

## 5. 故障排查

### 5.1 机器在 status 里显示 NO REPORT

已绑定但从未上报。按顺序查：

```powershell
# 1. 服务在跑吗
Get-Service AIEnvMgrAgent

# 2. 手动同步看报错
.\agent.exe sync

# 3. 看日志
Get-Content C:\ProgramData\AIEnvMgr\agent.log -Tail 30
```

常见原因：
- **打进镜像的 agent.exe 没填配置** —— `agent.exe status` 第一行若是 `config=config file`，说明这个 exe 是空的，填法见 `dist/部署说明.md`
- endpoint 填错（内网/公网搞反，或地域不对）
- AK/SK 错误或已被禁用
- 云电脑无法访问 OSS（安全组或网络策略拦截）

### 5.2 显示 UNBOUND

机器上报了但还没分配。正常现象，绑定即可：

```powershell
admin.exe machine bind <主机名> --user <员工名>
```

表格下方会列出该机器上有哪些账户，据此判断该绑给谁。

### 5.3 显示 USER MISSING

绑定的员工在该机器上没有 profile。两种原因：

- **绑错名字** —— `machine list` 看绑的是谁，`status` 看机器上实际有谁，重新绑定
- **该用户从未登录过** —— Windows 用户首次登录才会创建 profile。让员工登录一次即可

### 5.4 存活状态:OFFLINE / SLEEPING / STOPPED / STALE

活着的 agent 大约每分钟刷新一次上报(心跳),所以"多久没上报"是很强的信号。但云电脑会在下班、周末休眠或关机,这种静默是**正常**的。为了不把每天休眠的机器都报成故障,status 把静默分成了几档,并结合 agent 自己临走前留下的"遗言":

| 状态 | 判据 | 要不要管 |
|---|---|---|
| **OK** | **10 分钟**内有上报 | 否 |
| **SLEEPING** | agent 在休眠前上报了"我要睡了" | 否,预期内 |
| **STOPPED** | agent 上报了"我被停止/关机了"(干净退出) | 否,已知状态 |
| **OFFLINE** | 静默 **10 分钟 ~ 3 天**——多半是下班/休眠/关机 | 否,预期内 |
| **STALE** | 静默**超过 3 天**,或者说了"要睡"却再没醒 | **是,要排查** |

两条线的由来:

- **10 分钟(OK↔OFFLINE)**:活着的 agent **每分钟**都会心跳刷新一次上报,所以静默 10 分钟 = 10 次心跳都没了 = 铁定停了/关了。这条线远比同步间隔短,**停机/关机几分钟内就会显示 OFFLINE**,不依赖那条脆弱的"遗言"标记(硬断电根本留不下标记)。10 分钟也够宽,能吸收一次网络抖动。
- **3 天(OFFLINE↔STALE)**:休眠/关机的机器一两天内会醒;真挂了的 agent 不会自己醒。所以超过 3 天才从"预期内的离线"升级成"要排查的 STALE"。

原理:**休眠/关机都有"临终遗言",崩溃没有**——有遗言就即时显示 SLEEPING/STOPPED,没有(硬断电、来不及发)就靠上面两条时间线兜底。

- 看到 **STALE** 且机器确实该在用:按 §5.1 排查(服务是否在跑、手动 `agent.exe sync`、看日志、必要时 `admin log <主机名>` 远程看它上传的日志尾巴)。
- **SLEEPING / STOPPED / OFFLINE 不计入"需要关注"的统计**,底部汇总的 "N 台需要关注" 不会因为机器休眠而虚高。
- 表格下方会给出具体一行,比如"某机器在 3h 前上报了要休眠——这是预期,不是故障"。

> 注意:SLEEPING/STOPPED 这两个正向标记需要机器上跑着带该功能的新 agent(v1.2.3+)。老 agent 只会表现为普通静默,靠 OFFLINE/STALE 分级兜底。各场景可靠性:
> - **停服务**(`agent.exe stop` / `sc stop`,系统继续运行)→ 网络在,**可靠**报 `stopped`;
> - **关机 / 重启**→ agent 注册了 **PreShutdown**,在系统拆网络**之前**就收到通知(窗口约 180 秒),**大概率**报出 `stopped`(v1.2.2 只用普通 SHUTDOWN,收到太晚,常常来不及,v1.2.3 修正);
> - **真·休眠/挂起**(APM suspend)→ 挂起瞬间机器就冻结,是**尽力而为**,发得出去最好,发不出去靠 OFFLINE 兜底;
> - **强制断电 / 云控制台硬关机**→ 操作系统收不到任何通知,agent 无从上报,等同崩溃 → 只能靠 OFFLINE/STALE 分级。

### 5.5 显示 DISABLED USER

机器还绑定着一个已停用的员工。凭据已经吊销，但机器本身还在运行、还在上报，没人负责。

```powershell
admin.exe machine bind <主机名> --user <新员工>   # 转给别人
admin.exe machine unbind <主机名>                # 或者先解绑，等待下线
admin.exe machine forget <主机名>                # 机器已彻底下线：从列表里删掉（绑定+状态）
```

### 5.6 显示 EXTRA USERS

机器上有绑定员工和 Administrator 之外的账户。核查是否有不该存在的账号——这可能意味着有人在机器上建了额外账户绕过管控。

### 5.7 封禁不生效

```powershell
# 确认策略已下发到本机
.\agent.exe status          # 看 block 和 domains

# 确认注册表已写入
Get-ItemProperty "HKLM:\SOFTWARE\Policies\Google\Chrome\URLBlocklist"
```

- **注册表有值但浏览器仍能访问** → 浏览器没重启。重启浏览器，或在 `chrome://policy` 点"重新加载政策"
- **注册表没值** → agent 没同步成功，按 §5.1 查
- **换了个浏览器就能访问** → 只覆盖 Chrome/Edge/Firefox，其他浏览器要靠 AppLocker 拦

### 5.8 绿色版浏览器能绕过

绿色版不读系统策略，必须靠 AppLocker 拦截运行。

```powershell
.\agent.exe status          # 看 applocker 字段（只读，随便跑）
```

- 显示 **Audit** → 仍是审计模式，只记录不拦截。需在模板机切到强制模式后重做镜像
- 显示 **None** → AppLocker 未启用。检查 Windows 版本（需企业版/教育版/Server）和 AppIDSvc 服务

### 5.9 员工打开 AI 工具仍要求登录

```powershell
.\agent.exe status          # 只读，看 "AI credentials in place for:" 那行
.\agent.exe sync            # 要看同步过程的错误就跑这条
```

按现象分：

- **`status` 里该员工不在 "credentials in place" 列表里** → 文件根本没落地。跑 `sync` 看报错，常见是 OSS 里没有该员工的 `credentials.zip`（管理员还没执行 `login`），错误会写 `no credentials published for "xxx" yet`
- **文件在，但打开工具仍要求登录** → 分两种：
  - **Claude** → 多半是 `.claude.json` 的问题，它记着登录身份，只有 `.credentials.json` 是不够的。确认 `C:\Users\<员工>\.claude.json` 存在且含 `hasCompletedOnboarding` 与 `oauthAccount`
  - **两个都要求登录** → 令牌过期了，管理员重新 `login`
- **`sync` 报 `credentials written but not readable by <员工>`** → ACL 授权失败，文件写了但员工读不到。看具体错误，通常是 profile 权限异常

## 6. 安全边界

**能做到**：

- 阻止员工用受管浏览器访问外部 AI 网站
- 阻止运行绿色版浏览器等未授权程序（AppLocker 强制模式下）
- 员工不知道 AI 账户密码
- 员工（标准用户）无法自行解除管控
- Agent 密钥泄露也读不到员工名单、改不了策略、碰不到 `agent_workdir/` 以外的东西
- **还没分配给任何人的机器同样被封禁** —— 策略是全局的，不依赖绑定
- 离职后能远程吊销：删掉 OSS 上的凭据，机器下次同步就清掉本地登录态

**做不到**：

- 阻止员工用手机拍摄屏幕
- 阻止员工用个人设备访问 AI
- 阻止拥有本地管理员权限的人解除管控
- 阻止有管理员权限者读取 agent 密钥（密钥是明文编译在 exe 里的，`strings` 就能翻出来）
- **删掉 AI 账户本身** —— 只能删机器上的登录态，账户还得去 OpenAI / Anthropic 后台处理

**必要前提**：

- 员工账户必须是**标准用户**
- 严格控制本地管理员权限的授予
- OSS Bucket 必须是**私有**

## 7. 卸载与复原

**单台机器移除 agent**：

```powershell
cd "C:\Program Files\AIEnvMgr"
.\agent.exe stop
.\agent.exe uninstall
Remove-Item "C:\Program Files\AIEnvMgr" -Recurse -Force
Remove-Item "C:\ProgramData\AIEnvMgr" -Recurse -Force   # 日志与同步标记
```

**清除封禁策略**（agent 卸载后策略仍在）：

```powershell
Remove-Item "HKLM:\SOFTWARE\Policies\Google\Chrome\URLBlocklist" -Recurse -Force
Remove-Item "HKLM:\SOFTWARE\Policies\Microsoft\Edge\URLBlocklist" -Recurse -Force
Remove-Item "HKLM:\SOFTWARE\Policies\Mozilla\Firefox\WebsiteFilter\Block" -Recurse -Force
```

**或用 admin 全局解封**（保留 agent，只是不封了）：

```powershell
admin.exe disable-block
```

**完全停用整套系统**：禁用两个 RAM 用户的 AK/SK，各机器 agent 会失联但不影响已生效的本地配置；再逐台卸载服务、清除注册表。
