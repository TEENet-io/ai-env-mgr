# 超级管理员事务 SOP

版本：2026-10-19
管哪些东西：数据库模式下的管理后台 `windows-control`，以及它连接的 Windows Agent、LiteLLM 网关、OSS 和阿里云无影云电脑。
怎么组织：按“一次业务变更”来写，不按后台菜单来写。

## 先认识几个词

| 词 | 意思 |
|---|---|
| 管理后台（Admin） | 管理员使用的网页，项目名 `windows-control`，服务器上的服务名是 `ai-env-mgr-console`。 |
| 数据库模式 | `windows-control` 当前的部署方式。旧的 OSS 直连方式见第 4 节最后一条。 |
| Agent | 装在每台云电脑上的管理程序。它接收后台下发的配置、安装软件、上报机器状态。 |
| 网关（LiteLLM） | 员工调用 AI 模型时经过的中转服务，用的软件叫 LiteLLM。员工的令牌在这里校验。 |
| 令牌 | 访问凭证，相当于一把钥匙。本文有两种：员工调用模型用的“网关令牌”，机器连后台用的“设备令牌”。 |
| 渠道 | 模型背后实际提供服务的供应商线路，例如 AWS、Google、Azure。同一个模型可能挂在几个渠道上。 |
| 无影 | 阿里云的云电脑产品。员工用的云电脑实例和云账号在这里。 |
| OSS | 阿里云的云存储，存放安装包、采集数据和数据库备份。 |
| SLS | 阿里云的日志服务。 |
| AppLocker | Windows 自带的程序白名单。不在名单里的程序不能运行。 |
| CI | 自动构建安装包并上传的流程。 |
| SHA-256 | 安装包的“指纹”。指纹一致，说明拿到的就是构建出来的那个包。 |
| 关户 | 在后台停用员工账号，同时作废其网关令牌、撤回配置。 |
| 留痕 | 把操作和结果记录下来，事后能查。 |
| 补偿步骤 | 操作做到一半失败时，手动补做或撤销的步骤。 |
| AK/SK | 云平台的访问密钥对。 |

## 1. 角色和事务边界

### 谁能做什么

系统里没有叫 `superadmin` 的独立角色。本文说的“超级管理员”，指后台的 `admin` 角色。其他角色：

- `operator`：做日常操作，包括开户、绑定、预算、给机器指定版本。
- `viewer` / `security`：只能查看。

有些步骤要操作服务器操作系统、数据库、云平台、GitHub 或 LiteLLM，需要这些平台各自的权限。**有后台 `admin` 身份，不代表自动有这些权限。**

### 一次事务什么时候算完成

一次事务从“明确对象和影响范围”开始，到“**执行结果已经验证并记录下来**”结束。以下情况都不算业务完成：

- 点了按钮；
- 任务显示“已提交”；
- Agent 报告“同步成功”。

一次操作常常同时涉及后台、网关、OSS 和云电脑。这些系统不会一起成功、一起失败。中间某一步失败时，系统不会自动回滚，要按各节的补偿步骤继续处理。

### 每次要记录什么

每次事务至少记录：

- 事务编号、发起原因；
- 对象和影响范围；
- 申请人、执行人；
- 变更前的状态、批准依据；
- 操作时间；
- 后台任务 ID 或发布版本；
- 验证结果；
- 没做完的事和后续负责人。

高风险变更建议找第二个人复核。但系统**没有内置双人审批**，不要把这条建议写成系统已经强制执行的规则。

记录里不要贴密码、AK/SK、网关令牌或会话原文。

### 事务清单

| 编号 | 事务 | 什么时候需要做 | 怎样算完成 |
|---|---|---|---|
| S01 | 授予或收回后台管理员权限 | 人员入职、转岗、离职、账号有风险 | 角色和登录状态正确，交接或撤权有记录 |
| S02 | 员工紧急撤权与到期清理 | 离职、令牌泄露、违规使用 | 网关令牌失效；云账号和实例按期限处理 |
| S03 | 设备注册、重装与注销 | 新镜像、令牌丢失、设备退役 | 设备身份唯一，绑定和状态正确 |
| S04 | 修改全局浏览器/AppLocker 策略 | 安全策略变更、误封、应急测试 | 抽查的机器实际生效；临时放宽已恢复 |
| S05 | 暂停/恢复模型渠道并下发 | 云供应商故障、欠费、模型下架 | 网关权限和员工电脑上的模型列表符合预期 |
| S06 | 发布或回滚 Agent/Codex | 新版本、安全修复、故障回滚 | 目标机器回报了目标版本，异常机器有处理 |
| S07 | 审核、安装或升级其他软件 | 员工申请装机器级软件或更新版本 | 安装包、目标版本、安装结果和实际能否启动都通过 |
| S08 | 采集开关与留存清理 | 合规确认、期限到期 | 采集范围经过批准，删除有回执 |
| S09 | 配置告警、通知和令牌轮换 | 值班和安全策略变更 | 测试通知成功，自动任务状态正常 |
| S10 | 升级后台/数据库 | 后台发布新版本、数据库迁移 | 健康检查通过，关键业务能正常用 |
| S11 | 备份、恢复与密钥轮换 | 定期演练、故障、密钥有风险 | 备份能恢复；新密钥可用，旧密钥已安全撤销 |
| S12 | 处置全局故障或安全事件 | 大面积离线、误发布、凭证泄露 | 先止损，再恢复，最后复盘 |

## 2. 各事务操作

### S01｜授予或收回后台管理员权限

**先检查：**

- 确认申请人的职责，只给够用的最小角色。`admin` 能改全局策略、发布目标、管理其他管理员，不要当普通查看账号发。
- 确认至少还有一名能登录的 `admin`。

**步骤：**

1. 到 **设置 → 管理员**，按申请创建 `admin`、`operator`、`security` 或 `viewer` 账号。初始密码只显示一次。通过安全的渠道交给本人，不要放进工单或群聊。
2. 让本人第一次登录时绑定验证器、保存恢复码，再到 **我的账号** 改密码。然后在列表里核对“已绑定”、最近登录时间和角色。
3. 收回权限时，在同一页停用对应账号。停用会让该账号已登录的会话失效。核对状态显示为“停用”。不能停用自己正在登录的账号，要由另一名 `admin` 来操作。

**怎样算完成：** 新账号由本人成功登录一次；被收回权限的账号不能再登录。

**出了问题：**

- 停用错了，可以由其他 `admin` 重新启用。
- 验证器丢了，或只剩最后一名管理员能登录：不要借用别人的账号绕过去，按认证恢复流程处理，并做记录。

### S02｜员工紧急撤权与到期清理

**先检查：**

- 核对员工的 Windows 用户名、邮箱、绑定的机器，以及离职或事件的生效时间。
- 先分清两件事：“立即禁止调用模型”和“7 天后清理云资源”。
- 普通关户 `operator` 就能做。超级管理员负责涉及多个系统的处理和例外情况。

**步骤：**

1. 在 **员工账号 → 员工详情** 点“关户”。核对网关令牌已吊销、撤回配置的任务已生成。**先不要解绑机器**：保留绑定，Agent 才知道要清理哪个 Windows 用户的凭证。
2. 在 LiteLLM 或调用方实际验证旧令牌已经调不通。再到 **任务中心、审计、机器日志** 核对撤权已经送到机器上。机器离线、本地文件还没清掉时，网关这边的吊销也应该已经先挡住了调用。
3. 云资源管理员在阿里云停用云账号、关闭实例。到了客户确认的期限（当前业务流程是离职满 7 天），删除云账号、释放实例和数据，再到机器页注销设备。
4. 如果还要删除原始会话、账单或个人数据，另外执行 S08。后台的“删除员工账号”或“注销机器”，不等于把所有系统里的数据都删了。

**怎样算完成：** 网关拒绝旧令牌；后台员工状态为“已离职”；云实例已关闭；到期清理有凭证。

**出了问题：** 哪一步失败，就对同一员工重试，并查看任务详情。页面显示“关户”，不能说明云上的资源已经删除。

### S03｜设备注册、重装与注销

**先检查：**

- 确认三者一致：机器主机名、云电脑实例、绑定的员工。
- 做镜像前，在模板机上运行 `agent.exe prepare-image`（清掉本机的设备身份）。不能把设备令牌复制进镜像。

**步骤：**

1. 全新、从没绑定过的机器，开机后会自己注册。以下主机名要先在 **机器详情 → 允许注册（24 小时）** 打开注册窗口，再启动或重装 Agent：以前绑定过的、发过令牌的、注销过的。
2. 怀疑设备令牌泄露时，先在机器页点“吊销令牌”。注意它会同时允许这台机器在短时间内重新注册，所以**不是永久封锁**。要阻止这台主机继续拿到凭证，应先关户或解绑，并安排机器下线。
3. 在机器详情页核对：“直连控制台”、令牌签发时间、最后上报时间、本机用户目录（profile）、绑定的员工、凭证投递状态。只有确认实例永久下线后，才点“注销机器”。

**怎样算完成：** 这台主机在列表里只出现一次，绑定正确，状态持续更新。

**出了问题：**

- 报错 `the report names another machine`（意思是机器上报的身份和后台登记的对不上）：检查镜像里是否残留了旧的设备身份。
- 注册超时：先查后台是否健康、网络是否正常。不要反复新建同名设备。

### S04｜修改全局浏览器/AppLocker 策略

**先检查：**

- 列出会受影响的所有机器和当前的规则。能缩小变更范围就缩小。
- 全局开关也会影响没绑定员工的机器。
- AppLocker 的“审计”模式只记录、**不拦截**。

**步骤：**

1. 到 **设置 → 封禁策略**，修改域名清单或 AppLocker 放行目录。
   - 放行目录只能填机器级的目录树（以 `\*` 结尾）。
   - 不能放行用户目录、Temp（临时目录）或整个磁盘。
2. 如果要临时关闭网站拦截，或把 AppLocker 切到审计模式：记下原因、开始时间和预计恢复时间，并通知值班人。这是全局放宽安全限制，不能当作软件装不上时的常规解决办法。
3. 找至少一台在线机器，核对三项：策略已同步、浏览器实际在拦截、AppLocker 的执行模式。其他机器在总览里看版本和最后同步时间。测试结束后把开关改回原样，再验证一次。

**怎样算完成：** 机器的实际状态和策略目标一致；临时例外已关闭。

**出了问题：** 机器没生效，先看 Agent 日志和最后上报时间。不要来回提交相反的策略，那样会掩盖同步故障。

### S05｜暂停/恢复模型渠道并下发

**先检查：**

- 确认是 AWS、Google、Azure 中哪个渠道出了问题，影响了哪些模型和员工。同名模型可能在别的渠道上也有一份，只看模型名会判断错。
- LiteLLM 里模型、价格、部署的调整，要先在网关上做完。

**步骤：**

1. 在 **员工账号 → 模型与渠道** 找到目标渠道，输入渠道代号确认暂停，记下原因。暂停会更新渠道策略，并给相关员工重新生成模型列表。如果读取网关失败，页面会提示稍后点“全部下发”。
2. 查看“模型下发”里每个人的结果。先给一名测试员工下发，让他做完手上的请求后重启 Codex，验证效果。然后点“全部下发”，核对已收到的人数、失败原因，以及网关上实际的调用权限。
3. 恢复渠道前，确认供应商故障已经解除、价格和密钥都能用。点“恢复”，再按上面的方法先测测试员工、再全量验证。

**怎样算完成：** 网关拒绝走已暂停渠道的新调用；员工电脑上的模型列表和目标一致；恢复后测试调用成功。

**出了问题：**

- 有的员工设置了模型白名单（只允许用指定的模型）。如果白名单里的模型全都来自被暂停的渠道，给他下发可能失败，要单独调整他能用的模型。
- 后台下发失败，不代表渠道暂停被自动撤销了。

### S06｜发布或回滚 Agent/Codex

**先检查：** 准备好以下内容：

- 构建来源、版本号、SHA-256、变更说明、要求的最低 Agent 版本；
- 一台出问题可以回滚的测试机。

不要用同一个版本号去覆盖不同的程序文件。

**步骤：**

1. CI 把安装包上传到 OSS 后，到 **软件安装 → Agent/Codex 版本库** 点“立即扫描 OSS”。确认新版本登记为“候选”，大小和 SHA-256 与构建出的文件一致。登记本身不会改动任何机器。
2. 用“指定给机器…”选择测试机。在 **机器详情 → 版本记录** 和 Agent 日志里核对：下载、校验、安装、重启和功能验收。Codex 要在 Windows 真机上检查三点：能启动、模型列表正确、各项限制按预期生效。构建成功不算验收。
3. 人工点“标记已验收”，再点“批准稳定”。只有稳定版本能“设为全局”。输入版本号确认后，在总览和机器页跟踪“当前版本/应装版本”和异常机器。
4. 出了问题，二选一：
   - 点“清除全局”，让还没更新的机器不再尝试更新；
   - 把全局目标改回验证过的旧稳定版本。

   单独指定过版本的机器，要一台台改回旧版本，或改成“跟随全局”。“清除全局”不会卸载已经更新的版本。

**怎样算完成：** 预期的机器都回报了目标版本，关键功能正常；离线或失败的机器有单独的处理记录。

**出了问题：** 旧版 Agent 不支持只给部分机器发布（定向发布）。这种情况下不能说已经做了小范围试发布（灰度）。要安排人工真机验收，或者明确说明全局发布的风险。

### S07｜审核、安装或升级其他软件

完整流程见[软件安装与升级 SOP](软件安装与升级SOP.md)。大致顺序：

1. 客户提交工单；
2. 内部审核软件和目标机器；
3. 先在测试机上安装或升级；
4. 再逐台机器执行、验收，并回复客户。

补充说明：

- 工单已提交、任务显示成功，都不能代替在员工电脑上实际验证。
- Agent 和 Codex 本身的发布仍按 S06。
- 普通软件的安装任务目前不支持卸载。

### S08｜采集开关与留存清理

**先检查：**

- 取得客户的书面确认，内容包括：采集目的、涉及哪些员工、是否补传历史数据、存储地域、保留天数、删除例外。
- 原始会话里可能有提示词、文件内容和个人信息。
- 目前有一个已知问题：在多人共用的机器上，Agent 扫描的范围和后台允许上传的范围不一致。**这个问题修复、测试并经客户确认之前，不应开启原始会话采集。**

**步骤：**

1. 获批启用后，到 **设置 → 常规 → 采集开关** 设置起始日期和静默秒数。先用测试机验证采集范围、上传、权限和 OSS 路径，再推广到正式环境。起始日期决定能补传多早的数据，不是保留期限。
2. 要停止新增采集时，先关闭采集，并确认 Agent 已同步到关闭状态。关闭开关不会删除已上传的数据、Windows 上的原文件和备份。
3. 在 **采集数据自动保留** 设置保留天数。要一次性删除过期数据时，点“清理过期采集数据”，输入 `DELETE <天数>` 确认，然后在任务中心核对删除数量和失败项。

**怎样算完成：** 数据的数量和范围与批准单一致；清理任务成功，并有审计记录。

**注意：** 这个功能只清理 OSS 上的 `data_collect/` 目录。员工数据、网关、SLS、数据库、Windows 原文件和备份里的数据不会被删掉，要按[数据目录表](数据目录表_客户合规确认_2026-09.md)另外处理。

### S09｜配置告警、通知和令牌轮换

**先检查：** 确认值班接收人、告警阈值、令牌最长使用天数、每天最多轮换多少个，以及离线机器怎么处理。

**步骤：**

1. 到 **设置 → 告警与轮换**，设置告警开关、机器离线阈值、预算阈值和离职清理提醒天数。在 **通知渠道** 配好 Webhook 或邮件后，分别点“发送测试”，确认值班人真的收到了。
2. 开启自动令牌轮换（定期换新令牌）前，先看看员工当前令牌用了多久、最近机器同步是否正常。轮换会吊销旧令牌、下发新令牌。离线机器可能被跳过，要在任务和员工列表里跟踪。
3. 在 **告警** 页点“确认”，只表示有人接手了，不表示已解决。修好根本原因、确认告警条件已经消失后，再关闭告警，或等系统自动关闭。

**怎样算完成：** 测试通知能收到；任务中心没有持续失败的任务；异常告警有负责人。

**出了问题：** 更换通知密钥或 SMTP（发邮件用的服务）密码时，先确认新配置能用，再撤销旧的。

### S10｜升级后台/数据库

**先检查：** 准备好以下内容：

- 验证过的代码提交；
- 变更时间窗口；
- 数据库备份状态；
- 出问题时退回的版本；
- 访问服务器的方式。

部署脚本会重启 `ai-env-mgr-console` 服务。这期间 Agent 和后台的连接可能短暂断开，会自动重连。

**步骤：**

1. 在后台服务器上，进入正确的代码目录，确认没有未提交的改动，完成构建和检查。然后按[数据库模式部署](数据库模式部署.md)运行 `dist/deploy/deploy-console.sh`。脚本发现有待执行的数据库迁移时，会先导出一份数据库备份（dump），再迁移、替换程序、重启服务。
2. 逐项验证：`systemctl` 显示的服务状态、健康检查地址 `/healthz`、后台登录、员工和机器能读出来、任务中心、一次不改数据的 Agent 同步。记下部署的代码提交、迁移版本和重启时间。
3. 健康检查失败时，脚本会自动换回上一版程序，但**数据库迁移不会自动退回**。先保留现场，确认新旧数据库结构（schema）是否兼容，再决定要不要回退数据库。不要盲目重跑脚本。

**怎样算完成：** 服务健康；关键页面和 Agent 接口正常；失败的任务有原因说明。

**出了问题：** 看到 Cloudflare（网络转发服务）连接短暂断开，不要直接认定是 Agent 身份出错。先对照服务重启时间，看之后有没有重连成功。

### S11｜备份、恢复与密钥轮换

**先检查：**

- 分清“有备份”和“备份能恢复”是两回事。
- 数据库备份不包含 OSS 上的全部安装包和采集原文。
- 主密钥文件要和数据库备份分开保管。

**步骤：**

1. **定期检查和演练。** 核对 `ai-env-backup.timer`（每天自动备份的定时任务）最近一次成功的时间、OSS `_backup/` 目录里最新的备份文件和保留期限。在隔离的环境里做恢复演练，验证能登录、能读出任务、能解密凭证。演练时不能连正式网关做写操作。
2. **真正恢复时：**
   1. 先停止写入，记下恢复到哪个时间点，以及可能丢失哪段时间的数据。
   2. 先验证备份和主密钥都可用，再由数据库负责人执行恢复。
   3. 恢复后，把恢复时间点之后做过的撤权和删除再执行一遍。否则旧令牌、已删的数据或已取消的任务会“复活”。
3. **轮换密钥。** 主密钥，以及 OSS、网关、CI 的密钥，都按这个顺序换：先加入新密钥 → 验证能读写 → 把引用改到新密钥 → 撤销旧密钥。主密钥的具体步骤见[数据库模式部署](数据库模式部署.md)。不要先删旧密钥，否则以前加密的数据可能读不出来。

**怎样算完成：** 恢复演练有记录（时间、对象、校验和结果）；轮换后关键功能正常，旧密钥已撤销。

**注意：** 这一项需要云平台和数据库的权限，不是在后台页面点一下就能完成的。

### S12｜全局故障或安全事件止损

**什么时候用：** 多台机器同时离线、错误版本发布到了全局、渠道不可用、令牌出现异常调用、采集超出范围等。

先记下事件开始的时间和受影响的对象，指定一名处置负责人。

Agent 和网关的常见告警、响应时限，以及内部 Bug 工单从提交到修复发布的完整流程，见[Agent 与网关告警及 Bug 处置 SOP](Agent与网关告警及Bug处置SOP.md)。本节只写跨系统故障的止损要点。

1. **先止损。** 按事件类型只做对应的最小操作：
   - 误发布：清除全局目标，或切回原来的全局目标；
   - 渠道故障：暂停对应渠道；
   - 令牌泄露：关户或吊销令牌；
   - 采集超范围：立即关闭采集。

   不要为了修一个软件安装问题，就关掉全部机器的 AppLocker。
2. **再定位。** 查看 **总览 → 机器详情/日志、任务中心、告警、审计**，同时检查后台服务是否健康、网关和云平台是否正常。分清是哪种情况：“后台连不上”“Agent 离线”“机器休眠”还是“任务失败”。
3. **分批恢复。** 先恢复测试机或测试员工，再扩大范围。记下每一批的目标版本、结果和没恢复的名单。如果涉及数据外泄，更换相关密钥，并确认旧凭证已失效。
4. **结束和复盘。** 确认新请求、机器状态和员工那边的功能都恢复了。补齐事件时间线、根本原因、影响范围、对数据和费用的影响，以及预防措施。

**怎样算完成：** 止损已经在机器或网关上实际验证；没恢复的对象有负责人和预计时间。不能只因为“按钮已经点了”就关闭事件。

## 4. 使用本 SOP 必须知道的限制

- 后台的“审核应用”，目前是 `admin` 在上传时操作并记录，不是系统强制的双人审批。普通 EXE 安装包的静默安装参数和安装结果，必须在测试机上验收。
- “版本已登记”“任务已创建”“员工桌面上已经能用”是三种不同的状态。全局发布只允许用稳定版本，但“稳定”版本在真机上的表现仍要管理员负责确认。
- 关闭采集、关户、注销机器、删除软件包是四种不同的操作。做了其中一种，不会顺带完成其他几种的数据删除。
- 旧版[操作手册](操作手册.md)里保留了 OSS 直连方式和早期发布流程的历史说明。如果和本 SOP 冲突，以当前数据库模式的后台界面和实际代码为准，再核对当时部署的版本。
