# 客户工单系统实施计划与进度

> 2026-10-14。代码正在本地开发，还没有部署，也没有对客户开放。

## 先认识几个词

| 词 | 意思 |
|---|---|
| admin（内部后台） | 我们自己的运营人员使用的管理后台。 |
| 客户联系人 | 客户公司里负责提交工单的人。他有单独的账号，和内部人员的账号分开。 |
| 会话 | 登录后保持登录状态的凭证。客户和内部人员的会话是分开的。 |
| 后台任务 | 后台真正执行某个操作（开户、装软件等）时生成的任务，在"后台任务中心"里查看。 |
| 关联 | 在工单上记下相关的员工、机器、任务编号，方便查。关联本身不会执行任何操作。 |
| 审计 | 系统自动记下的"谁在什么时候做了什么"。 |
| 事务 | 数据库里"要么全部写成功、要么全部不写"的一组写入。 |
| 去重 / 幂等 | 同一个请求提交或点击多次，结果和只做一次一样，不会重复创建。 |
| 版本检查 | 保存前核对数据有没有被别人改过，防止两个人同时改同一张工单时互相覆盖。 |
| MFA | 多因素认证，例如登录时除了密码还要输入手机动态码。 |
| SLA | 对客户承诺的响应和完成时限。 |
| 灰度 | 先给一家公司试用，没问题再扩大。 |
| Agent | 装在每台云电脑上的管理程序。 |

## 当前进度

**已完成（基础流程已经能走通）：**

- 客户联系人有独立的账号和会话。
- 管理员可以邀请、停用客户联系人，重置他们的密码；客户可以自己改密码。
- 客户可以提交工单、查看工单、补充资料，并取消还没被受理的工单。
- 内部人员可以查看待办队列和工单详情，分派、回复、写内部备注、改状态。
- 开户、离职、权限调整三类工单有固定格式的字段。
- 重复提交用"请求键"去重；改状态时做版本检查。
- 内部备注只有内部查询能看到。
- 可以手动把员工、机器、后台任务、软件安装任务和管理员作业关联到工单。关联本身不会触发执行。
- 工单操作、全局审计记录、审计归档队列，在同一个数据库事务里一起写入。
- 数据库迁移、权限测试和集成测试已在本地通过。

**还没完成或还没确认：**

- 邮件和企业微信通知；
- 把现有的业务操作自动回链到对应工单；
- 用真实案例从头到尾验收一遍；
- 需要业务决定的事：客户要不要 MFA、对外承诺什么 SLA、工单和评论保留多久。

上线前必须做完这些决定，并完成灰度验收。当前代码还没部署，Agent 不需要改。

## 1. 目标与边界

**部署方式：** 每家公司单独部署一套后台。客户提交请求和补充资料；我们的运营人员在 admin 里受理、执行，并把结果告诉客户。

**首版不做的事：**

- 不让客户直接操作员工账号、机器、模型、额度或软件安装；
- 提交工单不会自动执行这些操作。

**工单和后台任务的分工：**

- 工单回答：客户要什么、谁在处理、处理到哪一步、结果是什么。
- 现有的后台任务中心回答：具体操作执行到哪一步、要不要重试。
- 两者互相关联，但不合并。
- 工单页面不显示内部任务的原始报错、密钥、机器日志或内部备注。

**首版支持四类请求：**

1. 新员工开户；
2. 员工离职；
3. 权限或额度调整；
4. 故障和其他请求。

软件安装先归到"其他请求"，并关联现有的安装任务。等用的人多了，再拆成单独的表单。

**首版不建设：** 跨公司的总工单台、收到邮件自动建单、复杂的 SLA 引擎、知识库、自动审批、自动执行。

## 2. 角色与入口

| 角色 | 可做的事 | 不可做的事 |
| --- | --- | --- |
| 客户联系人 | 提交工单、查看自己提交的工单、回复和补充资料、反馈结果 | 进入内部 admin、查看内部备注或执行任务 |
| 内部 operator（运营） | 查看本实例全部工单、分派、回复、标记状态、调用已有业务操作 | 修改客户身份与高风险系统设置 |
| 内部 admin（管理员） | 管理客户联系人和工单配置，处理需管理员权限的业务操作 | 不绕过工单记录或跳过执行结果核验 |
| 内部 viewer/security（只读/安全） | 按现有只读权限查看工单及审计 | 回复、分派或执行 |

**客户入口和内部入口要分开：**

- 两者可以由同一个服务提供，但登录身份、会话、页面路由和权限检查必须各自独立。
- 现有的 `admin_principals` 只代表内部人员。不能给客户开 operator 账号。
- 客户联系人采用邀请制：由内部 admin 创建和停用。
- 首版默认客户只能看自己提交的工单。

**不做跨公司查询：** 每家公司一套数据库和对象存储，所以首版不需要跨公司（跨租户）查询。以后如果改成多家公司共用一套后台，必须先完成租户隔离的设计；不能只是在现有查询上加一个页面筛选框。

## 3. 工单流程

主线：客户提交 → 待受理 → 处理中 → 已完成。

其他情况：

- **需要客户补资料：** 处理中可以转成"待客户补充"。客户回复后，回到"待受理/处理中"。
- **取消：** 受理前客户可以取消；开始处理后要取消，须由内部人员确认。
- **不能处理：** 以"已关闭—拒绝/重复/超出范围"等原因结束，并向客户说明。
- **重新打开：** 完成后，客户可以反馈问题并重新打开工单，原来的时间线保留。

**记录和权限：**

- 每次状态变化都记下操作人、时间和原因。
- 给客户看的回复和内部备注分开存。
- 权限在服务端检查，不能只靠页面隐藏。

**什么时候算完成：** 任务执行成功不会自动关闭工单。要由内部人员核对结果、告诉客户之后，工单才算完成。不要求客户再点一次确认。

### 新员工开户（首版流程）

1. **客户填表。** 填写姓名、工作邮箱、部门、Windows 用户名、预计入职日期和需要的资源。模型和额度可以填"按默认配置"。不收集密码、API Key 或私人证件。
2. **内部核对。** operator 核对各项内容、有没有重名、入职日期，以及提交人的身份。资料不够就退回让客户补充。
3. **执行开户。** operator 用现有的员工开户、模型授权和机器绑定流程操作，并在工单上关联相关的员工、机器和后台任务编号。需要 admin 权限的操作，仍按现有权限执行。
4. **核对并回告。** 执行完成后，核对员工状态、网关授权和设备结果。告诉客户交付了什么、还有什么待办，不显示凭据原文。
5. **关闭工单。** 内部人员核对完、告诉客户结果后，关闭工单。
   - 失败时保留工单。内部任务可以重试，但不能因为重复点击建出两个员工账号。
   - 客户发现问题可以重新打开。

**离职工单：**

- 单独标出生效时间和紧急程度。
- 内部要先撤销访问权限，再核对机器和凭据状态。
- 不能把"任务已排队"当作完成的依据。

## 4. 页面设计

**客户侧** 只有三个页面："提交请求""我的工单""工单详情"。

- 表单先选类型，再显示这类工单要填的字段。
- 详情页显示公开的时间线、当前状态、需要客户做什么，以及最终结果。
- 通知正文里不出现敏感信息。

**内部 admin** 新增"客户工单"栏目：

- 分为：待受理、待我处理、待客户补充、已关闭。
- 可以按类型、状态、联系人、员工和机器搜索，默认分页。
- 详情页集中显示：客户请求、内部备注、公开回复、负责人、关联的员工/机器、关联的任务和审计时间线。
- 常用操作放在详情页，不要把所有按钮都塞进列表。

**后台任务中心** 保持原来的功能。

- 可以从工单跳到相关任务。
- 任务失败时，应该在工单上写回一条客户能看懂的进度提示，由内部人员决定是重试还是联系客户。

## 5. 数据与接口

**建议新增的表：** `customer_contacts`、`customer_sessions`、`tickets`、`ticket_events`、`ticket_comments`、`ticket_task_links`。

**工单的核心字段：** 编号、类型、标题、状态、优先级、提交人、处理人、结构化的请求数据、关联员工/机器、创建/更新时间、完成时间和版本号。

**各类工单特有的字段：**

- 用带 `schema_version`（格式版本号）的 JSON 保存。
- 提交时按工单类型校验格式。
- 不能把任意 JSON 直接传给开户接口。

**事件记录和并发：**

- `ticket_events` 只追加、不修改。客户公开回复和内部备注用一个明确的字段标记谁能看到。
- 涉及开户、授权、解绑等操作时，工单动作和现有审计事件在同一个业务事务里记录。
- 外部任务用幂等键创建，并保存任务编号和最终结果。
- 用版本检查处理并发，避免两名运营人员同时执行同一个请求。

**附件和敏感信息：**

- 首版不支持附件。如果业务确实需要，另外定好文件类型、大小、病毒扫描、访问控制和保留/删除期限。
- 工单正文和评论里也禁止存密码、密钥。页面上给出提示；服务端对明显像密钥的内容拦截或打码。
- 工单和审计保留多久、客户不再合作时如何导出/删除数据，要在上线前定下来。

## 6. 实施顺序

1. **确认规则：** 定好四类工单的必填字段、客户联系人怎么创建、通知渠道、工作时间和保留期限。用真实的开户和离职案例在纸面上走一遍流程。
2. **基础能力：** 数据库迁移、客户身份和会话、服务端权限、工单和事件的存储、审计记录、防重复提交和并发保护。
3. **客户和内部页面：** 客户提交/查看/补充；内部队列、详情、分派、公开回复、内部备注、状态流转。
4. **接上现有业务：** 先关联员工开户和离职操作，再关联模型/额度和软件安装任务。所有执行都由内部人员明确触发。
5. **通知和验收：** 新工单、待补充、处理结果都要通知；失败时不泄露内部报错。完成权限、幂等、审计和异常情况的回归测试，再先给一家公司试用。

首版的前提是不改 Agent 和后台之间的通信方式。如果某类工单需要 Agent 做新的动作，单独设计和发布；不允许工单模块绕过现有的任务和策略通道直接下发。

## 7. 首版验收标准

- 客户只能访问自己的工单。即使伪造工单 ID 或改请求参数，也不能读取或操作别人的工单，更不能进入内部 admin。
- 新员工开户从提交到完成，每一步都能查到：客户请求、内部操作人、员工记录、关联任务和我方核验结果。
- 重复提交或重复点击执行，不会建出两个员工账号；任务失败时，工单不会被误标为已完成。
- 公开回复、内部备注、给附件预留的接口、通知和审计，都不泄露凭据或内部日志。
- 工单列表分页，待处理的排在前面；已关闭的历史默认折叠，不影响日常接单。

## 8. 会议待确认

1. 客户联系人怎么登录？首版建议用邀请制账号。要不要求 MFA？
2. 客户只能看自己的工单，还是要指定一名客户负责人看本公司全部工单？首版默认只能看自己的。
3. 通知先用邮件还是企业微信？首版建议"站内显示状态 + 邮件提醒"，通知正文只放工单编号和链接。
4. 首次响应和完成时限要不要对客户承诺？还没定的话，先记录时间点并统计超时情况，页面上不写固定的 SLA。
5. 工单、评论和以后的附件分别保留多久？必须在上线前和客户确认。
