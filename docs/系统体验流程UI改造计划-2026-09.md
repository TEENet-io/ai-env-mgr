# Admin / Agent 系统体验、流程与 UI 改造计划

版本：V1（2026-09-27）  
范围：Admin、Agent、发布流程、软件安装、任务中心、数据合规和后台 UI  
原则：先稳定流程和状态，再优化界面；先解决管理员高频操作，再扩展低频能力。

## 1. 目标

本次改造不以“增加页面数量”为目标，而是建立一套可预测、可恢复、可审计的管理流程：

1. 管理员能知道每个操作当前处于什么状态、下一步是什么。
2. Admin 重启、Agent 重启或网络中断后，任务不会丢失或重复执行。
3. 发布、软件安装、模型下发等高风险动作有预览、确认、回滚或重试路径。
4. 页面按管理员任务组织，而不是按内部实现组织。
5. 数据采集和删除有明确的策略、执行记录和客户可确认的口径。
6. 为后续 AWS/GCP/Azure 对账预留接口，但本轮不把对账作为主线。

## 2. 优先级

### P0：先做，影响系统可靠性和日常操作

- 统一并持久化后台任务
- 重构任务中心
- 发布与软件安装流程拆分
- 高风险操作确认和影响范围预览
- 机器状态与同步状态修正
- 任务、安装、发布的幂等和重复执行保护

### P1：随后做，影响管理效率和客户体验

- 版本发布审批流
- 软件包元数据和审核信息
- 数据保留、删除和合规状态
- 页面自动刷新、数据新鲜度和失败提示
- 告警、审计、任务的筛选、分页和关联跳转
- UI 组件和 CSS 统一

### P2：稳定后做，影响安全性和维护成本

- URL 下载安全限制
- 快捷方式和安装路径校验
- Agent 自动更新验收与回滚
- 数据库查询性能优化
- 移动端和无障碍优化

### P3：最低优先级，对账能力

对账暂不进入前几轮开发，只保留任务类型和数据模型预留。后续按以下顺序接入：

1. AWS Bedrock CUR 与 LiteLLM；
2. Azure；
3. GCP；
4. 多供应商统一报表和差异处理。

对账必须作为独立 Worker 运行，不能阻塞 Admin 或 Agent 控制请求。

## 4. P0 改造内容

### 4.1 统一任务模型

所有耗时操作统一进入 PostgreSQL 任务表，至少包括：

- task_id
- kind
- status
- progress
- requested_by
- target_type / target_id
- payload_hash
- attempts
- lease_until
- started_at / finished_at
- last_error
- cancel_requested
- result_reference

统一状态：

```text
pending → running → succeeded
                  ├→ retry_wait → running
                  ├→ cancelled
                  └→ failed
```

必须纳入统一任务模型的操作：

- 软件包上传和审核
- OSS 扫描和登记
- Agent / Codex 发布
- 机器版本更新
- 软件安装
- 模型下发
- 关户和凭据撤回
- 数据清理
- 告警通知

当前仅保存在内存中的上传、发布进度不能作为最终状态。Admin 重启后应能从数据库恢复任务。

### 4.2 重构任务中心

任务中心改成“摘要 + 筛选 + 详情”三层结构：

默认页面只显示：

- 进行中
- 失败待处理
- 最近完成
- 需要管理员操作

筛选条件：

- 任务类型
- 员工
- 机器
- 状态
- 时间范围
- 是否失败

任务详情显示：

- 当前步骤
- 进度
- 重试次数
- 最近错误
- 关联机器或员工
- 关联审计记录
- 取消、重试、查看日志入口

内部维护任务可以默认折叠，但不能从系统中完全隐藏。历史任务采用分页和时间分组，不一次性加载全部记录。

### 4.3 发布和软件安装拆分

发布流程：

```text
OSS/CI 发现
    ↓
候选版本
    ↓
测试机器或测试员工
    ↓
管理员批准
    ↓
指定机器 / 全局发布
    ↓
逐机执行与回报
    ↓
完成、失败或回滚
```

软件安装流程：

```text
上传或 URL 获取
    ↓
解析包信息
    ↓
管理员审核
    ↓
创建安装任务
    ↓
Agent 下载 / 校验 / 安装
    ↓
检测安装结果
    ↓
成功、失败、重试或取消
```

“上传并审核”可以保留为快捷操作，但后台仍需记录上传、审核和发布三个阶段，不能把它们视为一个不可拆分的动作。

### 4.4 高风险操作确认

所有高风险操作统一使用确认组件，并显示影响范围：

- 关户：员工、机器、凭据和数据影响
- 解绑：机器当前绑定员工和后续凭据影响
- 关闭 Codex：将终止的进程和员工影响
- 全部下发：员工数、机器数和预计执行时间
- 全局发布：目标版本、当前版本、在线机器数
- 删除软件包：删除范围、已安装软件是否保留

确认页面需要明确区分“删除记录”“删除 OSS 文件”“卸载机器软件”三种不同动作。

## 5. P0 状态与幂等改造

### 5.1 机器在线状态

机器在线状态使用服务器收到状态的时间，不直接信任 Agent 上报的时间。客户端时间单独保存，并限制允许偏差。

需要增加：

- 最后收到时间
- Agent 上报时间
- 最近一次成功同步
- 最近一次失败同步
- 状态来源（API / OSS / 缓存）

### 5.2 防止重复任务

创建任务前检查：

- 同一机器是否已有相同应用版本任务
- 同一机器是否有正在执行的更新任务
- 同一版本是否已成功安装
- 是否允许降级
- 上一个失败任务是否已明确取消或重试

幂等键示例：

```text
application_install:{machine}:{app_id}:{version}
release:{machine}:{product}:{version}
model_push:{scope}:{policy_hash}
```

### 5.3 Admin 和 Agent 重启恢复

Admin 或 Agent 重启后：

- 任务不能重新从头创建
- 已完成任务不能再次执行
- 运行中的任务进入恢复或超时状态
- 失去租约的任务可以被安全接管
- UI 显示“恢复执行”还是“需要人工重试”

## 6. P1 发布与软件安装体验

### 6.1 版本库

版本列表增加：

- 发布状态
- 上传人和审核人
- 上传时间和批准时间
- SHA-256
- 来源 URL / CI Run
- 最低 Agent 版本
- 当前影响机器数
- 最近失败率

候选版本不能直接成为全局版本，必须先通过测试或明确的管理员强制确认。

### 6.2 软件包目录

应用详情显示：

- 显示名称
- App ID
- 厂商
- 版本
- 安装包类型
- SHA-256
- 检测路径和检测规则
- 快捷方式配置
- 上传和审核记录
- AppLocker 兼容状态
- 已安装机器数

安装页面显示机器上下文：

- 在线 / 离线
- Agent 版本
- 当前软件版本
- 已有任务
- 最近错误
- 是否需要管理员权限

### 6.3 发布前预览

发布前提供影响范围预览：

```text
目标版本：1.5.6
跟随全局机器：8 台
在线：6 台
离线：2 台
当前版本过低：1 台
已有失败任务：1 台
```

管理员确认后才创建实际发布任务。

## 7. P1 数据合规流程

数据采集设置页面增加：

- 当前采集状态
- 采集范围
- 数据来源
- 存储位置
- 保留天数
- 下次清理时间
- 最近一次清理结果
- 待删除数据量
- 删除失败记录

新增数据清理任务：

```text
scheduled → running → deleted
                    ├→ partial
                    └→ failed
```

员工关户时，页面应显示完整链路：

```text
撤回凭据 → 停止采集 → 保留期 → 删除数据 → 删除确认 → 审计完成
```

删除操作必须产生审计记录和删除结果摘要，支持客户合规确认。

## 8. P1 UI 统一改造

### 8.1 统一视觉组件

建立以下基础组件：

- 状态标签
- 风险等级标签
- 任务卡片
- 确认弹窗
- 空状态
- 错误状态
- 加载状态
- 分页和筛选条
- 详情抽屉

清理重复 CSS 规则，统一颜色、间距、按钮和表格规范。

### 8.2 页面统一反馈

所有操作完成后必须显示：

- 成功或失败
- 任务编号
- 下一步操作
- 可跳转的任务详情

例如：

```text
已创建安装任务 install-123
机器将在下一次同步时执行
查看任务详情 →
```

### 8.3 自动刷新

任务、机器、发布和安装页面增加：

- 自动刷新开关
- 最近刷新时间
- 数据过期提示
- 手动刷新按钮

网络或网关不可用时，显示“最后一次成功数据”，不要让页面一直等待远程请求。

## 9. P2 安全、稳定性和性能

后续处理：

- URL 下载限制 HTTPS、大小、重定向和内网地址
- 快捷方式路径和安装路径白名单
- Agent 更新失败自动回滚
- 老版本 Agent 升级验收矩阵
- 日志大小和单文件采集上限
- 任务、告警、发布页面减少 N+1 查询
- 页面移动端和键盘操作优化
- 审计动作从内部英文 ID 转换为用户可读名称

## 10. P3 对账预留

本轮不实现完整对账，只做以下预留：

- 保留 `billing_reconcile` 任务类型
- 保留 provider、period、scope 字段
- 任务中心支持展示该类型
- 用量页面预留“费用对账”页签
- 不把 AWS AK/SK 或 LiteLLM DSN 放入 Admin 页面和普通任务 payload

真正实施时，单独部署 Billing Worker，先做 AWS Bedrock，再扩展 Azure 和 GCP。对账 Worker 不得阻塞 Admin HTTP 请求或 Agent 控制链路。

## 11. 实施批次

### 批次一：任务基础设施

- 统一任务状态和持久化
- 任务中心筛选、分页、详情、重试、取消
- 上传/发布任务从内存迁移到数据库
- Agent 重启和 Admin 重启恢复

验收标准：Admin 重启后，任务进度和错误仍可查看；同一任务不会重复执行。

### 批次二：发布和软件安装

- 拆分版本库、发布任务、软件目录
- 增加候选/批准/全局状态
- 增加发布前影响范围预览
- 增加安装任务重复检查和机器上下文
- 增加高风险确认

验收标准：管理员可以明确知道“谁会被影响、什么时候执行、失败后怎么办”。

### 批次三：状态、合规和 UI

- 修正在线时间来源
- 增加数据保留和删除任务
- 增加数据新鲜度提示和自动刷新
- 统一 UI 组件和 CSS
- 告警、审计、任务互相链接

验收标准：客户可以查看数据从采集到删除的完整链路，管理员无需依靠日志猜测系统状态。

### 批次四：安全和性能

- URL 下载安全
- 路径白名单
- Agent 更新回滚
- 查询性能和移动端优化

### 批次五：费用对账

- AWS Bedrock CUR 与 LiteLLM
- Azure
- GCP
- 多供应商统一差异报表

## 12. 暂不做

- 不在本轮开发完整 AWS/GCP/Azure 对账
- 不把对账程序直接编译进 Admin
- 不新增复杂的多租户模型；当前继续采用每家公司独立部署和独立云账号
- 不为了视觉效果引入大型前端框架
- 不把所有后台维护任务都默认展示在首页

## 13. 本轮实施状态（2026-09-27）

已落地并部署到 Admin：

- 软件目录与 Agent/Codex 版本库拆分；软件安装、发布任务、后台任务分别进入独立入口。
- 上传/扫描/安装等后台操作使用数据库持久化的 Admin Job，Admin 重启后会标记中断任务并保留进度、步骤和错误。
- 任务中心支持状态、类型筛选，系统维护任务默认折叠，进行中任务自动刷新，历史卡片可折叠。
- 发布状态增加候选、已验收、稳定、停用流程；只有稳定版本可以设为全局，避免候选包误发全员。
- 机器在线状态统一使用服务端接收时间；客户端时间仅用于诊断。
- 采集数据提供带二次确认的按保留天数清理任务，只匹配 `data_collect/` 前缀并记录到任务中心。
- 外部下载限制 HTTPS、大小上限和私网地址；应用检测路径、快捷方式路径和文件名做绝对路径校验。
- 高风险操作补齐确认提示，任务中心和软件页面统一了移动端布局及视觉状态。

本轮未改 Agent 二进制，因此不触发 Agent CI；费用对账仍按 P3 计划单独实施。
