# Admin / Agent 系统体验、流程与 UI 改造计划

版本：V1（2026-09-27）  
范围：Admin、Agent、发布流程、软件安装、任务中心、数据合规和后台 UI  
原则：
- 先把流程和状态做稳，再优化界面。
- 先解决管理员经常做的操作，再扩展不常用的功能。

## 先认识几个词

| 词 | 意思 |
|---|---|
| Admin | 管理后台，管理员在这里操作。数据存在 PostgreSQL 数据库里。 |
| Agent | 装在每台云电脑上的管理程序，负责执行后台下发的任务并回报结果。 |
| 任务 | 后台里比较耗时的操作，例如上传软件包、发布新版本、给机器装软件。 |
| 持久化 | 把数据存进数据库。程序重启后数据还在；只放在内存里的数据，重启就丢了。 |
| 幂等 | 同一个操作重复执行多次，结果和只执行一次一样。用来防止任务被重复执行。 |
| 幂等键 | 用来判断"是不是同一个任务"的标识。幂等键相同，就视为同一个任务。 |
| 租约 | Agent 领取任务时拿到的"占用期限"。期限内任务归它；过期没完成，任务可以被别人接手。 |
| Worker | 在后台单独运行、专门处理某类工作的程序。 |
| 对账 | 把云厂商的账单和网关记录的用量对一遍，找出差异。 |
| OSS | 阿里云的对象存储，用来存放安装包等文件。 |
| CI | 自动构建安装包并上传的流程。 |
| SHA-256 | 安装包的"指纹"。指纹一致，说明文件没有被换掉或损坏。 |
| AppLocker | Windows 自带的程序白名单。不在名单里的程序不能运行。 |
| LiteLLM | 员工调用 AI 模型时经过的网关软件。 |
| 关户 | 员工离职或停用时，关闭他的账号。 |
| 下发 | 后台把配置推送到机器上。 |
| 全局版本 | 默认装到所有机器上的版本。机器没有单独指定版本时，就"跟随全局"。 |
| P0～P3 | 优先级。P0 最高，P3 最低。 |

## 1. 目标

这次改造的目的不是多加几个页面，而是建立一套管理流程，做到三点：结果可以预期、出错能恢复、操作有记录可查。具体是：

1. 管理员能看到每个操作现在处于什么状态、下一步是什么。
2. Admin 重启、Agent 重启或网络中断后，任务不会丢，也不会重复执行。
3. 发布、软件安装、模型下发这类高风险操作，都要有预览、确认，以及回滚或重试的办法。
4. 页面按管理员要做的事来组织，而不是按程序内部怎么实现来组织。
5. 数据采集和删除要有明确的规则和执行记录，并且有客户可以确认的统一说法。
6. 给以后对接 AWS、GCP、Azure 的对账留好接口，但这一轮不把对账当作重点。

## 2. 优先级

### P0：先做。影响系统可靠性和日常操作

- 所有后台任务用统一的方式管理，并存进数据库
- 重做任务中心
- 把发布流程和软件安装流程分开
- 高风险操作要先确认，并预览影响范围
- 修正机器状态和同步状态
- 防止任务、安装、发布被重复执行（幂等）

### P1：接着做。影响管理效率和客户体验

- 版本发布审批流程
- 软件包的基本信息和审核信息
- 数据保留、删除和合规状态
- 页面自动刷新、显示数据是否过时、失败提示
- 告警、审计、任务页面支持筛选、分页和互相跳转
- 统一 UI 组件和 CSS 样式

### P2：系统稳定后再做。影响安全性和维护成本

- 限制通过 URL 下载文件时的安全风险
- 校验快捷方式和安装路径
- Agent 自动更新的验收与回滚
- 优化数据库查询性能
- 适配手机端和无障碍访问

### P3：最低优先级，对账功能

前几轮开发不做对账，只预留任务类型和数据结构。以后按这个顺序接入：

1. AWS Bedrock 的费用明细报告（CUR）与 LiteLLM 记录对账；
2. Azure；
3. GCP；
4. 多家供应商的统一报表和差异处理。

对账必须作为独立的 Worker 运行，不能拖慢 Admin，也不能卡住发给 Agent 的控制请求。

## 4. P0 改造内容

### 4.1 统一任务模型

所有耗时操作都记录到 PostgreSQL 的任务表里。任务表至少包括这些字段：

- task_id
- kind
- status
- progress
- requested_by
- target_type / target_id
- payload_hash
- attempts
- lease_until
- started_at / finished_at
- last_error
- cancel_requested
- result_reference

所有任务使用同一套状态：

```text
pending → running → succeeded
                  ├→ retry_wait → running
                  ├→ cancelled
                  └→ failed
```

状态含义：`pending` 等待执行，`running` 执行中，`succeeded` 成功，`retry_wait` 等待重试，`cancelled` 已取消，`failed` 失败。

以下操作必须纳入统一任务模型：

- 软件包上传和审核
- OSS 扫描和登记
- Agent / Codex 发布
- 机器版本更新
- 软件安装
- 模型下发
- 关户和凭据撤回
- 数据清理
- 告警通知

目前上传和发布的进度只存在内存里，不能当作最终状态。Admin 重启后，应该能从数据库恢复这些任务。

### 4.2 重做任务中心

任务中心分三层："摘要 + 筛选 + 详情"。

默认页面只显示：

- 进行中
- 失败待处理
- 最近完成
- 需要管理员操作

筛选条件：

- 任务类型
- 员工
- 机器
- 状态
- 时间范围
- 是否失败

任务详情显示：

- 当前步骤
- 进度
- 重试次数
- 最近错误
- 关联机器或员工
- 关联审计记录
- 取消、重试、查看日志的入口

系统内部的维护任务可以默认折叠，但不能完全藏起来。历史任务分页显示，并按时间分组，不要一次加载全部记录。

### 4.3 发布和软件安装分开

发布流程：

```text
OSS/CI 发现
    ↓
候选版本
    ↓
测试机器或测试员工
    ↓
管理员批准
    ↓
指定机器 / 全局发布
    ↓
逐机执行与回报
    ↓
完成、失败或回滚
```

软件安装流程：

```text
上传或 URL 获取
    ↓
解析包信息
    ↓
管理员审核
    ↓
创建安装任务
    ↓
Agent 下载 / 校验 / 安装
    ↓
检测安装结果
    ↓
成功、失败、重试或取消
```

"上传并审核"这个快捷按钮可以保留。但后台仍要分别记录上传、审核、发布三个阶段，不能把它们当成一个分不开的动作。

### 4.4 高风险操作确认

所有高风险操作都用同一个确认组件，并显示影响范围：

- 关户：对员工、机器、凭据和数据的影响
- 解绑：这台机器当前绑定的员工，以及之后对凭据的影响
- 关闭 Codex：会结束哪些进程，影响哪些员工
- 全部下发：涉及多少员工、多少台机器，预计要执行多久
- 全局发布：目标版本、当前版本、在线机器数
- 删除软件包：删除范围，以及机器上已经装好的软件是否保留

确认页面要把三种不同的操作分清楚："删除记录""删除 OSS 文件""卸载机器上的软件"。

## 5. P0 状态与防重复改造

### 5.1 机器在线状态

判断机器是否在线，用服务器收到状态的时间，不直接相信 Agent 自己报的时间。Agent 报的时间单独保存，并限制它和服务器时间最多能差多少。

需要增加：

- 最后收到时间
- Agent 上报时间
- 最近一次成功同步
- 最近一次失败同步
- 状态来源（API / OSS / 缓存）

### 5.2 防止重复任务

创建任务前先检查：

- 同一台机器是否已经有相同应用、相同版本的任务
- 同一台机器是否有正在执行的更新任务
- 这个版本是否已经装好了
- 是否允许装回旧版本（降级）
- 上一个失败的任务是否已经明确取消或重试

幂等键示例：

```text
application_install:{machine}:{app_id}:{version}
release:{machine}:{product}:{version}
model_push:{scope}:{policy_hash}
```

### 5.3 Admin 和 Agent 重启后的恢复

Admin 或 Agent 重启后：

- 不能把任务从头重新创建一遍
- 已经完成的任务不能再执行
- 原来正在运行的任务进入"恢复"或"超时"状态
- 租约已失效的任务，可以安全地交给别人接手
- 界面上显示是"恢复执行"还是"需要人工重试"

## 6. P1 发布与软件安装体验

### 6.1 版本库

版本列表增加以下信息：

- 发布状态
- 上传人和审核人
- 上传时间和批准时间
- SHA-256
- 来源 URL / CI Run（构建记录）
- 最低 Agent 版本
- 当前影响机器数
- 最近失败率

候选版本不能直接变成全局版本。必须先通过测试，或者由管理员明确确认强制发布。

### 6.2 软件包目录

应用详情显示：

- 显示名称
- App ID
- 厂商
- 版本
- 安装包类型
- SHA-256
- 检测路径和检测规则（用来判断软件是否装好）
- 快捷方式配置
- 上传和审核记录
- AppLocker 兼容状态
- 已安装机器数

安装页面显示机器的相关情况：

- 在线 / 离线
- Agent 版本
- 当前软件版本
- 已有任务
- 最近错误
- 是否需要管理员权限

### 6.3 发布前预览

发布前先展示影响范围：

```text
目标版本：1.5.6
跟随全局机器：8 台
在线：6 台
离线：2 台
当前版本过低：1 台
已有失败任务：1 台
```

管理员确认后，才真正创建发布任务。

## 7. P1 数据合规流程

数据采集设置页面增加：

- 当前采集状态
- 采集范围
- 数据来源
- 存储位置
- 保留天数
- 下次清理时间
- 最近一次清理结果
- 待删除数据量
- 删除失败记录

新增数据清理任务，状态如下：

```text
scheduled → running → deleted
                    ├→ partial
                    └→ failed
```

状态含义：`scheduled` 已排期，`running` 清理中，`deleted` 已删除，`partial` 只删了一部分，`failed` 失败。

员工关户时，页面要显示完整的处理过程：

```text
撤回凭据 → 停止采集 → 保留期 → 删除数据 → 删除确认 → 审计完成
```

删除操作必须生成审计记录和删除结果摘要，供客户做合规确认。

## 8. P1 UI 统一改造

### 8.1 统一界面组件

做出以下基础组件：

- 状态标签
- 风险等级标签
- 任务卡片
- 确认弹窗
- 空状态（没有数据时的显示）
- 错误状态
- 加载状态
- 分页和筛选条
- 详情抽屉（从侧边滑出的详情面板）

清理重复的 CSS 规则，统一颜色、间距、按钮和表格的样式。

### 8.2 页面统一反馈

每个操作完成后都必须显示：

- 成功还是失败
- 任务编号
- 下一步做什么
- 能点进去的任务详情链接

例如：

```text
已创建安装任务 install-123
机器将在下一次同步时执行
查看任务详情 →
```

### 8.3 自动刷新

任务、机器、发布和安装页面增加：

- 自动刷新开关
- 最近刷新时间
- 数据过期提示
- 手动刷新按钮

网络或网关不通时，显示"最后一次成功获取的数据"，不要让页面一直卡在等待远程请求上。

## 9. P2 安全、稳定性和性能

后续处理：

- 通过 URL 下载时：只允许 HTTPS，限制文件大小，限制跳转（重定向），禁止访问内网地址
- 快捷方式路径和安装路径只允许白名单里的位置
- Agent 更新失败时自动回滚
- 老版本 Agent 升级的验收清单（覆盖各种版本组合）
- 限制日志大小和单个采集文件的大小
- 任务、告警、发布页面减少 N+1 查询（列表里每一行都单独查一次数据库，导致页面变慢）
- 优化手机端显示和键盘操作
- 审计记录里的操作名，从内部英文 ID 改成用户看得懂的名称

## 10. P3 对账预留

这一轮不做完整的对账，只做以下预留：

- 保留 `billing_reconcile` 任务类型
- 保留 provider、period、scope 字段
- 任务中心能显示这类任务
- 用量页面预留"费用对账"页签
- 不把 AWS 的访问密钥（AK/SK）或 LiteLLM 的数据库连接串（DSN）放进 Admin 页面或普通任务的参数（payload）里

真正做的时候，单独部署一个账单 Worker（Billing Worker），先做 AWS Bedrock，再扩展到 Azure 和 GCP。对账 Worker 不能拖慢 Admin 的网页请求，也不能卡住发给 Agent 的控制请求。

## 11. 分批实施

### 第一批：任务基础功能

- 统一任务状态，并存进数据库
- 任务中心支持筛选、分页、详情、重试、取消
- 上传和发布任务从内存改存到数据库
- Agent 重启和 Admin 重启后能恢复

验收标准：Admin 重启后，仍能看到任务进度和错误；同一个任务不会重复执行。

### 第二批：发布和软件安装

- 把版本库、发布任务、软件目录拆开
- 增加候选 / 批准 / 全局三种状态
- 增加发布前的影响范围预览
- 安装任务增加重复检查，并显示机器的相关情况
- 增加高风险操作确认

验收标准：管理员能清楚知道"谁会受影响、什么时候执行、失败了怎么办"。

### 第三批：状态、合规和 UI

- 修正在线时间的来源
- 增加数据保留和删除任务
- 增加数据是否过时的提示和自动刷新
- 统一 UI 组件和 CSS
- 告警、审计、任务页面互相链接

验收标准：客户能看到数据从采集到删除的完整过程；管理员不用再靠翻日志猜系统状态。

### 第四批：安全和性能

- URL 下载安全
- 路径白名单
- Agent 更新回滚
- 查询性能和手机端优化

### 第五批：费用对账

- AWS Bedrock CUR 与 LiteLLM
- Azure
- GCP
- 多家供应商统一的差异报表

## 12. 暂不做

- 这一轮不开发完整的 AWS / GCP / Azure 对账
- 不把对账程序直接编译进 Admin
- 不做复杂的多租户（多家公司共用一套系统）模型；继续每家公司单独部署、单独使用自己的云账号
- 不为了好看引入大型前端框架
- 不把所有后台维护任务都默认显示在首页

## 13. 本轮完成情况（2026-09-27）

已经做完并部署到 Admin：

- 软件目录和 Agent/Codex 版本库已拆开；软件安装、发布任务、后台任务各有独立入口。
- 上传、扫描、安装等后台操作改用存进数据库的后台任务（Admin Job）。Admin 重启后，会把被中断的任务标记出来，并保留进度、步骤和错误。
- 任务中心：
  - 可以按状态、类型筛选；
  - 系统维护任务默认折叠；
  - 进行中的任务自动刷新；
  - 历史任务卡片可以折叠。
- 发布状态增加了"候选、已验收、稳定、停用"这套流程。只有稳定版本才能设为全局版本，避免候选包被误发给所有人。
- 机器在线状态统一用服务器收到状态的时间；机器自己报的时间只用于排查问题。
- 采集数据可以按保留天数清理。清理前要二次确认，只处理 `data_collect/` 路径下的数据，并在任务中心留下记录。
- 外部下载：只允许 HTTPS，限制文件大小，禁止访问内网地址。应用检测路径、快捷方式路径和文件名都要求是完整路径（绝对路径），并做校验。
- 高风险操作都加上了确认提示。任务中心和软件页面统一了手机端布局和状态显示样式。

这一轮没有改 Agent 程序本身，所以不会触发 Agent 的自动构建（CI）。费用对账仍按 P3 计划单独做。
