# 控制台数据库模式:部署与切换清单

> 2026-09-18。对应分支 `rds-phase0`。设计见 `docs/superpowers/specs/2026-09-12-rds-unified-control-plane-design.md`(rev.4),进度见 `docs/superpowers/plans/2026-09-12-rds-phase0-1.md`。

## 一句话

同一个 `admin` 二进制,设了 `AIENVMGR_DB_DSN` 就是数据库模式:账号 + 验证器登录,页面读表,每个操作是"一个事务 + 排队任务",Worker 在进程内跑,OSS/SLS 用服务端身份。不设就是原来的 OSS 模式,行为不变。

## 环境变量(全部走 systemd `EnvironmentFile`,600)

| 变量 | 作用 |
|---|---|
| `AIENVMGR_DB_DSN` | `postgres://aienv_app:...@<rds 内网地址>:5432/aienv?sslmode=require`。**存在即启用数据库模式。** |
| `AIENVMGR_MASTER_KEY_FILE` | 信封加密主密钥文件,root 专属 0600。生成:`umask 077; printf '{"current":"k1","keys":{"k1":"%s"}}\n' "$(openssl rand -base64 32)" > /etc/ai-env-mgr/master.key`。**备份到数据库备份之外的地方**:没有它,库里所有令牌和验证器种子都打不开。 |
| `AIENVMGR_OSS_ACCESS_KEY_ID` / `_SECRET` | 服务端 OSS 身份(读写 `agent_workdir/`、`admin/`,读 SLS)。新 ECS 上改用 RAM 实例角色后撤掉。 |
| `AIENVMGR_GATEWAY_URL` / `AIENVMGR_GATEWAY_ADMIN_KEY` | 同原来。注意 URL 必须是员工桌面能访问的公网地址(`https://litellm.teenet.app`),它会被写进每个人的 `config.toml`。 |
| `AIENVMGR_SLS_PROJECT` / `AIENVMGR_SLS_ENDPOINT` | 同原来;数据库模式下用上面的服务端身份读。 |
| `AIENVMGR_PUBLIC_HOST` | 验证器应用里显示的名字,填 `windows-control.teenet.app`。 |
| `AIENVMGR_FIRST_ADMIN_EMAIL` | 首个管理员的邮箱(可空)。 |
| `AIENVMGR_WORKER` | **`on` 才跑 Worker,默认关。** 迁移期间数据库一边导入一边比对,旧控制台还活着,一个自己启动的 Worker 会开始改写机器正在读的对象。 |

## 首次启动

1. 数据库上用超级账号跑一次 `go run ./cmd/migrate up`(或直接启动控制台,它自己会迁移)。三个角色的密码单独设:`alter role aienv_app login password '...'` 等,见 `go/db/README.md`。
2. 启动控制台。首次启动会在主密钥同目录写一个 root 专属的 `first-admin.txt`(用户名和初始密码,**不进日志**),日志只提示文件位置。用它登录,页面会引导绑定验证器并显示十个恢复码,之后在"我的账号"改密码,**然后删掉这个文件**。
3. `/healthz` 返回 `ok` 即数据库可达;Cloudflare/systemd 的健康检查指到这里。

## 切换流程

分四段,每段有明确的进入条件和退回方式。三个命令都从 `/etc/ai-env-mgr/console.env` 读身份,`import` 和 `compare` **不写 OSS、不写网关**。

### A. 影子运行(现在的状态,可以持续任意久)

- 新控制台 `AIENVMGR_WORKER` 未设(=关),只在内网端口。
- 随时可以 `ai-env-migrate import`(可重复,不改 epoch、不发令牌)和 `ai-env-migrate compare`。
- 在新控制台里点什么都只进库、进任务队列,**不会到达任何一台桌面**。
- 退回:什么都不用做。

### B. 停写(切换当天开始)

1. 停掉 AWS 上的旧控制台(`systemctl stop ai-env-mgr-admin`)。从这一刻起没有人能改 OSS 对象,机器照常按已有对象运行。
2. `ai-env-migrate import` 同步停写前的最后变化。
3. `ai-env-migrate compare` —— **门禁**:退出码 0 才往下走;2 表示有差异,逐条看。预期只剩两类:每个在用员工"有已发布凭据、库里无令牌明文"(下一步处理),以及网关上被人手工改过的额度/白名单(决定以谁为准:改库,或改网关后再导一次)。
- 退回:`systemctl start` 旧控制台。库里多出来的东西不影响它。

### C. 接管

4. `AIENVMGR_WORKER=on`,重启新控制台。Worker 开始导入机器状态、投递审计;它**不会**主动改任何凭据对象——只有排了任务的员工才会被碰。
5. 在新控制台里给比对点名的员工逐个"重发":Worker 在网关发新令牌(旧别名 `emp-<user>` 同时吊销)、写新的 `credentials.zip`,agent 下一轮换上并结束该员工的 Codex 一次。
6. `ai-env-migrate compare` 退出码 0 → 接管完成。此后库是权威,OSS 对象由 Worker 生成。
- 退回(第 5 步之后就有代价):关 Worker、启旧控制台,**并在旧控制台里把已重发的员工再重发一次**——他们机器上的是新令牌,旧控制台不认识。所以第 5 步之前把比对看干净。

### D. 收尾

7. Cloudflare 把 `windows-control.teenet.app` 指到新机器;nginx 用已有的源站证书反代到 `127.0.0.1:8090`。
8. 撤销旧控制台用过的 AK,新建一把只有 `agent_workdir/`、`admin/` 读写和 SLS 只读的给控制台(或挂 RAM 实例角色,见"还没做的")。
9. 发布不带 Claude 的新 agent。

## 运行中的几件事

- **后台任务**(告警 › 后台任务页签):每个操作排的任务、失败原因、重试次数;"立即对账网关"按钮。判定为永久失败(400 类)的任务不再重试,要人看。
- **对账**每小时自动跑;发现"我们以为吊销了、网关还在服务"的令牌会直接删掉并在日志里记 `gateway_drift`。
- **审计投递**每分钟写到本机审计流(Logtail 采走),五分钟后回查 SLS 按 event_id 确认;查不到的一直留在待确认列表,不会默认成功。
- **机器状态**每分钟从 `_status/` 导入;agent 协议不变。导入后按报告结算设备的发布目标(见 `OSS布局.md` §7.1)。
- **Logtail** 只送 12 小时内的日志行:从旧控制台导入的历史审计不会再被采集(它们当时已由旧控制台送过,用的是旧 id),这些条目在回查里标为"已由旧控制台归档";新产生的审计正常送到并确认。这台机器要在 SLS 项目 `windows-control-logs` 的机器组里(自定义标识 `wc-gateway`,写在 `/etc/ilogtail/user_defined_id`)。
- **发布**:`/releases` 一页:设为全局,或指定给机器(机器页也能改),流程见 `操作手册.md` §4.7。Worker 每天扫一次 `_codex/`、`_agent/`(页面上有"立即扫描 OSS"按钮),CI 传上来的包自动算 SHA-256 列进来(失败的 key 到重启前不再重读)。

- **用量快照** 每天 UTC 0:30 从 SLS `audit` 日志库汇总前三天的 `llm_call`,写 `usage_daily`;**告警规则** 每 10 分钟,**通知投递** 每分钟,**令牌轮换** 每天 UTC 1:00(默认关)。都在任务页可见;阈值、渠道、轮换在设置页。见 `操作手册.md` §4.8。
- **升级控制台**:带新迁移的版本,**先用属主账号(postgres)跑 `ai-env-migrate up`,再换 `/usr/local/bin/ai-env-admin` 重启**。控制台用的 `aienv_app` 不是表的属主,改表结构会报 `must be owner of table`;控制台发现有没跑的迁移会拒绝启动(不会带着旧表结构运行),所以顺序反了只是服务起不来,补跑迁移后自动恢复。上一版程序留在 `ai-env-admin.prev`。
- **换主密钥**:`ai-env-migrate rekey`,见 `操作手册.md` §4.10。
- **设备 API**:`/agent/v1/*`,agent 1.3.0 起直连控制台(注册只报主机名,令牌哈希存 `device_tokens`);过渡开关在"设置 › 设备通道"。见 `操作手册.md` §4.9。
- **每晚备份**:`ai-env-backup.timer`(UTC 2:00)执行 `/usr/local/sbin/ai-env-backup.sh`:容器内 `pg_dump` → gzip → `ai-env-admin backup` 传到 `agent_workdir/_backup/aienv-<日期>.sql.gz`,保留 30 天。单元文件在 `dist/backup/`。

## 还没做的

- **RAM 实例角色**:代码目前要求固定 AK/SK;挂角色需要接 STS 临时凭证自动刷新,要对着 ECS 元数据服务实测。在那之前 AK 留在 600 的环境文件里。
- **Agent 独立更新器与启动失败恢复**(设计稿 §5,agent 1.3.0):另一份计划。在它做完之前,agent 的定向发布只用于试发,不做全机队。
- **控制台直连网关源站**(2026-09-24 查明,暂不做):员工页不时报"无法读取网关模型清单 …/model/info: context deadline exceeded"。实测原因是**本机(阿里云 ECS)到 Cloudflare 边缘的线路丢包**:只打到边缘、不回源的 `/cdn-cgi/trace` 也会慢 1～7 秒,建连时间落在 1.05/3.17/7.13 秒(TCP SYN 重传);走 Cloudflare 的 `/model/info` 时快时慢(0.08 秒 ~ 30 秒超时),控制台给的上限是 20 秒。直连源站 `175.41.186.104:443` 8/8 都在 0.04 秒内。源站证书是 Cloudflare Origin CA 签的,公网不信任,但用 Cloudflare 公开的 Origin CA 根(`https://developers.cloudflare.com/ssl/static/origin_ca_rsa_root.pem`,SHA-256 `D3:C7:E8:5C:…:76:20`,到期 2029-08-15)按主机名 `litellm.teenet.app` 校验能通过。做法:`litellm.Client` 加一个"直连源站"选项(拨号改到源站地址、只对这个连接用该 CA、ServerName 仍是 `litellm.teenet.app`),配置走两个环境变量(如 `AIENVMGR_GATEWAY_ORIGIN`、`AIENVMGR_GATEWAY_CA_FILE`),控制台和 `ai-env-migrate` 都用;不改 `/etc/hosts`、不把该 CA 加进系统信任。另可加一层:模型清单缓存几分钟、失败时用上次成功的结果。员工云电脑上的 Codex 仍走 Cloudflare,不受影响。
- **agent:绑定变了要清掉前一个员工的本机凭据**(2026-09-24 发现):agent 只处理"当前绑定员工"的凭据——凭据对象消失时删本机文件、关 Codex。手动解绑或改绑给别人时,前一个员工的凭据文件和正在跑的 Codex 留在机器上。关户因此**不解绑**(吊销靠绑定送达),只让离线告警跳过离职员工的机器。修法在 agent:记住上次投递给了谁(credsmark 里已有 etag,加上用户),绑定对象里的用户变了就先对旧用户执行同样的删除和关进程。下一个 agent 版本做。
- KMS 主密钥(用户决定暂不做);
- 阶段 2:设备身份 + API,agent 1.3.x 双协议,之后停写 OSS 对象;
- 生产环境本身:阿里云 ECS + RDS PostgreSQL 15、三个库账号、实例角色。
