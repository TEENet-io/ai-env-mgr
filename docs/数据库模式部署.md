# 控制台数据库模式：部署与切换清单

> 2026-09-18。对应分支 `rds-phase0`。设计见 `docs/superpowers/specs/2026-09-12-rds-unified-control-plane-design.md`（rev.4），进度见 `docs/superpowers/plans/2026-09-12-rds-phase0-1.md`。

## 先认识几个词

| 词 | 意思 |
|---|---|
| 控制台 | 管理后台程序，可执行文件名是 `admin`。 |
| OSS 模式 | 原来的工作方式：控制台直接读写 OSS（阿里云对象存储）里的文件，机器上的 Agent 也从 OSS 读配置。 |
| 数据库模式 | 新的工作方式：数据存在 PostgreSQL 数据库（阿里云 RDS）里，OSS 里给机器读的文件由控制台根据数据库生成。 |
| Worker | 控制台进程里跑的后台任务执行器。页面上的操作先排成任务，由 Worker 去真正执行。 |
| 事务 | 数据库里"要么全部写成功、要么全部不写"的一组操作。 |
| 验证器 | 手机上生成 6 位动态码的应用（如 Google Authenticator），登录时的第二道验证。 |
| 信封加密 / 主密钥 | 库里的令牌和验证器种子用主密钥加密后保存。主密钥丢了，这些数据就再也解不开。 |
| AK / SK | 阿里云访问密钥（AccessKey ID / Secret），相当于程序的账号和密码。 |
| RAM 实例角色 | 阿里云给服务器（ECS）直接授予权限的方式，用了它就不用在服务器上存 AK/SK。 |
| SLS / Logtail | SLS 是阿里云日志服务；Logtail 是装在服务器上、把本机日志送到 SLS 的采集程序。 |
| 网关 | 员工调用 AI 模型时经过的中转服务（LiteLLM），员工的令牌在这里校验。 |
| 对账 | 定时比较"数据库里认为的状态"和"网关上的实际状态"，发现不一致就处理。 |
| `/healthz` | 健康检查地址，返回 `ok` 说明控制台活着、数据库连得上。 |

## 一句话说明

还是同一个 `admin` 程序，靠环境变量 `AIENVMGR_DB_DSN` 区分两种模式：

- **设了它，就是数据库模式。** 登录用"账号 + 验证器"；页面从数据库表读数据；每个操作是"一个事务 + 一条排队任务"；Worker 在控制台进程内运行；访问 OSS 和 SLS 用服务端自己的身份。
- **不设，就是原来的 OSS 模式**，行为完全不变。

## 环境变量

全部写在 systemd 的 `EnvironmentFile` 里，文件权限 600（只有属主能读写）。

| 变量 | 作用 |
|---|---|
| `AIENVMGR_DB_DSN` | 数据库连接串：`postgres://aienv_app:...@<rds 内网地址>:5432/aienv?sslmode=require`。**只要设了它，就启用数据库模式。** |
| `AIENVMGR_MASTER_KEY_FILE` | 主密钥文件的路径。文件只能 root 读写（0600）。生成方法：`umask 077; printf '{"current":"k1","keys":{"k1":"%s"}}\n' "$(openssl rand -base64 32)" > /etc/ai-env-mgr/master.key`。**要备份，而且备份放在数据库备份以外的地方**：没有它，库里所有令牌和验证器种子都解不开。 |
| `AIENVMGR_OSS_ACCESS_KEY_ID` / `_SECRET` | 服务端访问 OSS 用的 AK/SK（读写 `agent_workdir/`、`admin/`，读 SLS）。新 ECS 改用 RAM 实例角色后撤掉。 |
| `AIENVMGR_GATEWAY_URL` / `AIENVMGR_GATEWAY_ADMIN_KEY` | 和原来一样。注意 URL 必须是员工桌面能访问的公网地址（`https://litellm.teenet.app`），因为它会被写进每个人的 `config.toml`。 |
| `AIENVMGR_SLS_PROJECT` / `AIENVMGR_SLS_ENDPOINT` | 和原来一样。数据库模式下用上面那组服务端 AK 去读。 |
| `AIENVMGR_PUBLIC_HOST` | 验证器应用里显示的名字，填 `windows-control.teenet.app`。 |
| `AIENVMGR_FIRST_ADMIN_EMAIL` | 第一个管理员的邮箱（可以不填）。 |
| `AIENVMGR_WORKER` | **设为 `on` 才运行 Worker，默认关闭。** 原因：迁移期间数据库在一边导入一边比对，旧控制台也还在运行；这时如果 Worker 自己跑起来，就会开始改写机器正在读的 OSS 文件。 |

## 第一次启动

1. **建表。** 用数据库超级账号跑一次 `go run ./cmd/migrate up`（也可以直接启动控制台，它会自己做迁移）。三个数据库角色的密码要单独设置，例如 `alter role aienv_app login password '...'`，详见 `go/db/README.md`。
2. **首次登录。**
   1. 启动控制台。首次启动时，它会在主密钥所在目录写一个只有 root 能读的 `first-admin.txt`，里面是用户名和初始密码。这个文件内容**不会写进日志**，日志里只提示文件在哪。
   2. 用这个账号登录。页面会引导你绑定验证器，并显示十个恢复码。
   3. 在"我的账号"里改密码。
   4. **然后删掉 `first-admin.txt`。**
3. **健康检查。** 访问 `/healthz` 返回 `ok`，说明数据库连得上。Cloudflare 和 systemd 的健康检查都指向这个地址。

## 切换流程

一共四个阶段，每个阶段都写明了什么时候可以进入、出问题怎么退回。

三个命令都从 `/etc/ai-env-mgr/console.env` 读身份。其中 `import` 和 `compare` **不写 OSS，也不写网关**。

### A. 影子运行（现在就处在这个阶段，可以一直保持）

"影子运行"指新控制台跟着旧控制台跑，但不对外产生任何效果。

- 新控制台没有设 `AIENVMGR_WORKER`（等于关闭），只开在内网端口上。
- 随时可以运行 `ai-env-migrate import`（可以重复运行，不改 epoch、不发令牌）和 `ai-env-migrate compare`。
- 在新控制台里点任何按钮，都只是写进数据库和任务队列，**不会影响任何一台桌面**。
- 退回：什么都不用做。

### B. 停写（切换当天开始）

1. 停掉 AWS 上的旧控制台：`systemctl stop ai-env-mgr-admin`。从这一刻起，没有人能再改 OSS 里的文件；机器继续按现有文件正常运行。
2. 运行 `ai-env-migrate import`，把停写前最后的改动同步进数据库。
3. 运行 `ai-env-migrate compare`。**这一步是关卡**：
   - 退出码 0：没有差异，可以继续。
   - 退出码 2：有差异，要逐条看。预计只会剩两类差异：
     - 每个在用的员工都会显示"已经发过凭据，但库里没有令牌明文"。这在下一阶段处理。
     - 有人在网关上手工改过额度或白名单。要决定以哪边为准：改数据库；或者改网关，然后再导入一次。
- 退回：`systemctl start` 启动旧控制台即可。数据库里多出来的东西不影响它。

### C. 接管

4. 设 `AIENVMGR_WORKER=on`，重启新控制台。Worker 开始导入机器状态、投递审计日志。它**不会**主动改任何凭据文件，只有排了任务的员工才会被处理。
5. 在新控制台里，对比对结果点名的员工逐个点"重发"。Worker 会：
   - 在网关上发新令牌，同时作废旧的别名 `emp-<user>`；
   - 写新的 `credentials.zip`；
   - Agent 下一轮同步时换上新令牌，并把这名员工的 Codex 结束一次。
6. 再运行 `ai-env-migrate compare`，退出码为 0 就说明接管完成。从此数据库是唯一可信的数据来源，OSS 里的文件由 Worker 生成。
- 退回（做了第 5 步之后，退回就有代价）：关掉 Worker、启动旧控制台，**还要在旧控制台里把已经重发过的员工再重发一次**。因为这些员工机器上已经是新令牌，旧控制台不认识。所以，第 5 步之前一定要把比对结果看干净。

### D. 收尾

7. 在 Cloudflare 把 `windows-control.teenet.app` 指到新机器。nginx 用现有的源站证书，把请求转发到 `127.0.0.1:8090`。
8. 作废旧控制台用过的 AK。给控制台新建一把权限最小的 AK：只能读写 `agent_workdir/`、`admin/`，只读 SLS。或者改用 RAM 实例角色（见"还没做的"）。
9. 发布不带 Claude 的新版 Agent。

## 运行中需要知道的事

- **后台任务**（告警 › 后台任务页签）：能看到每个操作排出的任务、失败原因和重试次数；还有"立即对账网关"按钮。被判定为永久失败（400 类错误）的任务不会再重试，需要人去看。
- **对账** 每小时自动运行。如果发现某个令牌"我们以为已经作废了，网关却还在让它用"，会直接把它删掉，并在日志里记一条 `gateway_drift`。
- **审计投递** 每分钟把审计记录写到本机的审计日志流，由 Logtail 采走。五分钟后再去 SLS 按 event_id 查一遍确认。查不到的会一直留在"待确认"列表，不会默认算成功。
- **机器状态** 每分钟从 OSS 的 `_status/` 导入，Agent 那边的通信方式不变。导入后，根据机器的报告结算这台设备的发布目标（见 `OSS布局.md` §7.1）。
- **Logtail 只采 12 小时以内的日志。** 因此：
  - 从旧控制台导入的历史审计不会再被采集。它们当年已经由旧控制台送过（用的是旧 id），回查时标为"已由旧控制台归档"。
  - 新产生的审计正常送达、正常确认。
  - 这台服务器必须加入 SLS 项目 `windows-control-logs` 的机器组（自定义标识 `wc-gateway`，写在 `/etc/ilogtail/user_defined_id`）。
- **发布** 在 `/releases` 页面：可以设为全局，也可以指定给某些机器（机器页也能改）。流程见 `操作手册.md` §4.7。Worker 每天扫描一次 OSS 的 `_codex/`、`_agent/` 目录（页面上也有"立即扫描 OSS"按钮）。CI 传上来的安装包会自动算出 SHA-256 并列出来。读取失败的文件，在控制台重启前不会再读。
- **定时任务**（都能在任务页看到；阈值、通知渠道、令牌轮换在设置页调整，见 `操作手册.md` §4.8）：
  - 用量快照：每天 UTC 0:30，从 SLS 的 `audit` 日志库汇总前三天的 `llm_call`（模型调用记录），写进 `usage_daily` 表；
  - 告警规则：每 10 分钟；
  - 通知投递：每分钟；
  - 令牌轮换：每天 UTC 1:00（默认关闭）。
- **升级控制台**：在本机的代码目录里运行 `sudo dist/deploy/deploy-console.sh`。有未提交的改动时它会拒绝执行，加 `--dirty` 才放行。它按顺序做这些事：
  1. 编译。
  2. 用表的属主账号（配置在 `/etc/ai-env-mgr/migrate.env`，权限 600，只含 `AIENVMGR_DB_DSN`）检查有没有待执行的数据库迁移。有的话，先把整个库导出备份到 `/var/backups/ai-env-mgr/`，再执行迁移。**迁移失败就停下，什么都不替换。**
  3. 把旧程序留作 `.prev`，装上新程序，重启。
  4. 30 秒内 `/healthz` 不通，就自动换回 `.prev`。注意数据库迁移不会自动回退；要回退迁移用 `ai-env-migrate down`，由人决定。

  为什么要用属主账号：控制台平时用的 `aienv_app` 不是表的属主，改不了表结构。而控制台发现有没执行的迁移时，会拒绝启动。
- **换主密钥**：`ai-env-migrate rekey`，见 `操作手册.md` §4.10。
- **设备 API**：地址是 `/agent/v1/*`。Agent 从 1.3.0 版起直接连控制台（注册时只报主机名，设备令牌的哈希存在 `device_tokens` 表）。过渡期开关在"设置 › 设备通道"。见 `操作手册.md` §4.9。
- **每晚备份**：`ai-env-backup.timer` 在 UTC 2:00 运行 `/usr/local/sbin/ai-env-backup.sh`。流程是：在容器里 `pg_dump` 导出 → gzip 压缩 → 用 `ai-env-admin backup` 上传到 `agent_workdir/_backup/aienv-<日期>.sql.gz`，保留 30 天。相关的 systemd 单元文件在 `dist/backup/`。

## 还没做的

- **RAM 实例角色。** 代码目前只支持固定的 AK/SK。要改用实例角色，需要接入 STS 临时凭证并自动刷新，还得在 ECS 的元数据服务上实际测试。在那之前，AK 继续放在权限 600 的环境文件里。
- **Agent 独立更新器和启动失败自动恢复**（设计稿 §5，Agent 1.3.0）。这是另一份计划。它做完之前，Agent 的定向发布只用来试发，不推给全部机器。
- **控制台直连网关源站**（2026-09-24 查明原因，暂时不做）。
  - 现象：员工页时不时报"无法读取网关模型清单 …/model/info: context deadline exceeded"（意思是请求网关的模型列表超时了）。
  - 原因：实测是**本机（阿里云 ECS）到 Cloudflare 边缘节点的线路丢包**。
    - 只到边缘、不回源站的 `/cdn-cgi/trace` 也会慢 1～7 秒，建立连接的时间落在 1.05/3.17/7.13 秒（说明 TCP SYN 包在重传）。
    - 经过 Cloudflare 的 `/model/info` 时快时慢，从 0.08 秒到 30 秒超时都有；而控制台设的上限是 20 秒。
    - 直连源站 `175.41.186.104:443`，8 次都在 0.04 秒内。
  - 证书：源站证书由 Cloudflare Origin CA 签发，公网不信任。但用 Cloudflare 公开的 Origin CA 根证书（`https://developers.cloudflare.com/ssl/static/origin_ca_rsa_root.pem`，SHA-256 `D3:C7:E8:5C:…:76:20`，2029-08-15 到期）按主机名 `litellm.teenet.app` 校验，可以通过。
  - 做法：
    - 给 `litellm.Client` 加一个"直连源站"选项：连接地址改成源站地址，只对这个连接使用该 CA，ServerName 仍然是 `litellm.teenet.app`。
    - 配置走两个环境变量（例如 `AIENVMGR_GATEWAY_ORIGIN`、`AIENVMGR_GATEWAY_CA_FILE`），控制台和 `ai-env-migrate` 都用。
    - 不改 `/etc/hosts`，也不把这个 CA 加进系统信任列表。
    - 还可以再加一层：模型清单缓存几分钟，请求失败时用上一次成功的结果。
  - 员工云电脑上的 Codex 仍然走 Cloudflare，不受影响。
- ~~Agent：绑定关系变了，要清掉前一个员工留在本机的凭据~~ **不做**（2026-09-24 决定）。
  - 现状：Agent 只处理"当前绑定员工"的凭据。手动解绑或改绑后，前一个员工的凭据文件会留在机器上。
  - 为什么可以不做：
    - 机器换人时要在阿里云新建用户。旧文件在前一个员工自己的 Windows 用户目录里，新用户（标准用户，没有管理员权限）读不到。
    - 员工离职时，令牌已经在网关作废；云电脑实例满 7 天后连同数据一起释放。
  - 关户时仍然**不解绑**，因为作废凭据要靠绑定关系才能送到机器上。
  - 员工换了机器但没离职时，在员工页点"重发令牌"，让旧机器上的令牌作废。
- KMS 托管主密钥（用户决定暂时不做）。
- 阶段 2：设备身份 + 设备 API；Agent 1.3.x 同时支持新旧两种通信方式；之后停止写 OSS 文件。
- 生产环境本身：阿里云 ECS + RDS PostgreSQL 15、三个数据库账号、实例角色。
