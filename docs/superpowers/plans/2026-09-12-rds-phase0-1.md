# RDS 升级 阶段 0 与阶段 1 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把 windows-control 的业务状态(员工、额度、绑定、策略、任务、审计)从 OSS 整文件搬进 RDS PostgreSQL,控制台改为自管管理员账号登录,所有云资源访问改为服务端身份;旧 Agent 继续通过 Worker 导出的 OSS 兼容对象工作。

**Architecture:** 现有 `admincore.Manager` 保留为业务门面,底下的 `store`(OSS 对象读改写)被拆成按实体的仓储接口,新实现走 `database/sql` + PostgreSQL 事务;业务写入与持久任务(`tasks` 表)同事务提交,Worker 在同一进程内领取任务执行网关调用、OSS 兼容导出和审计副本投递。控制台登录改为 `admin_principals`(密码哈希 + TOTP),会话不再持有云 AK;OSS/SLS/KMS 通过实例角色(迁账号前为环境注入的受限 AK)。旧 Agent 的 OSS 协议(策略、绑定、凭据、状态)不变,由 Worker 从 RDS 生成。

**Tech Stack:** Go 1.25,PostgreSQL 15(RDS,新加坡),`github.com/jackc/pgx/v5`(驱动 + 连接池),`golang-migrate`(仅 CLI,迁移文件为纯 SQL),`golang.org/x/crypto/argon2`(密码哈希),`github.com/pquerna/otp`(TOTP),阿里云 KMS(信封加密,迁账号后),现有 `litellm`、`ossclient`、`slsclient`、`eventlog` 包。

**Spec:** `docs/superpowers/specs/2026-09-12-rds-unified-control-plane-design.md`(= `架构_RDS升级与统一控制面_2026-09.md` rev.3)。本计划覆盖 spec §11 阶段 0 和阶段 1;阶段 2(Agent 走 API、设备身份、可靠采集)另写计划。

## Global Constraints

- 业务变更与持久任务同事务提交(spec §6.1);任务至少一次交付,幂等键唯一(§6.2);网关调用结果不确定时先查询对账再重试(§6.3)。
- 读取失败区分"不存在 / 不可用 / 损坏",失败时禁止基于空值覆盖(§2)。
- 管理员会话不携带任何云 AccessKey;OSS、SLS、KMS 用该 ECS 的 RAM 实例角色(spec rev.4 §0);网关管理密钥仍走 systemd 环境变量。
- 秘密:服务级用 systemd 环境变量;按行秘密(员工令牌密文、TOTP 种子、恢复码、webhook)信封加密存 RDS,主密钥来自 `AIENVMGR_MASTER_KEY_FILE`(root 专属文件)或 KMS(§13 已定);明文不进日志、审计、错误信息。
- 金额定点存储 `numeric(12,6)`,不用浮点(§4.2)。
- 稳定 ID:员工、设备用 UUID;Windows 用户名小写、唯一,但不是员工身份(§4.2)。
- 审计只追加(应用账号无 UPDATE/DELETE 权限),事件 ID 与 SLS 副本一致(§4.2、§9.4)。
- 旧 Agent 的 OSS 对象格式与 key 不变:`agent_workdir/policy.json`、`_bindings/<machine>`、`<user>/credentials.zip`、`_status/<machine>`;RDS 是权威,OSS 是兼容输出(§11 阶段 1)。
- 阶段 1 期间旧 admin 二进制只读或停用,不允许双写入口(§11 阶段 1 第 4 步)。
- 任何阶段都不删旧字段、不切 Agent 协议、不撤销旧 OSS 密钥(§11 回滚规则)。
- 数据库账号分离:`aienv_app`(运行,审计表只 INSERT/SELECT)、`aienv_migrate`(DDL)、`aienv_ro`(查询)。

**写代码时发现并修掉的真问题**(记下来,免得回归):

1. 导出任务的幂等键原来是"员工 + epoch",而绑机器不改 epoch,键命中开户时那个**已完成**的任务,新绑定永远不会被写出去;"重启 Codex"按第二次同样失效。现在导出键带会变的标记,机器有设备级导出。
2. Worker 用自己的 context 记录任务结果,关停时刚做完的活会丢(任务卡在 running,一小时后被重跑)。改为用不受取消影响的 context 记结果。
3. `Credentials.Store` 原本想在一条语句里"退役旧的 + 插新的",会同时撞上部分唯一索引,必须分两条且退役在前。
4. 机器名唯一约束按原样大小写,`DESKTOP-01` 和 `desktop-01` 会变成两台机器、两份凭据发到同一张桌子上(迁移 0003 改成 `lower(hostname)` 唯一)。

## 2026-09-18 决定:Agent 改走 API,OSS 退回文件通道

用户决定阶段 2 提前,Agent 不再通过 OSS 对象接收控制指令,改为直接 POST 到控制台 API,每台机器一个设备身份。原因不只是优雅:现行 Agent 的 RAM 授权里有 `agent_workdir/*/credentials.zip` 这一行,**全机队共用的那把内嵌 key 能读到任何员工的凭据包**,而且无法单台吊销。

据此调整:

- **大文件永远留在 OSS**(Codex 安装包、agent 二进制、采集数据):API 只返回短时效签名 URL,字节仍直连 OSS。不走 API 代理——Cloudflare 有 100 MB 请求体上限,控制台主机也只有 2C4G。
- **Task 1.6 降级**:从"OSS 兼容导出器(长期双写)"改为"临时兼容写",复用 admincore 现有的对象写入代码,Worker 定期从库生成那四类对象。窗口长度由最慢的一台机器决定(有人休假关机两周,就是两周),全机队报到新版本后即可删除。
- **Agent 1.3.x 双协议**:先试 API,失败回落 OSS。新协议在无影云电脑上走不通时(出网策略、Cloudflare 那一跳),修它的唯一通道就是那个刚坏掉的 agent,所以回落是必须的一版成本。确认全机队正常用 API 后,1.4.x 再去掉 OSS 那条腿。
- **前置条件**:无影云电脑必须能出网到 `windows-control.teenet.app`。用户 2026-09-18 确认会开通。
- 升级通道仍是 policy 对象里的 `agentUpdateVersion` + SHA256,自更新机制不变,不需要手工碰机器。
