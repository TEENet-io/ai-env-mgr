# Agent 与 Codex 发布流程及功能改造

> 状态：待审阅设计稿，不代表功能已经实现或生产发布已完成。  
> 日期：2026-09-18  
> 范围：windows-control 后台、Windows Agent 自更新、企业版 Codex 安装与回滚。  
> 现状依据：`ai-env-mgr` 中的发布、更新及 Windows 服务重启实现。本次仅整理方案，不修改代码或部署。

## 1. 建议与目标

保留现有后台更新能力，补齐「指定机器试发、版本库、发布记录、设备结果确认」，并为 Agent 增加启动失败恢复能力。Codex 大包传输同步改为流式处理。

发布流程统一为：

**构建候选包 → 固定测试机验收 → 后台指定机器试发 → 人工扩大范围 → 观察结果 → 完成或回滚。**

构建成功、上传成功、安装成功、业务可用是不同的状态，不能相互替代。正常升级应保留员工配置、会话与业务文件。

第一期暂不做百分比灰度、多级审批、自动定时发布或根据失败率自动回滚全机队。小规模机队直接选择具体设备，更容易观察和处理问题。

## 2. 当前能力与缺口

| 项目 | 当前实现 | 本次改造 |
|---|---|---|
| 发布范围 | Agent、Codex 都通过全局策略发布；新 Agent 不再执行 Codex 百分比灰度 | 按指定设备试发，随后人工扩大范围 |
| 上传与发布 | 后台获取包、上传 OSS 后直接更新全局目标 | 上传只生成候选版本，下发是独立动作 |
| 文件校验 | 下载后校验策略中的 SHA256 | 保留校验；同一版本固定对应同一制品，拒绝不同内容覆盖 |
| 历史版本 | Codex 按版本路径存储；Agent 使用固定二进制路径 | 两者都按版本保存，提供历史版本选择 |
| 取消发布 | 清除全局目标；已安装设备不恢复旧版 | 按发布任务暂停后续下发，明确在途任务状态 |
| Codex 安装 | 进程运行或磁盘空间不足时延后；安装或校验失败有版本标记防止反复尝试 | 保留延后行为，明确原因及显式重试入口 |
| Agent 更新 | 替换程序并重启服务，保留 `agent.exe.old` | 独立更新器确认启动结果，失败恢复旧版 |
| 发布完成判定 | 有版本、状态上报，但缺少完整的设备发布任务与健康确认 | 记录每台设备的安装结果、实际版本及更新后的健康上报 |
| Codex 大包 | 后台下载仍整包读入内存 | 流式下载、校验、上传，限制资源占用 |

SHA256 用于检查文件内容是否与发布记录一致，不等同于制品签名。签名发布按整体架构的后续阶段实施，本期不将其描述为已具备。

## 3. 标准发布流程

### 3.1 构建候选版本

从确定的 Git 提交构建，生成安装包、SHA256 与变更说明。记录：

- 产品：Agent 或 Codex。
- 完整版本号、Git 提交、构建来源、文件大小和 SHA256。
- 最低兼容 Agent 版本，以及已验证的 Agent / Codex 版本组合。
- 本次影响、已知限制、上一稳定版本和回滚条件。

候选包上传到版本库后，不自动改变任何设备的目标版本。同一版本号不允许换包；重新构建且内容不同，应使用新版本号。

### 3.2 固定 Windows 测试机验收

保留至少一台与员工环境一致的测试机，使用普通员工账户验证。首次接入新发布机制时允许手动安装；机制具备后，必须补测真实后台升级链路。

| 产品 | 必测内容 |
|---|---|
| Agent | 服务启动与系统重启后自启、状态上报、绑定和策略同步、凭据投递、更新任务执行、失败恢复旧版 |
| Codex | 普通员工启动、网关模型调用、改文件和执行命令、功能屏蔽、AppLocker 兼容、配置和会话保留 |
| Codex 更新行为 | 正在使用时延后、退出后安装、磁盘不足延后、SHA256 不符拒装、安装失败停止循环尝试 |
| 两者共同项 | 从上一稳定版升级、回滚到上一稳定版、升级后实际版本核对 |

验收结果关联到具体版本与 SHA256。包内容变化后，原验收结果不能直接沿用。

### 3.3 后台试发与扩大范围

1. 选择候选版本及 1～2 台试发设备。
2. 后台预览实际设备名单、当前版本、兼容性和离线状态。
3. 创建发布任务，仅选中的设备获得该目标。
4. 验证设备更新后正常上报，并在试发机完成真实工作任务；建议至少观察一个正常工作日，紧急修复可缩短，但需记录实际观察范围。
5. 人工选择其余设备，扩大同一版本的发布范围。

扩大范围必须是显式动作，不因到时或测试机安装成功而自动发生。发布范围保存为设备快照，之后新增的设备不自动加入旧任务。

Agent 与 Codex 分别发布。如果 Codex 依赖新版 Agent，先升级 Agent 并确认稳定，再发布 Codex。后台应阻止向不满足最低版本条件的设备下发安装任务。

### 3.4 观察与收尾

设备更新完成后，核对实际版本及更新后的正常上报。试发阶段另做业务验收，不能仅凭后台状态判断功能全部正常。

离线设备保持待完成，不能计入成功。对于长期离线或停用设备，管理员可明确移出范围，并记录原因。

完成条件：任务内设备全部成功，或未完成设备已逐台排除并说明原因；报告分别展示成功、失败和排除数量，不将排除算成成功。

旧包与对应恢复说明至少保留当前稳定版及前两个稳定版；仍被设备、活动任务或回滚记录引用的制品不得清理。

## 4. 后台需要增加的功能

### 4.1 版本库

同一页面区分 Agent 与 Codex，展示版本、变更说明、SHA256、大小、兼容要求及验收记录。版本可标记为「候选」「已验收」「稳定」「停用」。

允许上传候选、登记验收、选择版本创建发布、选择旧版创建回滚。停用版本禁止新下发，但保留历史记录。版本库记录本身不触发设备安装。

### 4.2 发布任务与设备进度

每次发布记录操作者、时间、版本、目标设备、验收依据和回滚版本。页面展示汇总及设备明细：

| 设备状态 | 含义 |
|---|---|
| 待执行 | 目标已建立，设备尚未开始；单独显示在线、离线及最后联系时间 |
| 延后 | 当前不适合安装，记录正在使用、磁盘不足等具体原因 |
| 下载中 / 安装中 | 正在执行对应步骤 |
| 待健康确认 | 安装器已结束，等待目标版本及后续正常运行证据 |
| 成功 | 实际版本匹配，且更新后正常上报；不代替人工业务验收 |
| 失败 | 校验、安装或健康确认失败，保留错误及尝试次数 |
| 已取消 / 已取代 | 尚未执行的目标被取消，或已有更高代次的目标 |
| 已恢复旧版 | Agent 自动恢复成功；本次升级仍记为失败 |

同一设备、同一产品只允许一个有效目标。更新或回滚创建新的任务代次，旧回执不能覆盖新任务状态。失败重试需要显式动作，记录新的尝试，不依赖反复修改版本号。

### 4.3 暂停与回滚

暂停阻止尚未开始的设备继续更新。已经进入安装阶段的任务不强行杀死，继续上报最终结果；需要恢复时再执行回滚。

回滚作为一条新的发布任务，预览需回退的设备及目标旧版，保留原任务历史。支持选择已存储旧包，无需管理员重新上传。

不是所有版本都天然支持降级。制品记录需标明已验证的回滚版本；涉及不可逆配置或数据格式变化时，先给出恢复方案，不能仅修改目标版本就宣称可回滚。

## 5. Agent 启动失败恢复

这是 Agent 全量发布前的关键保护。更新器需独立于待替换的 Agent 进程运行，并保留本次升级前可启动的旧文件。

建议执行顺序：校验并准备新文件 → 保留旧版 → 停止服务并等待退出 → 替换 → 启动新服务 → 检查实际版本及本地健康信号。

如果新服务启动失败，或在约定期限内未给出有效本地健康信号，更新器恢复旧版并重新启动。恢复结果写入本地持久记录，由恢复后的 Agent 补报。

本地健康检查应覆盖服务初始化与核心循环进入正常运行。网络故障导致后台暂时收不到上报时，标为待确认，不单凭远端心跳缺失触发自动回退。磁盘损坏、旧版也无法启动等情形仍需独立远程运维或人工恢复。

该能力先在测试机演练启动崩溃、文件占用、服务停止超时、机器重启和恢复失败，再用于全量更新。

## 6. 大包传输

Codex 包从来源下载到受限临时文件，边下载边计算 SHA256，再流式上传 OSS。记录传输进度，限制并发、文件大小及磁盘用量；失败后清理本次临时文件。

只有制品完整上传并核对成功后，才能进入可下发状态。候选包准备失败不得改动设备目标，也不能影响正在使用的稳定版本。

第一期优先解决整包占用内存和失败清理；断点续传可随后补充。

## 7. 与 RDS 改造的衔接及旧 Agent 过渡

RDS 保存版本元数据、发布任务、设备目标、尝试结果和审计；OSS 保存二进制制品。沿用现有持久任务和 Worker 机制，避免另建一套发布调度系统。

现有旧 Agent 只理解全局更新策略，因此仅给后台增加设备选择框，不能实现真正的定向发布。需要明确分两步：

1. 先完成版本库、发布记录与大包传输；旧 Agent 继续使用现有全局发布方式，页面明确提示影响范围。试验包不得写入全局目标。
2. 新 Agent 实现设备目标与任务回执协议，按整体架构接入统一 API 和独立设备身份；经过试点后，再启用后台定向发布。

首版具备新协议及恢复能力的 Agent，先在测试机手动安装验收，再通过旧机制受控升级，或逐机安装。旧 Agent 替换成首个新版时，仍由旧更新逻辑执行，不能声称这一步已受新版自动恢复保护。

每台设备明确使用旧全局通道或新设备目标通道，禁止同时接受两套目标。新通道暂时不可用时不得自动回退到旧全局策略。迁移完成后再退出旧协议。

## 8. 实施顺序与验收标准

| 顺序 | 交付项 | 验收标准 |
|---|---|---|
| 1 | 版本库、候选与下发分离、Agent 按版本存储、Codex 流式传输 | 上传候选不改变设备；不同内容不能覆盖同版本；大包不整包驻留内存 |
| 2 | 发布任务、设备目标、回执与新 Agent 协议 | 只选 A 时 B 不更新；离线不误报成功；旧回执不能覆盖新目标 |
| 3 | Agent 独立更新器与失败恢复 | 故意使新 Agent 启动失败，旧版能恢复并补报结果 |
| 4 | 试发、扩大范围、暂停、回滚与完整验收 | 经后台走通两个产品的升级与回滚；配置、会话、业务数据保留 |

第一期定向发布正式投入全机队使用前，上述四项都需通过验收。完整流程的证据应记录设备、版本、动作、实际结果与失败原因。

建议优先按此范围实施；百分比灰度、自动定时发布、多级审批、签名发布及复杂渠道管理另行排期。
