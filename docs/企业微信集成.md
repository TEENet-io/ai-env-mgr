# 企业微信集成调研

> 面向：客户 IT 管理员 / 开发
> 目的：把告警接入企业微信；进一步，评估把 `admin` 做成企业微信机器人的可行性、架构与安全边界。

---

## 0. 术语澄清

客户说的"**微信企业版**"就是现在的 **企业微信（WeCom / WeChat Work）**——老的"微信企业号"已并入企业微信。

> ⚠️ **前提**：客户得已经在用**企业微信**。**个人微信 / 普通微信群没有官方机器人 API**，只能通过企业微信实现。若客户目前只有个人微信群，第一步是开通企业微信。

本方案分两块：**① 通知（简单，先做）**、**② admin 做成双向机器人（进一步，要加固）**。

---

## 1. 通知接入：群机器人 Webhook（最省事）

企业微信每个内部群都能加一个**自定义群机器人**，得到一个 **Webhook URL**；服务端往这个 URL **POST 一段 JSON** 就把消息发进群，**无需注册应用、无需 access_token**。

- **消息类型**：`text`、`markdown` / `markdown_v2`、`image`、`news`（图文）、`file`、`template_card`（模板卡片）。告警用 markdown 最合适（可加粗、变色、@人）。
- **频率限制**：群机器人约 **20 条/分钟**，超了会被限流 → 高频告警必须**聚合**（例如把"3 台 OFFLINE"合成一条，别一台一条）。
- **方向**：基本**单向出站**（服务端推给群），**收不了消息**。

### 与本系统的契合点

一个小常驻程序定时跑 `admin status`（复用现有 `admincore`），把这些事件推到企业微信群：

- 机器 `STALE` / `NO REPORT`（可能真挂了）
- 凭据过期、离职未处理（`DISABLED USER`）
- `EXTRA USERS`（计划外账户）
- agent 自更新进度（AGENT 版本一台台翻新）

**只读、低风险，半天可做**。这是客户"接入企业微信做通知"的最短路径。

> ⚠️ **Webhook URL 本身就是 bearer 密钥**：谁拿到谁能往群里发消息。别提交进仓库、别外发、别贴聊天记录长期留存。

### 消息示例（markdown）

```jsonc
// POST 到 https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=<KEY>
{
  "msgtype": "markdown",
  "markdown": {
    "content": "**AI Env Mgr 巡检告警**\n> 2 台需要关注：\n> - `DESKTOP-B` STALE（静默 4 天）\n> - `DESKTOP-D` NO REPORT\n<@zhangsan>"
  }
}
```

## 2. admin 做成企业微信机器人（双向）

群机器人**收不了消息**，所以"对它发指令 → 它执行并回复"这种**双向机器人**要走另一条路。

### 2.1 两种实现

1. **自建应用 + 接收消息回调（经典做法）**
   - 在企业微信管理后台建**自建应用**，拿到 **CorpID / AgentID / Secret**；配置**回调 URL + Token + EncodingAESKey**。
   - 用户在企业微信里给应用发消息 → 企业微信把消息（**AES 加密**）POST 到回调服务器 → 服务端**解密、解析指令、执行、回复**（被动回复，或用 `access_token` 主动发）。
   - `access_token` 有效期 **2 小时，必须缓存**，别每条消息都重新取（会触发限流）。
   - 回调 URL 首次配置时，企业微信会发一个 GET 带签名+密文来**验证**，服务端要验签并返回解密后的明文才算通过。
2. **智能机器人（长连接）**：企业微信较新的能力，机器人可在群里收 @ 消息、走长连接接收，也能双向。可作备选。

### 2.2 架构：机器人 = admincore 的又一个前端

现有 `admin` 已经是 `admincore`（`CollectMachines` / `FetchLog` / `PublishAgentUpdate` …）之上的一个前端（CLI + TUI）。**机器人只是再加一个前端**——一个 `botserver`：收企业微信回调 → 映射到 `admincore` 调用 → 回消息。**不是重写，是加壳。**

```
企业微信消息  →  botserver（验签+解密+白名单）  →  admincore  →  回复
   "status"                                      CollectMachines
   "log <主机名>"                                 FetchLog
   "machine list"                                CollectMachines(bound)
```

## 3. 安全（重点）

**`admin` 里编译着全 Bucket 读写密钥**。做成机器人 = 这把密钥所在的服务变成一个**公网可达（企业微信要回调）+ 能执行管理操作**的高价值目标。必须：

- **回调服务公网 HTTPS 可达** → 它持有全桶 RW 密钥，要单独加固：独立小机器、最小权限、审计日志。
- **校验来源**：验 `msg_signature`，确保只有企业微信能调回调。
- **白名单**：只有指定管理员的 `FromUserName`（userid）才能发指令，其余一律拒绝。
- **读写分级**：
  - **只读**（`status` / `log` / `list`）走机器人**安全**；
  - **破坏性/敏感**（`forget` / `disable` / `publish`）**建议不开放给机器人**，继续留 TUI/CLI，或至少"二次确认 + 审计 + 双人"。
- **`login`（代员工登录）是交互式粘贴流程，天然不适合机器人**，不要放进去。
- **审计**：每条指令记录 who / when / what。

---

## 4. 分期建议

| 期 | 做什么 | 风险 | 工作量 |
|---|---|---|---|
| **P1** | 群机器人**只读告警**（status 巡检 → 推群） | 低 | 半天 |
| **P2** | 自建应用回调，**只读查询机器人**（status/log/list，白名单管理员） | 中（需公网回调） | 2–3 天 |
| **P3（可选）** | 开放**写操作**（publish/forget…），强管控 | 高 | 谨慎评估，建议先不做 |

**P1 即满足"接入企业微信做通知"的核心诉求**；机器人是"更进一步"，按 P2 递进。

---

## 5. 落地要客户企业微信侧提供什么

- **P1**：一个内部群 + 群机器人的 **Webhook URL**（管理员在企业微信里点几下就有）。
- **P2**：管理员建**自建应用**，提供 **CorpID / AgentID / Secret / 回调 Token / EncodingAESKey**，以及一个**公网 HTTPS 域名**放回调服务。
