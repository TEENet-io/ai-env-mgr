# AI Env Mgr 架构说明（Go 双二进制 · OSS 配置中心）

> 版本：2026-09 · 给谁看：做方案设计和实施的同事
> 适用场景：**阿里云无影共享型云电脑，多台，文件系统相互隔离，无 AD 域**

---

## 先认识几个词

| 词 | 意思 |
|---|---|
| 二进制 / exe | 编译好、可以直接运行的程序文件。本系统有两个：`agent.exe` 和 `admin.exe`。 |
| Agent（`agent.exe`） | 装在每台云电脑上的后台程序，负责拉取配置、写入策略、投递凭据、上报状态。 |
| Admin 控制台 | 管理员使用的管理后台（网页 + 接口），数据存在 PostgreSQL 数据库里。 |
| OSS | 阿里云的对象存储，可以理解为云上的文件仓库。Bucket 是其中的一个"仓库"，前缀相当于文件夹路径。 |
| RAM | 阿里云的访问权限管理。RAM 策略规定一把密钥能读写哪些路径。 |
| AK/SK | 阿里云的访问密钥（AccessKey ID / Secret），程序凭它访问 OSS。 |
| 设备 token | 每台云电脑独有的访问凭证。新版 Agent 用它访问 Admin 接口，不再带 AK/SK。 |
| AD 域 / GPO | Windows 企业里集中管理电脑的方式。GPO（组策略）可以统一下发设置。本场景没有 AD 域，所以用不了 GPO。 |
| HKLM | Windows 注册表里对整台机器生效的部分。浏览器的封禁策略写在这里。 |
| profile | Windows 用户的个人目录，例如 `C:\Users\work1`。 |
| ACL | 文件的访问权限列表，规定谁能读写这个文件。 |
| SYSTEM | Windows 里权限最高的系统账号。Agent 以这个身份运行。 |
| AppLocker | Windows 自带的程序白名单。不在名单里的程序不能运行。 |
| LiteLLM 网关 | 员工调用 AI 模型时经过的中转服务。 |
| ETag | OSS 给每个文件算的版本标识。ETag 没变，说明文件没变，可以跳过下载。 |
| 租约 | Agent 领取任务时拿到的"占用期限"。期限内任务归它；过期没完成，Admin 可以把任务重新派给别人。 |
| worker | Agent 里专门干重活（下载、安装）的后台执行单元，和主循环分开。 |
| 长轮询 | Agent 向服务器发一个请求并保持等待，服务器有新指令时立刻返回。比定时询问更及时。 |
| marker | Agent 在本机留下的记录文件，记着上次投递了什么、执行过哪条指令。 |
| nonce | 一个随机值，用来标记"这是哪一次指令"，保证同一条指令只执行一次。 |
| MSIX | Windows 的一种应用安装包格式。ChatGPT 桌面应用就是 MSIX 包。 |

## 近期变更

> **2026-09-18**：Claude Code 已从本系统移除。
> - 控制台不再投递或采集 Claude 相关文件。
> - `users.json` 里的 `claudeAccount` 字段、归档里的 `claude/*` 条目会被忽略，并在下次投递时删掉。
> - `claude.ai` 和 `anthropic.com` 仍在封禁名单里。

> **2026-09-25**：软件安装任务的整个生命周期改由 Admin 和 PostgreSQL 管理。
> - OSS 只保存安装包和清单，这些文件上传后不再修改。
> - Agent 通过带租约的接口领取任务，在独立的 worker 里执行，并回报进度、成功、失败或取消。
> - Agent 主循环只负责心跳、长轮询和控制，不会因为下载或安装而卡住。
> - 新版 Agent（通过接口工作的版本，下文称 API Agent）不再读取 OSS 上旧的 `MachineApplications` 安装计划。这样已取消的任务不会被重新执行。

## 1. 背景与约束

### 1.1 场景

| 约束 | 影响 |
|---|---|
| 多台云电脑（≥2） | 不能只在一台机器上解决，需要跨机器分发 |
| 文件系统相互隔离 | 在一台上装好，不代表其他机器也有 |
| 无 AD 域 | 不能用组策略（GPO）集中下发 |
| 员工为标准用户 | 员工没有管理员权限，自己解除不了管控 |

### 1.2 设计目标

- 多台云电脑配置一致
- 封禁策略可以随时更新，不用重做镜像，也不用一台台操作
- 员工访问 AI 模型一律走 LiteLLM 网关，密钥在入职时发放
- 不保存任何用户密码
- 管理员能看到所有机器的运行状态

## 2. 整体架构

```
┌───────────────────────────────────────────────┐
│  管理员工作机                                   │
│  Admin 控制台（PostgreSQL + HTTPS API）           │
│    add-site        增删封禁域名                  │
│    disable-block   临时全局开放                  │
│    status          查看所有机器状态               │
└────────────────────┬──────────────────────────┘
                     │ HTTPS（公网 endpoint）
                     ↓
┌───────────────────────────────────────────────┐
│  Admin 控制台 + PostgreSQL                       │
│    策略、绑定、凭据、发布记录和安装任务生命周期    │
│    Agent 任务租约、取消、重试、进度和审计          │
├────────────────────┬──────────────────────────┤
│  OSS 私有 Bucket     │ 只保存策略兼容对象、凭据归档 │
│  安装包/清单         │ 和不可变安装包              │
└────────────────────┬──────────────────────────┘
                     │ HTTPS（内网 endpoint）
                     ↓
┌───────────────────────────────────────────────┐
│  共享型云电脑 × N 台                             │
│                                                │
│  [镜像固化]                                     │
│    · Codex（C:\Tools）                           │
│    · ChatGPT 桌面应用（整机预置）                 │
│    · AppLocker 规则                             │
│    · agent.exe（仅持有本机设备 token）             │
│                                                │
│  [agent.exe] Windows 服务，开机自启                │
│    1. 用主机名查绑定 → 得知服务哪个员工            │
│    2. 拉全局 policy.json       → 写 HKLM 浏览器策略  │
│    3. 拉该员工 credentials.zip → 投递到其 profile   │
│    4. 主循环维持心跳、长轮询和控制                 │
│    5. 独立 worker 领取任务、下载、安装并回报        │
│                                                │
│  [用户会话]                                     │
│    · 首次登录自动装 ChatGPT 应用（镜像预置）       │
│    · AI 工具已是登录态，直接可用                   │
└───────────────────────────────────────────────┘
```

图中几个说法：
- "镜像固化"：这些东西做进云电脑的系统镜像里，用这个镜像创建的每台机器都自带。
- "绑定"：管理员指定某台机器归哪个员工用。
- "公网 / 内网 endpoint"：访问地址。管理员从公网访问控制台，云电脑走阿里云内网访问 OSS。

## 3. 两个程序

两个程序都用 Go 编写，编译成 Windows 64 位（`windows/amd64`）的单个 exe 文件。拷过去就能运行，不需要另外安装运行环境。

### 3.1 `agent.exe`：部署到每台云电脑

**运行方式**：作为 Windows 服务运行，开机自动启动，一直在后台。

**自带的管理命令**：

| 命令 | 作用 |
|---|---|
| `agent.exe install` | 注册为 Windows 服务并设置开机自启 |
| `agent.exe uninstall` | 卸载服务 |
| `agent.exe start` / `stop` | 启停服务 |
| `agent.exe sync` | 立即执行一次同步（调试用，不经过服务） |
| `agent.exe status` | 打印本机当前状态 |

**服务主循环**（默认每 30 分钟一轮）：

主循环从不等待安装、升级、采集或大文件上传。这些耗时的工作交给后台 worker 做。

每个 Admin 任务都有租约和取消状态。Agent 重启后，不靠本机的失败记录决定要不要重试。是否重新派发，由 Admin 根据租约有没有过期来决定。

每一轮按下面的顺序执行：

0. **策略同步**：拉取全局的 `policy.json`。ETag 没变就跳过。这一步**无论如何都执行**，不管机器有没有绑定员工。
1. **查绑定**：用主机名读绑定文件，知道本机归哪个员工。查不到就只上报状态，不下发凭据。
   - `blockEnabled=true`：把 Chrome、Edge、Firefox 的网址黑名单写进 `HKLM`。
   - `blockEnabled=false`：清除黑名单（管理员临时开放时用）。
2. **凭据分发**：拉取该员工的 `credentials.zip`。ETag 没变就跳过。
   - 解压后复制到该员工的 profile（`C:\Users\{员工}`）。
   - 修复文件权限（ACL），确保这个员工能读。
   - **什么时候结束员工的 Codex**：
     - 条件：写到磁盘上的文件真的变了，或者凭据对象被删了。"真的变了"包括：新增文件、内容不同、员工删掉后又补回；第一次投递时所有文件都算变了。
     - 做法：只结束该员工会话里的 Codex，命令是 `taskkill /F /FI "USERNAME eq <员工>" /IM ...`。
     - 为什么要结束：Codex 启动时把令牌和配置读进内存，之后不再读磁盘。不重启，它会一直用旧的。
     - 为什么只结束这个员工的：同一台云电脑上可能还有别人的会话。全机结束会连带中断别人的工作。
     - 判断依据是文件内容（逐字节比较），不是"是否投递过一次"。下面两种情况文件其实一个没动，所以不结束：
       - ETag 变了但内容相同，比如控制台重发了同样的包；
       - 本机 marker 读不了导致重新投递，比如 Agent 升级时改了 marker 格式。
   - **一次性指令（`restartCodex`）**：
     - 控制台在绑定对象里写一个随机 nonce，放在 `restartCodex` 字段。
     - 它和本机 marker 里记的值不同时，Agent 同样结束该员工的 Codex，然后把这个 nonce 写进 marker。
     - 执行结果（nonce、时间、`killed 1 process` 之类的信息，意思是"结束了 1 个进程"）随状态一起上报。
     - 同一个 nonce 只执行一次。执行失败也要写 marker，否则每一轮都会去结束一次别人的会话。
     - 指令放在绑定对象里，而不是新开一个 OSS 路径，原因是：Agent 每一轮本来就要读绑定对象，这样不用修改 Agent 的 RAM 权限。
3. **会话采集**（可选，默认关闭）：以下三个条件都满足才执行：`policy.json` 里 `collectEnabled=true`；机器已绑定；绑定的员工在本机有 profile。
   - 做法：把该员工 `.codex` 目录里的原始会话，按增量写入 `agent_workdir/{员工}/data_collect/`。
   - Agent 对这个路径只能写、不能读。它的权限和凭据、策略的权限分开，单独授权。详见 `OSS布局.md` §6。
4. **状态上报**：按主机名写状态文件。

具体路径见 `OSS布局.md` §4。API Agent 不再从 `_machines/*.json` 读取软件安装任务。

**为什么不需要用户密码**：往其他用户的 profile 写文件、写 `HKLM` 注册表，只需要 SYSTEM 权限。Agent 不模拟用户登录，也不保存用户凭据。

**日志**：`C:\ProgramData\AIEnvMgr\agent.log`。超过 4MB 时换新文件，旧的改名为 `agent.log.1`，只保留这一份旧日志。

### 3.2 `admin.exe`：管理员工作机

**运行方式**：在数据库模式下，管理功能由 Admin 控制台的网页和接口提供。访问云的身份凭证只放在服务端，Agent 不带 OSS 的 AK/SK。

| 子命令 | 作用 |
|---|---|
| `admin.exe add-site <域名...>` | 增加封禁域名并上传 |
| `admin.exe remove-site <域名...>` | 移除封禁域名并上传 |
| `admin.exe list-sites` | 查看当前封禁清单 |
| `admin.exe disable-block` | 全局临时开放（`blockEnabled=false`） |
| `admin.exe enable-block` | 恢复封禁 |
| `admin.exe status` | **拉取所有机器状态并汇总展示** |

**员工名单相关命令**：

```
admin.exe user add work1 --codex a@x.com    加入名单
admin.exe user disable work1                                  停用（Agent 会清除其本地凭据）
admin.exe user list                                           查看名单与凭据状态
```

**`admin.exe status` 输出示例**：

```
USER     HOSTNAME     LAST SYNC   POLICY   CREDS    BLOCK  APPLOCKER  STATE
work1    DESKTOP-A    2m ago      abc123   def456   ON     Enforce    OK
work2    DESKTOP-B    35m ago     abc123   ghi789   ON     Enforce    OK
work3    DESKTOP-C    3h ago      old!     jkl012   ON     Audit      STALE
```

从这张表可以直接看出：
- 哪台掉线了：`LAST SYNC`（上次同步时间）太久。
- 哪台策略没更新：`POLICY` 和别的机器不一致。
- 哪台 AppLocker 还没切到强制模式：`APPLOCKER` 显示 `Audit`（只记录不拦截），而不是 `Enforce`（强制拦截）。

## 4. OSS 数据结构与权限

### 4.1 Bucket 目录布局

**部署方式：一人一台云电脑。** 每个员工有自己的 AI 账户和自己的 OSS 目录。Agent 用主机名查 `_bindings/`，知道自己服务哪个员工，再去读这个员工的目录。

```
your-bucket/
├── admin/                       管理员专用，Agent 完全够不到
│   └── users.json               用户名单与账户映射
└── agent_workdir/               Agent 的全部活动范围
    ├── _bindings/               机器归属，Agent 靠它知道自己服务谁
    │   └── DESKTOP-A.json       { "user": "work1", ... }
    ├── _status/                 各机器上报的运行状态（Agent 只写）
    │   └── DESKTOP-A.json
    ├── policy.json              封禁策略，全局一份，机器级
    ├── work1/                   绑定到 work1 的机器读这里
    │   ├── credentials.zip      work1 专属的 AI 凭据
    │   └── data_collect/        会话采集，已实现，默认关闭（见 OSS布局.md §6）
    └── work2/
        └── ...
```

**为什么这样分**：
- Agent 用到的东西全放在 `agent_workdir/` 下。RAM 授权只要锁住这一个路径，Bucket 里其他位置还能另作他用。
- 员工名单单独放在外面。不管 Agent 的授权怎么写，都碰不到它。
- 属于某个员工的东西全在他自己的目录里，一个路径前缀对应一个人。
- `_bindings/` 和 `_status/` 是例外，按主机名索引。因为机器在绑定员工之前就要能上报状态。

> **完整结构、文件格式、权限对照以 `OSS布局.md` 为准**。本文只讲为什么这样设计。

**隔离效果**：
- 每个员工的 AI 凭据放在各自目录。Agent 只投递本机员工那一份，员工看不到别人的凭据。
- 员工始终不知道 AI 账户的密码。
- Agent 没有写 `policy.json` 的权限，没法通过 OSS 篡改策略。
- 没绑定员工的机器同样被封禁，因为策略不看"这台机器归谁"。

> **策略下发**：`policy.json` 全局只有一份。它管的是整台机器（写在 HKLM），和谁登录无关；而且必须对**还没分配给任何人的机器**也生效。所以它不放在员工目录下，Agent 也总是读取并应用它。
>
> **兼容说明**：§4.6 讲的是旧版 Agent（直接连 OSS）的兼容方案。当前的 API Agent 每台机器用自己的设备 token；安装任务、状态和取消都由 Admin 和 PostgreSQL 管理，Agent 不再读取 OSS 上的任务计划。

### 4.2 agent_workdir/policy.json

```json
{
  "blockEnabled": true,
  "blockedDomains": ["openai.com", "chatgpt.com", "claude.ai", "anthropic.com"],
  "updatedAt": "2026-08-03T16:20:00Z"
}
```

### 4.3 admin/users.json（用户名单，只有管理员能看）

```json
{
  "users": [
    { "windowsUser": "work1", "codexAccount": "ai-work1@company.com", "enabled": true },
    { "windowsUser": "work2", "codexAccount": "ai-work2@company.com", "enabled": true },
    { "windowsUser": "work3", "codexAccount": "ai-work3@company.com", "enabled": false }
  ],
  "updatedAt": "2026-08-03T16:20:00Z"
}
```

- `windowsUser`：云电脑上的 Windows 用户名。Agent 根据它决定把哪份凭据投给谁。
- `codexAccount`：该员工使用的 AI 账户（**密码由管理员保管，员工不知道**）。
- `enabled`：设为 `false` 时，Agent 会清除这个员工本机上的凭据（用于离职或停用）。

### 4.4 agent_workdir/{员工}/credentials.zip

每个员工一份，里面的结构相同：

```
codex/auth.json            该用户的 Codex CLI 凭据
codex/config.toml          Codex 配置
```

### 4.5 agent_workdir/_status/{主机名}.json

文件按**主机名**命名，而不是用户名。因为机器还没绑定员工时也要能上报；否则管理员看不到这台机器正在等分配。

字段清单见 `OSS布局.md` §4.3。

### 4.6 RAM 权限与 AK/SK（旧版直连 OSS 的兼容方案）

本节只适用于还没切换到 Admin 接口的旧版 Agent。新版本不要再按本节的做法把 AK/SK 编进 Agent。

#### 为什么这样取舍

最理想的隔离是"每个员工一套 AK/SK，只能访问自己的目录"。但这和**所有机器用同一个镜像**冲突：每个员工的程序都不一样，就变成一人一个镜像，运维成本无法接受。

**当前方案（原型阶段）：所有机器用同一个 Agent、同一套 AK/SK。Agent 用主机名认出自己，再按绑定关系去取数据。**

```
一个镜像  →  一个 agent.exe（内嵌同一套 AK/SK）  →  部署到所有云电脑
                    ↓
        Agent 启动时读取【主机名】作为自己的身份
                    ↓
        查 agent_workdir/_bindings/{主机名}.json  →  得知服务对象是 work1
                    ↓
        只访问 agent_workdir/work1/ 下的对象
```

**为什么不用本机的 Windows 用户名**：Agent 以 SYSTEM 身份运行，拿不到员工的身份。比如 `os.UserHomeDir()`（Go 里取当前用户目录的函数）返回的是 SYSTEM 账号自己的目录。主机名是这个程序唯一能可靠拿到的标识。员工是谁，只能由管理员在 OSS 上绑定后告诉它。

#### RAM 权限

Agent 用的这套 AK/SK 只能读，或者只能写少数路径：

```json
{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["oss:GetObject"],
      "Resource": ["acs:oss:*:*:your-bucket/agent_workdir/policy.json",
                   "acs:oss:*:*:your-bucket/agent_workdir/_bindings/*",
                   "acs:oss:*:*:your-bucket/agent_workdir/*/credentials.zip"]
    },
    {
      "Effect": "Allow",
      "Action": ["oss:PutObject"],
      "Resource": ["acs:oss:*:*:your-bucket/agent_workdir/_status/*"]
    }
  ]
}
```

上面的意思是：只能读（`oss:GetObject`）策略文件、绑定文件和各员工的凭据包；只能写（`oss:PutObject`）状态目录。

**能做到的隔离**：
- 员工是标准用户，读不到 Agent 程序里的密钥（有一定门槛，但不是绝对安全）。
- Agent 只往本机员工的 profile 写他自己的凭据，员工看不到别人的凭据文件。
- 员工始终不知道 AI 账户的密码。
- 没法通过 OSS 修改策略配置（没有写 policy 的权限）。

**当前方案的风险（明确告知）**：
- AK/SK 内嵌在所有机器共用的程序里。如果有人通过逆向把它提取出来，**理论上能访问所有员工目录**下的凭据。
- 这是**原型阶段可以接受的折中**，换来的是所有机器用同一个镜像、能快速交付。

**管理员的 RAM 用户**：
- 权限：整个 Bucket 可读写，另加 `AliyunECDReadOnlyAccess`（只读查看云电脑的权限，控制台用它查云电脑状态）。
- 只有管理员持有。
- 这把密钥**不编译进任何程序**：登录时在浏览器里输入，只存在程序运行时的内存里。

> 放宽管理员密钥的权限，和放宽 Agent 密钥的权限，不是程度上的差别，而是性质上的差别：
> - 管理员的密钥是运行时手动输入的，不存到磁盘，也不出现在发布的程序里。
> - Agent 的密钥以明文形式放在每台员工的云电脑上。如果给它查看云电脑（ECD）的权限，任何一台机器都能列出全公司的云电脑，以及哪台机器归哪个人。

#### AK/SK 怎么放进 agent.exe

不用配置文件。编译前把密钥填在源码里（`cmd/agent/credentials.go` 中的几个字符串），`make agent` 编译出的 exe 自带 OSS 地址和密钥。

**理由**：
- 配置文件要跟着镜像走，就多了一个可能被改、被挪走、或者忘了设权限的东西。
- 有人在旁边放一个配置文件，就能让 Agent 去连别的 Bucket。
- 写进源码后，这些问题都不存在了：内置配置优先于同目录下的任何文件。

**两套密钥必须放在不同的代码包里**：
- 密钥是明文字符串，编译进哪个包，就跟着哪个 exe 走。
- 如果放在两个程序共用的 `internal/config` 里，`agent.exe` 会把管理员那把可读写的密钥一起带到员工机器上，前面所有权限收紧都白做了。
- 所以 `cmd/agent/credentials.go` 和 `cmd/admin/credentials.go` 各存各的。
- `cmd/agent` 里有一个测试：编译两个 exe，各注入一个用于检测的特殊值（哨兵值），检查两个 exe 里都不含对方的密钥。

**用明文是有意的选择**：
- 用 `strings agent.exe`（列出文件里所有可读文字的命令）就能翻出这把密钥。
- 加密只能挡住随手一翻，因为解密需要的一切也都在同一个程序里。
- 既然挡不住有心人，不如省掉这份复杂度，依靠真正起作用的两层保护：
  1. 上面那份受限的 RAM 策略：只能读策略、写状态，读不到员工名单，改不了配置。
  2. 收紧 exe 文件的权限：用 `icacls /inheritance:r` 去掉继承的权限，只留 SYSTEM 和 Administrators。

#### 后续演进方向

原型验证之后，可以不再用 OSS，改为**自建服务端（客户端/服务端架构）**，从根本上解决上面的风险：

| 项 | 当前（OSS 原型） | 演进后（自建服务端） |
|---|---|---|
| 配置分发 | OSS 对象存储 | 自建 API 服务 |
| 身份认证 | 共享 AK/SK | **每台机器独立 token / 双向 TLS** |
| 权限粒度 | OSS 前缀 | 服务端按机器身份鉴权，天然隔离 |
| 凭据下发 | 静态文件 | 服务端按请求方身份动态返回，**只给它自己的** |
| 镜像 | 统一 | 统一（token 首次注册时下发） |
| 审计 | 状态文件 | 完整请求日志 |

演进时，Agent 内部的逻辑（写注册表、分发凭据、上报状态）**基本不用改**，只需要替换"配置从哪里来"这一层。

## 5. 分层职责

| 层 | 内容 | 变更方式 | 频率 |
|---|---|---|---|
| **镜像** | AI 工具、ChatGPT 应用预置、**AppLocker 规则**、agent.exe | 重做镜像 | 低 |
| **OSS** | 封禁策略、AI 凭据 | admin.exe 上传 | 高 |
| **Agent** | 拉取并应用、上报状态 | 自动 | 每 30 分钟 |

> **为什么 AppLocker 不走远程更新**：规则配错会导致程序无法运行，影响面大，而且难恢复。把规则做进镜像，再分批替换机器，比远程直接改更安全。

> **2026-09-12 变更**：控制台去掉了「代员工登录」和「文件传输」两项功能。
> - 去掉「代员工登录」：员工访问模型一律走 LiteLLM 网关，密钥入职时发放，已经没人需要管理员代为完成 OAuth 登录。
> - 去掉「文件传输」：Agent 随镜像预装，升级走「发布更新」，也不再需要临时下载链接。

> **2026-09-12 变更**：控制台的「机器」「策略总览」「模型网关」三页合并成一页「总览」。
> - 原因：这三页回答的是同一个问题的三个方面：机器整体状况好不好、机器被要求做什么、网关通不通。分开看要切换三次页面。
> - 三块数据各自读取，各自出错互不影响：网关连不上，只影响网关那一块。
> - 旧地址 `/machines`、`/policy`、`/gateway` 暂时自动跳转（302）到 `/overview`，方便用书签打开的人。

## 6. 安全设计

| 项 | 措施 |
|---|---|
| OSS Bucket | 私有，不开放公网匿名访问 |
| 云电脑访问 | 内网 endpoint + 受限 AK/SK：`agent_workdir/` 内只读策略与凭据、只写状态；`admin/` 完全够不到 |
| 管理员访问 | 读写 AK/SK，仅管理员持有 |
| Agent 密钥 | 明文编译在 agent.exe 内，exe 的 ACL 仅 SYSTEM/Administrators 可读 |
| 员工权限 | 标准用户，无法读 agent.exe、无法改 HKLM |
| 传输 | 全程 HTTPS |

**仍然存在的风险**：
- 只读的 AK/SK 存在云电脑本地。如果被有管理员权限的人拿到，可以下载凭据包。应对：严格控制管理员权限，定期更换密钥。
- 凭据包是明文的。应对：私有 Bucket、内网访问、按路径前缀授权，三重限制。

## 7. 典型流程

### 7.1 初次部署

```
1. 准备模板云电脑
2. 跑 PowerShell 脚本装 AI 工具、配 AppLocker（一次性）
3. 放入统一的 agent.exe，执行 agent.exe install（注册为服务）
4. 制作自定义镜像 ← 所有云电脑共用这一个镜像
5. 用该镜像批量创建云电脑，每台创建一个 Windows 标准用户
6. Agent 开机自启，用主机名上报自己
7. 管理员在 admin.exe status 里看到新机器，绑定给对应员工
8. Agent 下次同步即拉取该员工的配置
```

> Agent 不需要一台台配置：所有机器用同一个程序、同一套密钥。Agent 靠**主机名**认出自己，靠**管理员的绑定**决定去 OSS 的哪个目录取数据。管理员事先不需要知道主机名，机器开机后会自己出现在 status 里。

### 7.1b 新增员工

```
1. admin.exe user add work4                      加入名单，同时签发网关密钥
2. 用统一镜像开一台云电脑，创建 Windows 用户 work4
3. 员工登录 → Agent 自动拉取 work4 的凭据 → 直接可用
```
**不需要**重新编译 Agent，也不需要重做镜像。

### 7.2 更新封禁域名

```
管理员：admin.exe add-site newsite.com
   ↓ 上传 OSS
各台 Agent ≤30 分钟内自动拉取应用
   ↓
员工重启浏览器后生效
```
**不需要**重做镜像、一台台操作或重启机器。

### 7.3 AI 凭据过期

```
管理员在控制台「员工账号」页对该员工重新签发
   ↓ 组装凭据 → 上传 OSS
各台 Agent 自动分发到所有用户 profile → 员工无感
```
管理员在**任意机器**上操作都可以，本机不需要装 AI 工具。

### 7.4 新员工

```
1. 创建 Windows 标准用户
2. 首次登录 → ChatGPT 应用自动安装（镜像预置）
3. Agent 下次同步 → 凭据到位
4. 直接可用，零配置
```

### 7.5 巡检

```
admin.exe status     一屏看所有机器：是否掉线、策略是否同步、AppLocker 模式
```

### 7.6 AppLocker 规则变更（不常发生）

```
模板机调整并验证 → 重做镜像 → 灰度替换
```

（"灰度替换"指先替换一小部分机器，确认没问题再逐步扩大。）

- Go 负责需要常驻后台、跨机器、需要编程控制的部分。

## 9. 已知限制

1. **ChatGPT 桌面应用（MSIX）必须在用户登录后的会话里注册**：Agent 做不了这件事，只能靠镜像预置，在用户第一次登录时自动安装。
2. **策略生效有延迟**：要等 Agent 下一次同步（默认间隔 30 分钟），再加上员工重启浏览器。
3. **AppLocker 不能远程更新**：改规则需要重做镜像。
4. **凭据是明文**：靠私有 Bucket、内网访问和按路径前缀授权来保护，没有额外加密。
5. **防不了物理层面的手段**：比如用手机拍屏幕、用个人设备访问 AI，本方案不覆盖。
