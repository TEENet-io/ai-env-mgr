# AI Env Mgr 架构说明（Go 双二进制 · OSS 配置中心）

> 版本：2026-08 · 面向：方案设计与实施人员
> 适用场景：**阿里云无影共享型云电脑，多台，文件系统相互隔离，无 AD 域**

---

## 1. 背景与约束

### 1.1 场景

| 约束 | 影响 |
|---|---|
| 多台云电脑（≥2） | 无法在单机内解决，需跨机分发 |
| 文件系统相互隔离 | 装一台不等于所有机器都有 |
| 无 AD 域 | 无法用组策略（GPO）集中下发 |
| 员工为标准用户 | 无管理员权限，无法自行解除管控 |

### 1.2 设计目标

- 多台云电脑配置一致
- 封禁策略可随时更新，不重做镜像、不逐台操作
- AI 工具登录由管理员统一维护，员工无需各自登录
- 不保存任何用户密码
- 管理员可查看所有机器的运行状态

## 2. 整体架构

```
┌───────────────────────────────────────────────┐
│  管理员工作机                                   │
│  admin.exe（Go CLI，读写 AK/SK）                │
│    login           代员工登录，凭据直接入 OSS      │
│    add-site        增删封禁域名                  │
│    disable-block   临时全局开放                  │
│    status          查看所有机器状态               │
└────────────────────┬──────────────────────────┘
                     │ HTTPS（公网 endpoint）
                     ↓
┌───────────────────────────────────────────────┐
│  OSS 私有 Bucket（结构见 OSS布局.md）             │
│    admin/users.json              ← 仅管理员      │
│    agent_workdir/_bindings/{机器}.json ← 管理员写 │
│    agent_workdir/_status/{机器}.json   ← Agent 写 │
│    agent_workdir/policy.json           ← 管理员写 │
│    agent_workdir/{员工}/credentials.zip ← 管理员写 │
└────────────────────┬──────────────────────────┘
                     │ HTTPS（内网 endpoint）
                     ↓
┌───────────────────────────────────────────────┐
│  共享型云电脑 × N 台                             │
│                                                │
│  [镜像固化]                                     │
│    · Codex CLI / Claude Code（C:\Tools）        │
│    · ChatGPT 桌面应用（整机预置）                 │
│    · AppLocker 规则                             │
│    · agent.exe（内含受限 AK/SK）                 │

│    1. 用主机名查绑定 → 得知服务哪个员工            │

│                                                │
│  [用户会话]                                     │
│    · 首次登录自动装 ChatGPT 应用（镜像预置）       │
│    · AI 工具已是登录态，直接可用                   │
└───────────────────────────────────────────────┘
```

## 3. 两个二进制

用 Go 编写，交叉编译为 `windows/amd64` 单文件可执行程序，无运行时依赖。

### 3.1 `agent.exe` — 部署到每台云电脑

**形态**：Windows 服务，开机自启，常驻后台。

**自管理命令**：

| 命令 | 作用 |
|---|---|
| `agent.exe install` | 注册为 Windows 服务并设置开机自启 |
| `agent.exe uninstall` | 卸载服务 |
| `agent.exe start` / `stop` | 启停服务 |
| `agent.exe sync` | 立即执行一次同步（调试用，不走服务） |
| `agent.exe status` | 打印本机当前状态 |

**服务主循环**（默认每 30 分钟）：

0. **策略同步** — 拉全局 `policy.json`，ETag 无变化则跳过。**无条件执行**，不依赖绑定
1. **查绑定** — 用主机名读绑定文件，得知本机服务哪个员工。查不到就只上报，不下发凭据
   - `blockEnabled=true` → 写 Chrome/Edge/Firefox 的 URL 黑名单到 `HKLM`
   - `blockEnabled=false` → 清除黑名单（管理员临时开放场景）
2. **凭据分发** — 拉该员工的 `credentials.zip`，ETag 无变化则跳过
   - 解包后复制到该员工的 profile（`C:\Users\{员工}`）
   - 修复 ACL，确保目标用户可读
3. **会话采集**（可选，默认关闭）— 仅当 `policy.json` 的 `collectEnabled=true` 且机器已绑定、绑定员工在本机有 profile 时才跑：把该员工 `.claude`/`.codex` 的原始会话增量写入 `agent_workdir/{员工}/data_collect/`，agent 对这个前缀只写不读，权限与凭据/策略分开单独授权，见 `OSS布局.md` §6
4. **状态上报** — 按主机名写状态文件

具体路径见 `OSS布局.md` §4。

**为什么不需要用户密码**：写文件到其他用户 profile、写 `HKLM` 注册表，只需 SYSTEM 权限。Agent 不模拟登录、不保存用户凭据。

**日志**：`C:\ProgramData\AIEnvMgr\agent.log`，超过 4MB 滚动一次，保留上一代 `agent.log.1`

### 3.2 `admin.exe` — 管理员工作机

**形态**：CLI，单文件，用读写 AK/SK。

| 子命令 | 作用 |
|---|---|
| `admin.exe login` | **代员工登录**：生成登录链接 → 浏览器授权 → 拿到 token → **内存打包直接上传 OSS** |
| `admin.exe add-site <域名...>` | 增加封禁域名并上传 |
| `admin.exe remove-site <域名...>` | 移除封禁域名并上传 |
| `admin.exe list-sites` | 查看当前封禁清单 |
| `admin.exe disable-block` | 全局临时开放（`blockEnabled=false`） |
| `admin.exe enable-block` | 恢复封禁 |
| `admin.exe status` | **拉取所有机器状态并汇总展示** |

#### `admin.exe login` — 代员工登录，凭据直接入 OSS

**核心场景**：每个员工有**自己独立的** AI 账户，账户密码由**管理员保管，员工不知道**。管理员用此命令代为完成登录，token 直接写入 OSS，员工那边自动就是登录态。

**流程**：

```
管理员执行  admin.exe login --user work1 --tool claude
   ↓
admin.exe 发起 OAuth 流程，输出登录链接（或设备码）
   ↓
管理员用浏览器打开链接，用 work1 对应的 AI 账户完成授权
   ↓
admin.exe 拿到 token → 在内存中组装凭据文件 → 打包为 zip
   ↓
直接上传到 OSS  agent_workdir/work1/credentials.zip   ← 全程不落本地磁盘
   ↓
Agent 下次同步 → 只投递到 C:\Users\work1
   ↓
work1 打开工具即为登录态，且始终不知道账户密码
```

> **凭据不落盘**：token 从拿到、组装、打包到上传全在内存完成，管理员机器上不残留凭据文件。

**命令形式**（**一次一个用户**，每次都需要人工完成浏览器授权，不支持批量）：

```
admin.exe login --user work1 --tool claude     为 work1 登录 Claude
admin.exe login --user work1 --tool codex      为 work1 登录 Codex
admin.exe login --user work1 --tool all        两个依次登录（仍是逐个授权）
```

**相关命令**：

```
admin.exe user add work1 --codex a@x.com --claude a@x.com    加入名单
admin.exe user disable work1                                  停用（Agent 会清除其本地凭据）
admin.exe user list                                           查看名单与凭据状态
```

> 实现细节（OAuth 端点、client_id、token 组装格式）待补充。

**`admin.exe status` 输出示例**：

```
USER     HOSTNAME     LAST SYNC   POLICY   CREDS    BLOCK  APPLOCKER  STATE
work1    DESKTOP-A    2m ago      abc123   def456   ON     Enforce    OK
work2    DESKTOP-B    35m ago     abc123   ghi789   ON     Enforce    OK
work3    DESKTOP-C    3h ago      old!     jkl012   ON     Audit      STALE
```

一眼看出：哪台掉线（LAST SYNC 过久）、哪台策略没更新（POLICY 不一致）、哪台 AppLocker 还没切强制。

## 4. OSS 数据结构与权限

### 4.1 Bucket 布局

**部署模型：一人一台云电脑。** 每个员工有独立的 AI 账户和独立的 OSS 目录；Agent 用主机名查 `_bindings/` 得知自己服务哪个员工，再去读那个员工的目录。

```
your-bucket/
├── admin/                       管理员专用，Agent 完全够不到
│   └── users.json               用户名单与账户映射
└── agent_workdir/               Agent 的全部活动范围
    ├── _bindings/               机器归属，Agent 靠它知道自己服务谁
    │   └── DESKTOP-A.json       { "user": "work1", ... }
    ├── _status/                 各机器上报的运行状态（Agent 只写）
    │   └── DESKTOP-A.json
    ├── policy.json              封禁策略，全局一份，机器级
    ├── work1/                   绑定到 work1 的机器读这里
    │   ├── credentials.zip      work1 专属的 AI 凭据
    │   └── data_collect/        会话采集，已实现，默认关闭（见 OSS布局.md §6）
    └── work2/
        └── ...
```

**为什么这样分**：Agent 的东西全收在 `agent_workdir/` 下，RAM 授权锁一条路径即可，Bucket 还能另作他用；员工名单单独放在外面，Agent 的授权无论怎么写都碰不到它。属于某个员工的东西则全在他自己的目录里，一个前缀覆盖一个人。`_bindings/` 与 `_status/` 例外——它们按主机名索引，机器在绑定前就要能上报。

> **完整结构、对象格式、权限对照以 `OSS布局.md` 为准**，本文只讲取舍。

**隔离效果**：
- 每个员工的 AI 凭据存放在各自目录，Agent 只投递本机用户那一份，员工看不到别人的凭据
- 员工始终不知道 AI 账户密码
- Agent 无权写 `policy.json`，无法通过 OSS 篡改策略
- 未绑定的机器同样被封禁：策略不依赖"这台机器归谁"

> **策略下发**：`policy.json` 全局一份。它是机器级管控（写 HKLM），与登录者无关，且必须对**尚未分配给任何人的机器**生效——所以它不在员工目录下，agent 也无条件读取应用。
>
> **当前限制**：原型阶段所有 Agent 共用一套 AK/SK（见 §4.6），目录隔离靠 Agent 自身约束而非 RAM 权限强制。演进到自建服务端后可做到真正的强隔离。

### 4.2 agent_workdir/policy.json

```json
{
  "blockEnabled": true,
  "blockedDomains": ["openai.com", "chatgpt.com", "claude.ai", "anthropic.com"],
  "updatedAt": "2026-08-03T16:20:00Z"
}
```

### 4.3 admin/users.json（用户名单，仅管理员可见）

```json
{
  "users": [
    { "windowsUser": "work1", "codexAccount": "ai-work1@company.com", "claudeAccount": "ai-work1@company.com", "enabled": true },
    { "windowsUser": "work2", "codexAccount": "ai-work2@company.com", "claudeAccount": "ai-work2@company.com", "enabled": true },
    { "windowsUser": "work3", "codexAccount": "ai-work3@company.com", "claudeAccount": "ai-work3@company.com", "enabled": false }
  ],
  "updatedAt": "2026-08-03T16:20:00Z"
}
```

- `windowsUser` — 云电脑上的 Windows 用户名，Agent 据此决定把哪份凭据投给谁
- `codexAccount` / `claudeAccount` — 该员工使用的 AI 账户（**密码由管理员保管，员工不知**）
- `enabled` — 置为 `false` 时 Agent 会清除该用户本地的凭据（离职/停用场景）

### 4.4 agent_workdir/{员工}/credentials.zip

每个用户一份，内容结构相同：

```
codex/auth.json            该用户的 Codex CLI 凭据
codex/config.toml          Codex 配置
claude/.credentials.json   该用户的 Claude Code 凭据
claude.json                Claude Code OAuth 会话状态（缺此文件仍会要求登录）
```

### 4.5 agent_workdir/_status/{主机名}.json

按**主机名**而不是用户名——机器还没绑定时也要能上报，否则管理员看不到它在等分配。

字段清单见 `OSS布局.md` §4.3。

### 4.6 RAM 权限与 AK/SK（当前：统一 Agent 方案）

#### 设计取舍

理想的隔离是"一个用户一套 AK/SK，只能访问自己目录"，但这与**镜像统一**矛盾 —— 每个用户的二进制不同，就变成一人一个镜像，运维成本不可接受。

**当前方案（原型阶段）：统一 Agent + 统一 AK/SK，按主机名认自己、按绑定关系取数据。**

```
一个镜像  →  一个 agent.exe（内嵌同一套 AK/SK）  →  部署到所有云电脑
                    ↓
        Agent 启动时读取【主机名】作为自己的身份
                    ↓
        查 agent_workdir/_bindings/{主机名}.json  →  得知服务对象是 work1
                    ↓
        只访问 agent_workdir/work1/ 下的对象
```

**为什么不用本机 Windows 用户名**：agent 以 SYSTEM 身份运行，取不到员工的身份——`os.UserHomeDir()` 返回的是 system profile。主机名是这个进程唯一能可靠拿到的标识，员工是谁只能由管理员在 OSS 上绑定告知。

#### RAM 权限

Agent 用一套只读/受限写的 AK/SK：

```json
{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["oss:GetObject"],
      "Resource": ["acs:oss:*:*:your-bucket/agent_workdir/policy.json",
                   "acs:oss:*:*:your-bucket/agent_workdir/_bindings/*",
                   "acs:oss:*:*:your-bucket/agent_workdir/*/credentials.zip"]
    },
    {
      "Effect": "Allow",
      "Action": ["oss:PutObject"],
      "Resource": ["acs:oss:*:*:your-bucket/agent_workdir/_status/*"]
    }
  ]
}
```

**能做到的隔离**：
- 员工是标准用户，读不到 agent 二进制内的密钥（有门槛，非绝对）
- Agent 只往本机用户的 profile 写属于他的凭据，员工看不到别人的凭据文件
- 员工始终不知道 AI 账户密码
- 无法通过 OSS 修改策略配置（无写 policy 权限）

**当前方案的风险（明确告知）**：
- AK/SK 内嵌在统一二进制中，若被逆向提取，**理论上可访问所有用户目录**下的凭据
- 属于**原型阶段的可接受折中**，换取镜像统一与快速交付

**管理员的 RAM 用户** — 全 Bucket 读写，仅管理员持有。

#### AK/SK 怎么进到 agent.exe 里

不用配置文件，而是编译前填在源码里（`cmd/agent/credentials.go` 的几个字符串），`make agent` 产出的 exe 自带 OSS 地址和密钥。

**理由**：配置文件要跟着镜像走，就多出一个能被改、被挪、被忘记设 ACL 的东西；而且丢一个配置文件在旁边就能把 agent 指向别的 Bucket。写进源码之后这些都不成立——内置配置优先于任何同目录文件。

**两套密钥必须分在不同的包里**。密钥是明文字符串，编译进哪个包就跟着哪个 exe 走；如果放在共享的 `internal/config` 里，agent.exe 会把管理员那把读写密钥一起带到员工机器上，前面所有的权限收敛都白做。所以 `cmd/agent/credentials.go` 和 `cmd/admin/credentials.go` 各存各的，`cmd/agent` 里有个测试编译两个 exe、各注入一个哨兵值，检查彼此不含对方的密钥。

**明文是有意的取舍**：`strings agent.exe` 能翻出这把密钥。加密只能挡住随手一翻——解密所需的一切也在同一个二进制里。既然挡不住有心人，就不如把复杂度省下来，靠真正起作用的两层：上面那份受限 RAM 策略（只能读策略、写状态，读不到员工名单、改不了配置），以及给 exe 收紧 ACL（`icacls /inheritance:r`，只留 SYSTEM 和 Administrators）。

#### 后续演进方向

原型验证后，可去掉 OSS、改为**自建 CS 架构**，从根本上解决上述风险：

| 项 | 当前（OSS 原型） | 演进后（自建服务端） |
|---|---|---|
| 配置分发 | OSS 对象存储 | 自建 API 服务 |
| 身份认证 | 共享 AK/SK | **每台机器独立 token / 双向 TLS** |
| 权限粒度 | OSS 前缀 | 服务端按机器身份鉴权，天然隔离 |
| 凭据下发 | 静态文件 | 服务端按请求方身份动态返回，**只给它自己的** |
| 镜像 | 统一 | 统一（token 首次注册时下发） |
| 审计 | 状态文件 | 完整请求日志 |

演进时 Agent 的内部逻辑（写注册表、分发凭据、上报状态）**基本不用改**，只替换"配置来源"这一层。

## 5. 分层职责

| 层 | 内容 | 变更方式 | 频率 |
|---|---|---|---|
| **镜像** | AI 工具、ChatGPT 应用预置、**AppLocker 规则**、agent.exe | 重做镜像 | 低 |
| **OSS** | 封禁策略、AI 凭据 | admin.exe 上传 | 高 |
| **Agent** | 拉取并应用、上报状态 | 自动 | 每 30 分钟 |

> **为什么 AppLocker 不走远程更新**：配错会导致程序无法运行，影响面大且难恢复。固化在镜像、用灰度替换推进，比远程热更新安全。

## 6. 安全设计

| 项 | 措施 |
|---|---|
| OSS Bucket | 私有，不开放公网匿名访问 |
| 云电脑访问 | 内网 endpoint + 受限 AK/SK：`agent_workdir/` 内只读策略与凭据、只写状态；`admin/` 完全够不到 |
| 管理员访问 | 读写 AK/SK，仅管理员持有 |
| Agent 密钥 | 明文编译在 agent.exe 内，exe 的 ACL 仅 SYSTEM/Administrators 可读 |
| 员工权限 | 标准用户，无法读 agent.exe、无法改 HKLM |
| 传输 | 全程 HTTPS |

**残余风险**：
- 只读 AK/SK 存在云电脑本地，若被有管理员权限者获取，可下载凭据包。缓解：严控管理员权限、定期轮换密钥。
- 凭据包为明文。缓解：私有 Bucket + 内网 + 前缀级权限三重限制。

## 7. 典型流程

### 7.1 初次部署

```
1. 准备模板云电脑
2. 跑 PowerShell 脚本装 AI 工具、配 AppLocker（一次性）
3. 放入统一的 agent.exe，执行 agent.exe install（注册为服务）
4. 制作自定义镜像 ← 所有云电脑共用这一个镜像
5. 用该镜像批量创建云电脑，每台创建一个 Windows 标准用户
6. Agent 开机自启，用主机名上报自己
7. 管理员在 admin.exe status 里看到新机器，绑定给对应员工
8. Agent 下次同步即拉取该员工的配置
```

> Agent 不需要逐台配置：同一个二进制、同一套密钥，靠**主机名**认自己，靠**管理员的绑定**决定去 OSS 的哪个目录取数据。管理员事先不需要知道主机名——机器开机后会自己出现在 status 里。

### 7.1b 新增员工

```
1. admin.exe user add work4                      加入名单
2. admin.exe login --user work4 --tool all       代为登录，凭据入 OSS
3. 用统一镜像开一台云电脑，创建 Windows 用户 work4
4. 员工登录 → Agent 自动拉取 work4 的凭据 → 直接可用
```
**无需**重新编译 Agent、无需新做镜像。

## 9. 已知限制

1. **ChatGPT 桌面应用（MSIX）必须在用户会话中注册** —— Agent 无法代劳，依赖镜像预置在用户首次登录时自动安装。
2. **策略生效有延迟** —— Agent 同步间隔（默认 30 分钟）+ 浏览器重启。
3. **AppLocker 不可远程更新** —— 变更需重做镜像。
4. **凭据为明文** —— 靠私有 Bucket + 内网 + 前缀权限保护，未做额外加密。
5. **无法防护物理层面** —— 手机拍屏、个人设备访问 AI，本方案不覆盖。
