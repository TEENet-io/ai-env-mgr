# ai-env-mgr 代码审查报告

审查日期：2026-09-26  
审查范围：`rds-phase0` 分支，以 `v1.5.1`（提交 `addfe5c`）为基准；另外，工作区里还有一批没提交的 Windows 更新器改动。  
审查方式：

- 人工阅读代码，跟踪跨模块的调用过程，检查出错时的处理和权限边界。
- 运行了 `go test ./...`（全部单元测试）、对关键包加 `-race`（检查多线程同时读写同一数据的问题），以及 `make check`，都通过了。
- 测试通过，不代表下面这些跨组件的场景已经被测到。

## 先认识几个词

| 词 | 意思 |
|---|---|
| Admin | 管理后台（管理员用的网页和服务）。 |
| Agent | 装在每台云电脑上的管理程序。 |
| API | 后台给 Agent 调用的接口服务。 |
| OSS | 阿里云的云存储。老版本用它在后台和 Agent 之间传配置。"旧 OSS 计划"指老版本放在 OSS 上、按机器分配的软件安装计划。 |
| manifest | 软件包的说明文件，写着版本、下载地址、校验值、快捷方式等信息。 |
| 租约（lease） | Agent 领取（claim）一个任务后拿到的"占用凭证"，有有效期，需要续期。lease token 就是这个凭证。 |
| rollout | 把新版本分批推到机器上的发布过程。settle 指判断一次发布"已经落定"。 |
| SHA-256 | 文件的"指纹"，用来确认文件没被换掉或损坏。 |
| CSRF | 一种跨站伪造请求攻击。CSRF 校验用来防它。 |
| SYSTEM | Windows 里权限最高的系统账户。Agent 以它的身份运行。 |
| bootstrap（自举） | 让旧程序先把自己升级到"能正常升级"的版本。 |
| ACL | 文件的访问权限列表，规定哪些账户能读写。 |
| DPAPI | Windows 自带的数据加密接口。 |
| SSRF | 服务端请求伪造：诱导服务器去访问它不该访问的地址，例如内网服务。 |
| data race | 数据竞争：两个线程同时读写同一个变量，结果不确定。 |
| candidate / accepted / stable / retired | 版本状态：候选 / 已验收 / 稳定 / 已退役。 |

## 本轮修复状态（2026-09-26）

**C-01 已修复。**

- PostgreSQL 任务现在通过 `GET /agent/v1/application-tasks/{id}/manifest` 和 `/download` 获取资源。这两个接口要求 Agent 带上当前有效的 lease token。
- 旧 OSS 计划仍然走原来的兼容接口。
- 新增了客户端、Agent 安装流程和 API 路径的测试。`make check`、Windows 编译、关键包的 `-race` 检查都通过了。
- 数据库集成测试没有跑，因为当前环境没设置 `TEST_PG_DSN`（测试数据库的连接地址）。部署前应在本地 PostgreSQL 上补跑。

## 结论摘要

现有代码已经有不错的基础防护：

- 应用安装包有 SHA-256 校验；
- 应用任务有租约和取消状态；
- API 会校验设备 token、CSRF 和角色；
- 发布出去的文件使用不可变的存储路径（同一路径的内容不会被改）。

但还有一个高优先级问题会直接让新功能用不了。另有若干风险，可能导致：在线状态显示错误、任意写文件、恢复码被重复登录使用、更新失败。

| 等级 | 数量 | 需要优先处理 |
| --- | ---: | --- |
| 严重（Critical） | 1 | PostgreSQL 软件安装任务拿不到 manifest，任务会失败或反复重试 |
| 高（High） | 7 | 状态时间可伪造、更新器自举、快捷方式路径、恢复码并发、token 文件权限（ACL）、安装进程树、候选版本直接发布 |
| 中（Medium） | 7 | URL 下载存在 SSRF 且无大小上限、采集范围和内存、token 数据竞争、日志无限增长、机器注册、发布任务状态 |

## 发现项

### C-01（严重）：新的数据库安装任务拿不到应用 manifest

**场景**：

1. 管理员在后台创建任务，任务记录写入 `application_tasks` 表。
2. Agent 成功领取（claim）这个任务。
3. Agent 接着调用 `GET /agent/v1/application/{id}/{version}/manifest` 取 manifest。
4. 这个接口只从 `cfg.Applications` 里找"已分配给这台机器"的旧计划。
5. 但 API 配置已经明确不再填入旧 OSS 计划；`deviceconfig.Build` 也没有把 PostgreSQL 里的租约任务填进 `Applications`。
6. 所以新任务会收到 `application is not assigned to this machine`（应用没有分配给这台机器）/ 404，表现为安装失败或反复重试。

**证据**：

- [Admin 创建 DB 任务](../go/internal/adminweb/apps.go:94)
- [Agent claim 后请求 manifest](../go/cmd/agent/application_worker.go:26)
- [manifest 只检查 cfg.Applications](../go/internal/deviceapi/artifact.go:94)
- [API 明确不复制旧 OSS plan](../go/internal/deviceapi/config.go:12)
- [Build 仅声明 Applications，未赋值](../go/internal/deviceconfig/deviceconfig.go:45)

**影响**：

- 软件安装功能实际上用不了。
- OSS 上如果还残留旧计划文件，也不应重新启用，否则已取消的任务会"复活"。

**建议**（二选一）：

- 新增一个用任务 ID 和租约做权限校验的 manifest / 安装包接口：只允许这台设备凭当前有效的租约，读取对应的应用和版本；服务端还要再检查任务状态、应用是否已审核、文件 SHA 是否一致。
- 或者在生成设备配置时，只填入当前有效的租约任务（不能恢复整套旧 OSS 按机器分配的计划）。

另外，增加端到端测试，覆盖完整流程：创建任务 → 领取 → 取 manifest → 下载 → 完成或取消。

### H-01（高）：设备自己报的时间，直接决定了在线状态和发布是否落定

**场景**：

- Agent 上报的 `LastSyncAt`（上次同步时间）可以被改成未来的时间。
- API 和 OSS 状态导入程序（OSS importer）都直接用它覆盖 `devices.last_seen_at`（最后在线时间）。
- 结果，后台会把这台机器显示为"在线"；后续判断发布是否落定（settle）时，也可能接受不该接受的状态。

**证据**：[API 状态处理](../go/internal/deviceapi/status.go:46)、[OSS 状态导入](../go/internal/worker/status.go:85)。

**建议**：

- `last_seen_at` 只用服务端收到请求时的 UTC 时间。
- 设备自己报的时间另存为诊断字段，并限制在合理的误差范围内。
- 判断发布是否落定时，不能信任未来时间。

### H-02（高）：旧版 Agent 无法把自己升级到修好的更新器

**场景**：

- v1.4.x / v1.5.0 的旧更新器会尝试给正在运行的 exe 改名，Windows 会报 `Access is denied`（拒绝访问）。
- v1.5.1 加入了一个独立运行的辅助程序（detached helper）来解决这个问题。但要用上它，旧版本得先成功完成一次更新。
- 旧版本没法靠同一条更新流程完成这次自举，所以现有机器会一直停在旧版本。

**证据**：

- 历史版本的更新器直接给当前 exe 改名；当前辅助程序的实现见 [更新器](../go/cmd/agent/updater_windows.go:18)。
- `winsvc.Start` 只发出启动请求，不等新服务真正进入 RUNNING（运行中）状态（[service_windows.go](../go/internal/winsvc/service_windows.go:74)）。

**建议**：

- 为 v1.5.1 / 1.5.2 提供一次性的手动安装方式，或者一个独立的更新程序。
- 辅助程序应等服务进入 RUNNING 状态再算成功；失败时保留旧备份，并记下可以恢复的结果。
- 当前工作区的改动已经把 `agent.exe.old-*` 当作临时回滚文件，新服务成功启动后删除。注意：确认启动成功之前不要删它。

### H-03（高）：快捷方式字段可能让 SYSTEM 往任意路径写文件

**场景**：

- `Shortcut.Name`（快捷方式名称）被直接拼进公共桌面（Public Desktop）的路径，没有限制它只能是一个单纯的文件名。
- `Target`、`WorkingDirectory`、`Icon` 也都来自 manifest。
- 一个恶意或配错、但已经通过审核的 manifest，可能让 SYSTEM 在桌面以外的地方创建或覆盖 `.lnk` 文件，或者通过构造 PowerShell 参数影响其他路径。

**证据**：[manifest 校验只检查非空](../go/internal/admincore/apps.go:45)、[快捷方式写入](../go/cmd/agent/application_windows.go:133)。

**建议**：

- Name 只允许 `[A-Za-z0-9._ -]` 这些字符，并拒绝路径分隔符、`.`、`..`。
- 拼出的最终路径用 `filepath.Rel` 检查后，必须仍在 `PUBLIC\Desktop` 里面。
- Target / WorkingDirectory / Icon 也应限制为本地绝对路径，或安装目录内的路径。
- 服务端和 Agent 两边都要做这些校验。

### H-04（高）：判断"是否正在安装"只看进程名，可能被无关进程冒充

**场景**：

- `Running()` 只比较进程的文件名（不含路径）。机器上只要有任何同名进程，这次安装就会被永远跳过。
- EXE 安装程序超时后，只结束父进程。子安装程序可能还在运行，并锁住文件。

**证据**：[只按进程名检测](../go/cmd/agent/application_windows.go:46)、[超时后结束和回收进程](../go/cmd/agent/application_windows.go:91)。

**建议**：

- 优先用进程 ID（PID）、完整路径或数字签名来判断。
- 把安装程序放进 Job Object（Windows 用来统一管理一组进程的机制）。超时时结束整个进程树，并在返回前确认子进程都已退出。

### H-05（高）：消费恢复码不是原子操作，并发时可以重复使用

**场景**：

1. 两个登录请求同时进来，都读到同一份恢复码哈希（recovery hash）。
2. 两边各自校验，都通过。
3. 两边各自执行一条不带条件的 UPDATE。
4. 两次登录都可能成功，同一个恢复码被用了两次。

**证据**：[先读、再校验、再写的流程](../go/internal/authn/authn.go:247)、[不带条件的替换](../go/internal/dbstore/admins.go:146)。

**建议**：

- 用事务加行锁；或者用 SQL `DELETE ... WHERE id=? AND recovery_hashes @> ...`，并检查 `RowsAffected=1`（确实只改了一行）。
- 失败时重新读取，再试一次。
- 加一个并发登录的测试。

### H-06（高）：Windows 设备 token 用机器级加密，但文件权限没收紧

**场景**：

- token 用 `CRYPTPROTECT_LOCAL_MACHINE` 方式加密。这种方式下，同一台机器上任何能读到 token 文件的普通用户都能解密。
- Go 代码里设置的 `0700/0600` 权限，在 Windows 上并不等于完整的访问权限控制（ACL）。
- 代码也没有对 `%ProgramData%\AIEnvMgr` 目录递归执行 `icacls`（Windows 设置文件权限的命令）来收紧权限。

**证据**：[保存 token](../go/internal/agentapi/tokenstore.go:35)、[LocalMachine DPAPI](../go/internal/agentapi/tokenstore_windows.go:10)。

**建议**：

- 安装或启动时明确设置 ACL，只允许 LocalSystem、Administrators 和服务账户（服务 SID）读取状态目录。
- 或者改用绑定到用户或服务账户的 DPAPI 加密方式。
- 在真实的 Windows 镜像上，用标准用户身份验证：读取和解密都应失败。

### H-07（高）：发布流程允许候选版本直接发给所有机器

**场景**：`SetGlobalTarget`（设全局目标）和 `CreateRollout`（创建分批发布）只拒绝已退役（retired）的版本。候选（candidate）版本可以直接设为全局目标，或者发给整批机器，跳过了"已验收 / 稳定"（accepted / stable）的审核。

**证据**：[全局目标](../go/internal/ops/releases.go:104)、[rollout 创建](../go/internal/ops/releases.go:163)。

**建议**：

- 默认只允许已验收 / 稳定的版本。
- 候选版本只有在明确打开"试验 / 小范围"开关时才允许，并记录审批人、范围和过期时间。

### M-01（中）：通过 URL 发布应用，存在 SSRF 风险且没有大小上限

**场景**：

- 后台"通过 URL 发布"时，服务器会直接去下载任意 `http/https` 地址。
- 下载函数传入的是 `maxBytes=0`（不限大小）。
- 后果：可以借此访问云服务器的元数据地址（metadata）或内网服务；超大的响应也会被整个读进内存。

**证据**：[Admin URL 入口](../go/internal/adminweb/download.go:20)、[无上限下载](../go/internal/ghrelease/download.go:54)。

**建议**：

- 只允许 HTTPS，并且只允许白名单里的域名。
- 禁止访问内网地址和元数据地址。
- 限制跳转次数和响应大小。
- 先下载到临时文件，再边读边上传。

### M-02（中）：采集时把整个会话文件读进内存，可能耗尽 Agent 内存

**场景**：采集时，对每个会话文件先用 `io.ReadAll` 整个读进内存，再上传。如果某个 jsonl 文件异常变大或已损坏，同步会被卡住，内存占用也会很高。

**证据**：[整文件读入内存](../go/internal/agentcore/collect.go:150)。

**建议**：

- 设置单个文件和单轮采集的大小上限。
- 改成边读边传的分块上传（流式 multipart）。
- 超过上限时记录错误，并留一个标记，下次再试。

**另一个问题**：采集器声明支持 `.claude/projects/**/*.jsonl`，但 [Sessions()](../go/cmd/agent/collect.go:42) 实际只遍历 `.codex/sessions`。如果产品仍要求采集 Claude 会话，这部分现在会悄悄漏掉、不报错。应把这个目录加进遍历范围，并加上用样例文件（fixture）做的测试。

### M-03（中）：采集的范围和 API 的授权规则对不上

**场景**：

- Agent 会采集本机所有用户（[sync.go:517](../go/internal/agentcore/sync.go:517)）。
- 但上传地址只允许"这台机器绑定的员工"对应的 Windows 用户（[artifact.go:184](../go/internal/deviceapi/artifact.go:184)）。
- 所以在多人共用的机器上，其他用户的采集一定会被拒绝（403），反复报错。

**建议**：先明确产品上到底要采谁：

- 只采绑定的用户；或者
- 为每个本地用户建立明确的授权对应关系，由 API 签发对应的上传路径。

不要靠"先采集、再上传失败"来兜底。

### M-04（中）：APISource 更新 token 时有数据竞争风险

**场景**：

- `Reset` 在加锁（mutex）的情况下写 `a.Client.Token`。
- 但 Client 发请求时直接读这个字段，没加锁。
- 重新注册和同步 / 心跳同时发生时，可能出现数据竞争，或者请求带上旧 token。

**证据**：[Reset](../go/internal/agentcore/source_api.go:72)、[Client 请求读 token](../go/internal/agentapi/client.go:60 附近)。

**建议**：

- 把 token 封装起来，通过加锁或原子操作（atomic）的方法读取；或者每次整体替换一个不再修改的新 Client。
- 补一个"Reset 和请求同时进行"的 race 测试。

### M-05（中）：日志只在启动时轮转，长时间运行仍会无限增长

**场景**：`openLog` 只在进程启动时检查一次日志是否超过 4 MiB。Agent 一直运行时不会再轮转（把旧日志另存、重新开一个文件），所以单个 `agent.log` 可能无限变大。

**证据**：[启动时的轮转逻辑](../go/cmd/agent/logfile.go:58)。

**建议**：

- 用带大小限制的日志写入器，或者在每次写入时按大小轮转。
- 只保留固定份数的旧日志，并处理好多处同时写的情况。

### M-06（中）：没登记过的主机名也能直接注册，可能被占用或被刷爆

**场景**：

- 注册接口（enrol API）允许没登记过的主机名直接创建设备记录。
- 攻击者只要提交大量随机主机名，就能往设备表里塞满垃圾数据（也是一种拒绝服务，DoS）。
- 如果管理员主要靠主机名来认设备，还会造成混淆。

**建议**：

- 使用一次性注册码、预先登记的一次性随机码（nonce），或者管理员审批队列。
- 主机名只用来显示；设备身份以 token / 公钥为准。

### M-07（中）：后台的发布任务状态只保存在进程内存里

**场景**：

- 应用 / 发布页面的后台任务和进度，只保存在 Admin 进程的内存里。
- 执行发布的代码使用 `context.Background()`，不随页面请求结束而取消。
- Admin 重启、崩溃，或者在多个实例之间切换后，页面就看不到任务状态了。
- 这时 OSS 可能已经写入了安装程序、但还没写 manifest，留下没人管的孤立文件，或者没法恢复的半成品。

**证据**：[进程内的任务状态](../go/internal/adminweb/job.go:27)、[后台发布代码](../go/internal/adminweb/publish.go:113)。

**建议**：

- 把发布任务、状态、进度和租约存进 PostgreSQL。
- 先用临时路径存文件；安装程序校验完成后，再一次性发布 manifest。
- 启动时扫描超时的任务：能恢复就恢复，不能恢复就明确标为失败，并清理临时文件。

## 已确认有效的防护

- 应用安装包在发布时和 Agent 下载时都做 SHA-256 校验；存储路径按"应用 / 版本"固定命名。
- 应用任务有领取（claim）、续租（lease renew）、取消（cancel）和完成（finish）几种状态；Agent 的主同步循环不会等安装程序装完。
- API 的日志有大小限制，状态上报的内容也有大小上限；设备 token 没通过授权时，会触发重新注册。
- 管理后台已有默认的角色校验、CSRF 校验和应用审核流程。
- 当前没提交的更新器改动，会在更新成功后删除 `agent.exe.old-*`。但这个文件应保留到新服务启动成功之后；不要为了"不留旧文件"而提前删掉回滚副本。

## 建议的处理顺序

1. 先修 C-01，并补上安装任务的端到端测试。不修的话，后台的软件安装功能还是用不了。
2. 修 H-01、H-02、H-05：改用服务端时间、解决旧 Agent 自举、让恢复码消费成为原子操作。
3. 修 H-03、H-04、H-06：Windows 上的路径、进程树和文件权限问题，并在真实的 Windows 标准用户镜像上验证。
4. 把可发布的版本限制为已验收 / 稳定，再处理 SSRF、采集上限、日志轮转和注册策略。
