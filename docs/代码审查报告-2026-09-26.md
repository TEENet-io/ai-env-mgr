# ai-env-mgr 代码审查报告

审查日期：2026-09-26  
审查范围：`rds-phase0`，基线 `v1.5.1`（`addfe5c`）；工作区另有未提交的 Windows 更新器改动。  
审查方式：静态阅读跨模块调用链、检查错误处理和权限边界，并运行 `go test ./...`、关键包 `-race`、`make check`（均通过）。通过测试不代表下面的跨组件场景已经覆盖。

## 本轮修复状态（2026-09-26）

已修复 C-01：PostgreSQL 任务现在通过 `GET /agent/v1/application-tasks/{id}/manifest` 和 `/download` 获取资源，接口要求当前有效 lease token；旧 OSS 计划仍使用兼容接口。新增了客户端、Agent 安装链路和 API 路径测试，`make check`、Windows 编译及关键包 `-race` 均通过。数据库集成测试因当前环境未设置 `TEST_PG_DSN` 未执行，部署前应在本地 PostgreSQL 上补跑。

## 结论摘要

当前代码已经具备较好的基础防护：应用包有 SHA-256 校验，应用任务有租约和取消状态，API 有设备 token/CSRF/角色校验，发布物使用不可变对象键。但仍有一个会直接阻断新功能的高优先级问题，以及若干可能造成错误在线状态、任意文件写入、重复登录和更新失败的风险。

| 等级 | 数量 | 需要优先处理 |
| --- | ---: | --- |
| 严重（Critical） | 1 | PostgreSQL 软件安装任务无法取得 manifest，任务会失败/重试 |
| 高（High） | 7 | 状态时间伪造、更新器 bootstrap、快捷方式路径、恢复码并发、token ACL、安装进程树、候选版本直发 |
| 中（Medium） | 7 | URL SSRF/无大小上限、采集范围/内存、token data race、日志增长、机器注册、发布任务状态 |

## 发现项

### C-01（Critical）：新的数据库安装任务无法取得应用 manifest

**场景**：Admin 在 `application_tasks` 创建任务后，Agent 成功 claim；随后 Agent 调用 `GET /agent/v1/application/{id}/{version}/manifest`。该 endpoint 只从 `cfg.Applications` 查找“已分配给机器”的旧计划，但 API 配置已明确不再注入 OSS 旧计划，而 `deviceconfig.Build` 也没有从 PostgreSQL 的租约任务填充 `Applications`。因此新任务会得到“application is not assigned to this machine”/404，表现为安装失败或重复重试。

**证据**：

- [Admin 创建 DB 任务](../go/internal/adminweb/apps.go:94)
- [Agent claim 后请求 manifest](../go/cmd/agent/application_worker.go:26)
- [manifest 只检查 cfg.Applications](../go/internal/deviceapi/artifact.go:94)
- [API 明确不复制旧 OSS plan](../go/internal/deviceapi/config.go:12)
- [Build 仅声明 Applications，未赋值](../go/internal/deviceconfig/deviceconfig.go:45)

**影响**：软件安装功能实际上不可用；旧 OSS 对象若残留也不应被重新启用，否则会复活已取消任务。

**建议**：新增“带 task ID/lease 鉴权”的 manifest/package endpoint：只允许当前设备持有的有效租约读取对应 app/version，并在服务端再次校验任务状态、应用已审核和对象 SHA；或在构建配置时只注入当前有效租约（不能恢复整套旧 OSS machine plan）。增加端到端测试：创建任务→claim→manifest→下载→完成/取消。

### H-01（High）：设备自报时间直接决定在线状态和 rollout settle

**场景**：Agent 上传的 `LastSyncAt` 可以被篡改为未来时间。API 和 OSS importer 都用它覆盖 `devices.last_seen_at`，Admin 因而显示“在线”，后续 settle 判断也可能接受不应接受的状态。

**证据**：[API 状态处理](../go/internal/deviceapi/status.go:46)、[OSS 状态导入](../go/internal/worker/status.go:85)。

**建议**：`last_seen_at` 只使用服务端收到请求的 UTC 时间；设备时间单独存为诊断字段，并限制在合理偏差范围内。settle 逻辑不得信任未来时间。

### H-02（High）：旧 Agent 无法自举到修复后的更新器

**场景**：v1.4.x/v1.5.0 的旧更新器会尝试重命名正在运行的 exe，Windows 返回 `Access is denied`。v1.5.1 引入了 detached helper，但仍需要旧版本先成功完成一次更新；旧版本无法靠同一条更新链完成 bootstrap，现有机器会一直停在旧版本。

**证据**：历史版本的更新器直接对当前 exe 做 rename；当前 helper 的实现见 [更新器](../go/cmd/agent/updater_windows.go:18)。`winsvc.Start` 只发送启动请求，并不等待新服务进入 RUNNING 状态（[service_windows.go](../go/internal/winsvc/service_windows.go:74)）。

**建议**：为 v1.5.1/1.5.2 提供一次性手动安装或独立 updater；helper 应等待服务进入 RUNNING，失败时保留旧备份并记录可恢复结果。当前工作区改动已将 `agent.exe.old-*` 作为临时回滚文件，成功启动后删除；不要在启动确认前删除。

### H-03（High）：快捷方式字段可导致 SYSTEM 向任意路径写文件

**场景**：`Shortcut.Name` 直接拼入 Public Desktop 路径，未限制为单一 basename；`Target`、`WorkingDirectory`、`Icon` 也来自 manifest。恶意或误配置的已审核 manifest 可能使 SYSTEM 创建/覆盖桌面以外的 `.lnk`，或通过 PowerShell 参数构造影响其他路径。

**证据**：[manifest 校验只检查非空](../go/internal/admincore/apps.go:45)、[快捷方式写入](../go/cmd/agent/application_windows.go:133)。

**建议**：Name 仅允许 `[A-Za-z0-9._ -]` 且拒绝路径分隔符、`.`、`..`；最终路径必须 `filepath.Rel` 后仍位于 `PUBLIC\Desktop`。Target/WorkingDirectory/Icon 也应限制为绝对本地路径或安装目录内路径，并在服务端和 Agent 双重校验。

### H-04（High）：安装检测按进程 basename，可能被无关进程伪装

**场景**：`Running()` 只比较进程名 basename。机器上任意同名进程都会让安装被永久跳过。EXE 超时只 kill 父进程，子安装器可能继续运行并锁住文件。

**证据**：[basename 检测](../go/cmd/agent/application_windows.go:46)、[超时 kill/reap](../go/cmd/agent/application_windows.go:91)。

**建议**：优先使用 PID/完整路径/签名验证；安装器放入 Job Object，超时终止整个进程树，并在返回前确认子进程已退出。

### H-05（High）：恢复码消费不是原子操作，可被并发复用

**场景**：两个并发登录都读取同一份 recovery hash，分别验证成功，再各自执行无条件 UPDATE；两次都可能成功，恢复码被重复使用。

**证据**：[读-验-写流程](../go/internal/authn/authn.go:247)、[无条件替换](../go/internal/dbstore/admins.go:146)。

**建议**：使用事务/行锁，或 SQL `DELETE ... WHERE id=? AND recovery_hashes @> ...` 并检查 `RowsAffected=1`；失败时重新读取并重试一次。加入并发登录测试。

### H-06（High）：Windows 设备 token 的机器级 DPAPI 与文件 ACL 不匹配

**场景**：token 使用 `CRYPTPROTECT_LOCAL_MACHINE`，同机可读取 token 文件的普通用户可以解密。Go 的 `0700/0600` 在 Windows 上不是完整 ACL；代码没有对 `%ProgramData%\AIEnvMgr` 递归执行 `icacls` 限制。

**证据**：[保存 token](../go/internal/agentapi/tokenstore.go:35)、[LocalMachine DPAPI](../go/internal/agentapi/tokenstore_windows.go:10)。

**建议**：安装/启动时显式设置 ACL，仅允许 LocalSystem/Administrators/服务 SID 读取状态目录；或改用用户/服务 SID 绑定的 DPAPI scope。应在真实 Windows 镜像以标准用户验证读取和解密均失败。

### H-07（High）：发布流程允许 candidate 直接全局投放

**场景**：`SetGlobalTarget` 和 `CreateRollout` 只拒绝 retired，candidate 可以直接作为全局目标或 fleet rollout，绕过 accepted/stable 审核。

**证据**：[全局目标](../go/internal/ops/releases.go:104)、[rollout 创建](../go/internal/ops/releases.go:163)。

**建议**：默认只允许 accepted/stable；candidate 仅在显式“试验/小范围”开关下允许，并记录审批人、范围和过期时间。

### M-01（Medium）：应用 URL 发布存在 SSRF 和无大小上限

**场景**：Admin 的 URL 发布由服务器直接抓取任意 `http/https` URL；下载函数传入 `maxBytes=0`，可访问云 metadata/内网服务，超大响应也会被完整读回内存。

**证据**：[Admin URL 入口](../go/internal/adminweb/download.go:20)、[无上限下载](../go/internal/ghrelease/download.go:54)。

**建议**：仅允许 HTTPS 与明确域名白名单，禁止私网/metadata 地址，限制重定向和响应大小，下载到临时文件后流式上传。

### M-02（Medium）：采集读取整个 session 文件，可能耗尽 Agent 内存

**场景**：采集对每个 session 使用 `io.ReadAll` 后才上传；异常增长或损坏的 jsonl 文件会阻塞同步并造成高内存。

**证据**：[整文件读入内存](../go/internal/agentcore/collect.go:150)。

**建议**：设置单文件/单周期上限，使用流式 multipart/分块上传，超限记录错误并保留下次重试标记。

另外，采集器声明支持 `.claude/projects/**/*.jsonl`，但 [Sessions()](../go/cmd/agent/collect.go:42) 实际只遍历 `.codex/sessions`；如果产品仍要求采集 Claude 会话，这部分目前会静默漏采。应补充 root 并加入 fixture 测试。

### M-03（Medium）：采集范围与 API 授权模型不一致

**场景**：Agent 对所有本地用户执行采集（[sync.go:517](../go/internal/agentcore/sync.go:517)），但上传 URL 只允许机器绑定员工的 Windows 用户（[artifact.go:184](../go/internal/deviceapi/artifact.go:184)）。共享机器上其他用户的采集必然 403，形成重复错误。

**建议**：明确产品语义：只采绑定用户，或为每个本地用户建立明确授权映射并让 API 签发对应路径；不要依赖“先采集再失败”。

### M-04（Medium）：APISource token 更新存在 data race 风险

**场景**：`Reset` 在 mutex 内写 `a.Client.Token`，而 Client 请求路径直接读该字段；重注册与同步/心跳并发时可能出现竞态或请求带旧 token。

**证据**：[Reset](../go/internal/agentcore/source_api.go:72)、[Client 请求读 token](../go/internal/agentapi/client.go:60 附近)。

**建议**：把 token 封装为 mutex/atomic getter，或替换整个不可变 Client；补充“Reset 与并发请求”的 race 测试。

### M-05（Medium）：日志只在启动时轮转，长时间运行仍可无限增长

**场景**：`openLog` 仅在进程启动时检查 4 MiB；持续运行的 Agent 不会再次轮转，单个 `agent.log` 可无限增长。

**证据**：[启动轮转逻辑](../go/cmd/agent/logfile.go:58)。

**建议**：使用带大小限制的 writer，或在写入路径按大小轮转；保留固定代数并处理并发写。

### M-06（Medium）：未知 hostname 可直接注册，存在占用/DoS 风险

**场景**：enrol API 允许未知 hostname 创建设备记录。攻击者只需提交大量随机 hostname 即可污染设备表；若 hostname 是管理员识别设备的主要键，也会造成混淆。

**建议**：使用一次性 enrollment code、预注册 nonce 或管理员批准队列；hostname 仅作展示字段，设备身份以 token/公钥为主。

### M-07（Medium）：Admin 发布任务状态仅存在进程内

**场景**：应用/发布页面的异步 job 和进度保存在 Admin 进程内，发布闭包使用 `context.Background()`。Admin 重启、崩溃或多实例切换后，页面看不到任务状态；OSS 可能已经写入 installer 但尚未写入 manifest，形成孤儿对象或无法恢复的半成品。

**证据**：[进程内 job 状态](../go/internal/adminweb/job.go:27)、[后台发布闭包](../go/internal/adminweb/publish.go:113)。

**建议**：将发布任务、状态、进度和 lease 持久化到 PostgreSQL；使用临时对象键，只有 installer 校验完成后才原子发布 manifest；启动时扫描并恢复超时任务，或明确标记为失败并清理临时对象。

## 已确认的防护

- 应用安装包在发布和 Agent 下载路径均使用 SHA-256；对象键按 app/version 固定命名。
- application task 有 claim、lease renew、cancel 和 finish 状态，Agent 主同步循环不会等待安装器完成。
- API 端日志有大小限制、状态 body 有上限；设备 token 未授权会触发重新 enrol。
- 管理后台默认角色/CSRF 检查和应用审核流程已存在。
- 当前未提交的更新器改动已删除成功更新后的 `agent.exe.old-*`，但应保留到新服务启动成功之后；不要为了“不保留旧文件”而提前删除回滚副本。

## 建议执行顺序

1. 先修 C-01，补端到端安装任务测试；否则后台软件安装功能仍不可用。
2. 修 H-01/H-02/H-05：服务端时间、旧 Agent bootstrap、恢复码原子消费。
3. 修 H-03/H-04/H-06：Windows 路径/进程树/ACL，并在真实 Windows 标准用户镜像上验证。
4. 将发布状态限制为 accepted/stable，再处理 SSRF、采集上限、日志轮转和注册策略。
