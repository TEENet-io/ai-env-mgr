# 账单对账嵌入 Admin 实施计划

版本：V1（方案评审稿）
范围：第一阶段做 AWS Bedrock 和 LiteLLM 的对账；架构上给 Azure、GCP 留好位置。
分工原则：
- Admin 负责管理、排队和展示；
- 对账引擎负责读取数据和计算；
- 凭据不进页面，也不进数据库。

## 先认识几个词

| 词 | 意思 |
|---|---|
| 对账 | 把云厂商账单上的费用，和我们网关自己记录的费用逐项比对，找出差额和异常。 |
| Admin | 我们的管理后台，用 Go 编写。 |
| AWS Bedrock | AWS 的 AI 模型服务，是第一阶段要对账的供应商。 |
| LiteLLM | 我们的 AI 模型网关，员工的模型调用经过它，它会记录每次调用的费用。 |
| `billing-reconcile` | 现有的独立对账程序，用 Python 编写。 |
| 执行器（Worker） | 在后台实际跑对账的独立进程，本文中"执行器"和"Worker"指同一个东西。 |
| CUR | AWS 的费用明细报告（Cost and Usage Report），存在 S3 上。 |
| S3 | AWS 的云存储。 |
| Parquet | CUR 使用的一种数据文件格式。 |
| manifest | CUR 附带的清单文件，说明本期账单包含哪些文件、何时更新。 |
| AK/SK | AWS 的访问密钥（Access Key / Secret Key），相当于账号密码。 |
| DSN | 数据库连接串，里面包含地址、账号和密码。 |
| 账期 | 账单所属的月份，格式为 `YYYY-MM`。 |
| payload | 创建任务时附带的参数。 |
| 幂等键 | 任务的唯一标识。同一个键只会执行一次，用来防止重复执行。 |
| 快照 | 某次对账时保存下来的输入数据副本。"激活快照"指把某份快照设为当前使用的版本。 |
| 租约 | 执行器领取任务后持有的"占用权"，过期或丢失时任务可以被别的执行器接管。 |
| systemd timer | Linux 的定时任务，目前用它每天自动运行独立对账程序。 |
| SKU | 云厂商账单里的计费项目编号。 |
| 路由配置 | 记录每个模型调用走哪个供应商、哪个区域的配置。 |

## 1. 目标

把现有的独立程序 `billing-reconcile` 接入 Admin，让管理员在一个界面里就能：

- 手动发起某个月份的对账；
- 查看这次运行的状态和历史记录；
- 查看 AWS 供应商费用、LiteLLM 费用、差额和异常；
- 下载或查看详细报告；
- 在任务中心统一看到对账任务；
- 每日自动对账、失败重试和差额告警，都交给统一的任务机制管理。

第一阶段只启用 AWS Bedrock。Azure 和 GCP 只接入统一接口，这一阶段不改它们的生产账单配置。

## 2. 不采用的方案

- 不把 Python 对账代码直接编译进 Go 写的 Admin。
- 不在网页请求（HTTP 请求）里当场跑完整的账单下载和解析。

原因：

1. 下载 CUR、解析 Parquet、查询 LiteLLM 可能要好几分钟。不能让 Admin 的请求卡住，也不能影响机器控制功能。
2. 不应让 Admin 程序悄悄依赖 Python 和它的虚拟环境才能运行。
3. 不应因此让所有 Admin 进程都能拿到 AWS AK/SK、LiteLLM DSN 等凭据。
4. 对账失败后要能重试、能被别的进程接管、能审计。不能只靠一个 HTTP 请求从开始到结束的那段时间。

## 3. 推荐架构

```text
Admin UI
  │  POST /reconciliation/run
  ▼
Admin PostgreSQL: tasks(kind=billing_reconcile)
  │
  ├── Admin 任务中心：等待、进行中、完成、异常
  │
  ▼
Billing Reconcile Worker
  │  独立 Unix 用户、独立凭据、独立 Python 环境
  │
  ├── AWS CUR 2.0 S3（只读）
  ├── LiteLLM PostgreSQL 受限视图（只读）
  ├── billing-reconcile SQLite（快照、输入、明细）
  └── 报告目录（Markdown / CSV / JSON）
  │
  ▼
Admin PostgreSQL 汇总结果 + 认证后的报告查看接口
```

流程说明：

1. 管理员在 Admin 页面点击发起对账，Admin 在数据库的任务表里写入一条 `billing_reconcile` 任务。
2. 任务中心显示这条任务的状态。
3. 执行器领取任务。它用独立的系统用户、独立的凭据和独立的 Python 环境运行。
4. 执行器只读 AWS 的 CUR 账单和 LiteLLM 数据库的受限视图，把快照、输入和明细存进自己的 SQLite，把报告写进报告目录。
5. 执行器把汇总结果写回 Admin 数据库。报告要登录后才能通过接口查看。

执行器可以先和 Admin 部署在同一台 Linux 服务器上，但必须是独立进程、独立系统用户。以后需要扩容时，可以把执行器搬到单独的机器上，Admin 页面和任务协议都不用改。

## 4. 任务设计

新增任务类型：

```text
billing_reconcile
```

不要复用现有的 `reconcile` 类型，它是用来核对网关状态的。

任务 payload 只放业务参数，不放凭据和文件路径：

```json
{
  "provider": "aws",
  "period": "2026-09",
  "scope": "bedrock",
  "requested_by": "admin"
}
```

幂等键：

```text
billing_reconcile:aws:bedrock:2026-09
```

防重复规则：

- 同一供应商、同一范围、同一账期已经有成功的任务时，默认直接返回已有结果。
- 失败的任务，管理员可以手动明确地重试。
- 同一个任务正在运行时，不能再启动一次。

任务状态沿用现有的任务队列：

```text
pending → running → succeeded
                   ├→ retry_wait → running
                   └→ failed
```

（`pending` 等待中，`running` 运行中，`succeeded` 成功，`retry_wait` 等待重试，`failed` 失败。）

账单还没出来时，对账要等，这不算系统故障。这种情况用单独的状态 `waiting_for_bill`（等待账单），避免反复重试造成误报。

## 5. 数据库改造

### 5.1 对账运行汇总表

新增表 `billing_reconcile_runs`：

| 字段 | 说明 |
|---|---|
| id | 对账运行 ID |
| task_id | 对应的 Admin 任务 |
| provider | `aws` / `azure` / `gcp` |
| scope | 第一阶段为 `bedrock` |
| period | `YYYY-MM` |
| status | running / completed / failed / waiting_for_bill |
| provider_cost | 按同一分组从供应商账单算出的费用，用来和网关记录的费用（`gateway_cost`）比对 |
| gateway_cost | LiteLLM 费用 |
| difference | 供应商费用减 LiteLLM 费用 |
| relative_difference | 相对差额 |
| issue_count | 问题数量 |
| report_path | 受控的报告引用，不直接暴露文件系统路径 |
| report_hash | 报告的完整性哈希，用来确认报告没被改过 |
| mapping_hash | 路由配置的哈希 |
| source_updated_at | 账单来源的更新时间 |
| started_at / finished_at | 开始和结束时间 |
| error | 去掉敏感信息后的错误信息 |

### 5.2 问题摘要表

新增表 `billing_reconcile_issues`，只存页面要显示的摘要：

- 问题类型：未匹配、未知路由、账单过期、数量差异、价格差异、测试/未托管用量；
- 供应商、账期、模型、区域、SKU；
- 数量、费用、差额；
- 是否已确认、确认人、确认时间；
- 在详情文件中对应的行位置。

原始 Parquet、LiteLLM 输入快照和完整 CSV 不写进 Admin 的主表，继续由对账程序存在受限目录里。

## 6. 对账执行器改造

在现有 `billing-reconcile` 上增加"Admin 集成模式"，流程如下：

1. 接收任务 ID、供应商（provider）、账期（period）；
2. 从受限的配置里读取 AWS AK/SK、LiteLLM DSN 和路由配置；
3. 运行现有命令行（CLI）的对账逻辑；
4. 最后输出一份程序可以读取的 JSON 摘要；
5. 把摘要、问题统计和报告引用传回 Admin；
6. 详细报告仍然写到专用目录；
7. 退出码保持现有含义：成功、等待账单、配置或数据来源失败，三者分别用不同的退出码。

执行器必须做到：

- 用 `exec.CommandContext` 或同等的受控方式启动进程；
- 禁止拼接 shell 命令，禁止把用户输入直接当成命令参数；
- 设置最长运行时间；
- 输出里不能出现 AK/SK、DSN 密码、完整连接串和请求内容；
- 支持取消任务；租约丢失后要安全停止；
- 同一 provider + period 使用现有的锁，防止同时下载、重复激活快照。

## 7. Admin 页面

### 7.1 导航

在「用量」下新增页签：

```text
用量 · 调用明细 · 费用对账
```

### 7.2 对账首页

页面分四块：

1. **当前状态**：AWS Bedrock、本月账期、最近一次运行时间、账单更新时间；
2. **金额卡片**：AWS 费用、LiteLLM 费用、差额、差额比例；
3. **问题摘要**：未托管用量、未知路由、账单过期、价格差异、数量差异；
4. **历史运行**：可按供应商、账期、状态筛选。默认只显示最近的记录，其余折叠。

操作按钮：

- 「运行本月对账」
- 「运行上月对账」
- 「重新运行」
- 「查看报告」
- 「导出摘要」

点击按钮后只创建任务，页面马上返回，不等账单下载或数据库查询完成。

### 7.3 任务中心

任务中心新增这类任务卡片：

```text
费用对账 · AWS Bedrock · 2026-09
```

卡片显示状态、账期、运行耗时、差额、问题数量和最近一次错误。详细历史默认折叠，每个状态栏只显示第一条。

## 8. 自动调度

第一阶段保留两步：

1. Admin 每天为上一账期和当前账期各创建一个对账任务；
2. 靠任务的幂等键防止同一账期重复执行。

验收完成后，停用原来独立运行的 systemd timer。否则 Admin 调度和旧 timer 会各跑一份对账。

刚切换的那段时间，可以暂时保留旧 timer，但必须设成只读观察模式，不能和 Admin 同时写同一份运行记录。

## 9. 告警规则

对账结果接入现有的告警中心。以下情况告警：

- 对账任务连续失败；
- 等账单的时间超出预期；
- manifest 或账单快照过期；
- 差额的绝对值超过阈值；
- 差额比例超过阈值；
- 出现未知路由，或不经过我们网关的 Bedrock 用量（未托管用量）。

告警必须区分"账单还没出来"和"账单真的有差异"。AWS CUR 有延迟，不能因为延迟就判定为漏账。

## 10. 权限和凭据

### Admin 角色

| 角色 | 查看汇总 | 发起/重跑 | 确认差异 | 查看明细 |
|---|---:|---:|---:|---:|
| viewer | 是 | 否 | 否 | 脱敏摘要 |
| operator | 是 | 是 | 否 | 是 |
| security | 是 | 否 | 是 | 是 |
| admin | 是 | 是 | 是 | 是 |

### 凭据边界

- AWS 只读 AK/SK 留在 `/etc/billing-reconcile.env`，文件权限 600（只有文件所有者能读写）；
- LiteLLM 用单独的数据库只读账号和受限视图；
- Admin 页面不显示、不编辑、不回显任何凭据；
- 任务 payload、审计日志和错误信息里不能有凭据；
- AWS 只读取 Bedrock 中可以比对的账单。其他 AWS 费用留在供应商报告里，但不算进和 LiteLLM 的差额。

## 11. 实施阶段

### Phase 0：设计接口和数据库

- 定义 `billing_reconcile` 任务的 payload；
- 新增运行汇总表和问题摘要表的数据库迁移；
- 定义执行器输出 JSON 的格式；
- 确定报告目录和访问权限。

完成条件：迁移可以回滚；现有任务和对账 CLI 的测试不受影响。

### Phase 1：AWS 手动对账

- Admin 新增对账页；
- 增加"运行本月/上月"按钮；
- Worker 调用现有的 Python 对账程序；
- 任务中心显示运行状态；
- 展示费用、差额和问题数量。

完成条件：用 2026-09 的样本和线上 CUR 各跑一次，结果和现有独立程序一致。

### Phase 2：报告和告警

- 增加报告查看和下载；
- 增加差额告警和过期告警；
- 增加重跑、失败原因和审计记录；
- 验证凭据不会写进日志。

完成条件：人为制造失败、等待账单、超阈值三种情况，页面和告警状态都正确。

### Phase 3：切换到自动调度

- Admin 每天为当月和上月账期排队任务；
- 观察一周，看重复执行、延迟和失败率；
- 停用旧的 systemd timer；
- 保留回退脚本。

完成条件：连续 7 天没有重复账期、任务丢失或报告覆盖错误。

### Phase 4：Azure / GCP

- 复用供应商适配器（provider 适配器）接口；
- 每家供应商用独立的凭据和账期状态；
- 页面按供应商筛选，不把不同币种、不同计费口径的费用混在一起；
- 用真实的脱敏样本验证通过后，再启用生产调度。

## 12. 验收清单

- [ ] Admin 能为 AWS 的指定月份创建对账任务；
- [ ] 请求马上返回不卡住，任务中心能看到"进行中"状态；
- [ ] Worker 重启后任务能恢复，不会重复激活快照；
- [ ] 同一账期重复点击，不会生成重复的运行记录；
- [ ] AWS 费用、LiteLLM 费用、差额和问题数量与独立程序一致；
- [ ] 失败、等待账单、超阈值都有明确的状态；
- [ ] 报告只有已登录且有权限的管理员能访问；
- [ ] 日志和审计记录里没有 AK/SK、DSN 密码或完整连接串；
- [ ] 停用旧 systemd timer 后，Admin 调度仍能正常补跑；
- [ ] 不影响机器同步、软件安装、网关开户和现有任务队列；
- [ ] Azure/GCP 还没配置时，不会显示成"对账正常"或零费用。

## 13. 回滚方案

1. 停止 Admin 的 `billing_reconcile` 调度，不再创建新任务；
2. 保留并单独启用现有的 `billing-reconcile.timer`；
3. 把 Admin 页面和任务处理程序回滚到旧版本；
4. 不删除 SQLite 快照、报告和 Admin 汇总记录；
5. 已完成的对账结果保持只读，避免回滚后历史结果消失。
