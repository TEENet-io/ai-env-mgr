# AI 工作间数据目录表（客户合规确认稿）

版本：2026-09-26
范围：Windows Agent、管理后台（Admin 控制台）、PostgreSQL 数据库、阿里云 OSS 和 SLS，以及和 LiteLLM 网关之间交换的数据。

阅读前请注意：

- 本表写的是**根据当前代码和部署配置能确认的行为**。
- 「建议 Policy」（建议的保留和删除策略）是等客户确认的目标，不代表已经实现，也不构成法律结论。
- 实际云资源的生命周期、地域、备份和供应商那边的留存情况，要在交付前逐项核实。

## 先认识几个词

| 词 | 意思 |
|---|---|
| Agent | 装在每台 Windows 云电脑上的管理程序。负责接收配置、安装软件、上报状态，开启采集后也负责上传会话文件。 |
| 管理后台（Admin） | 管理员使用的网页控制台。 |
| Worker | 管理后台里定时在后台运行的任务程序，例如每天清理过期数据。 |
| PostgreSQL | 管理后台使用的数据库。 |
| OSS | 阿里云的云存储，存放上传的文件、安装包和数据库备份。 |
| SLS | 阿里云的日志服务，存放运维日志和审计日志。 |
| LiteLLM 网关 | 员工调用 AI 模型时经过的中转服务。员工的令牌在这里校验，请求从这里转给模型服务商。 |
| 令牌 | 访问凭证，相当于一把钥匙。网关令牌用来调用模型，设备令牌用来让机器连后台。 |
| 会话采集 | 把员工电脑上 Codex（AI 编程助手）的对话记录文件上传到 OSS。 |
| TTL | 数据的自动过期时间。到期后系统自动删除。 |
| 去重状态 | Agent 在本机记下哪些文件已经上传过，避免重复上传。 |
| 软删除 | 只把记录标记为“已删除”，数据本身还留在数据库里。 |
| 去标识 | 去掉能认出具体某个人的信息。 |
| profile | Windows 上每个用户自己的文件夹。 |
| 全链路删除 | 把一份数据在所有存放位置（数据库、云存储、备份、本机、供应商等）都删掉。 |
| 前缀 | OSS 里的“文件夹路径”。 |
| UTC | 世界协调时间，比北京时间晚 8 小时。 |
| DPA | 数据处理协议，规定服务商怎样处理客户数据。 |

## 重要前提和边界

- **关闭采集只是不再上传新数据。** 以下内容都不会被删除：Windows 上的源文件、OSS 上已上传的文件、Agent 本地的去重状态、备份。
- `collectSince`（采集起始日期）按文件最后修改日期（UTC）筛选要上传的文件。它留空时，会把能看到的历史文件全部补传。它不是保留期限。
- 会话采集默认关闭。开启后上传原文，**不做脱敏**。内容可能包括：提示词、模型回复、文件内容和路径，以及用户自己粘贴进去的个人信息或密钥。不能把它当成普通的运行日志对待。
- **共享机器上有一个已知问题。** Agent 会扫描机器上每个普通本地账户（跳过内置的 Administrator）。但后台只接受机器当前绑定员工的上传。结果是：其他账户的文件可能被本机读取，但上传会被拒绝。**在确定客户允许采集哪些人、并修好这个问题之前，不应开启采集。**
- 旧文档里的“离职满 7 天”是**清理提醒**，不会自动删除任何东西。另有一条独立的规则：自己注册、从没绑定过员工的设备，7 天后自动注销。
- 删除数据时，要同时考虑这些位置：在线数据库、OSS/SLS、副本和备份、Windows 原始文件、网关和模型供应商。只在管理后台里删掉账号或机器，不等于全链路删除。

## 数据目录

说明：

- 标为「建议」的天数，只供客户选择。
- 没有写明“已实现自动删除”的条目，目前都不能承诺到期自动删除。

### D01｜Codex 会话原文

- **来源：** Windows 用户目录下的 `.codex/sessions/**/rollout-*.jsonl`。
- **内容和用途：** 提示词、模型回复、工具调用等原始交互记录。只在采集开启时上传。
- **存在哪里：**
  - 源文件：员工的 Windows profile；
  - 副本：OSS `agent_workdir/{windows_user}/data_collect/.codex/sessions/...`；
  - 去重记录：`C:\ProgramData\AIEnvMgr\collect-state.json`。
- **现在怎么保留和删除：**
  - 默认不上传。
  - 目前 OSS 没有设置自动过期规则，也没有按人自动清理。
  - 删除本地源文件，不会删除 OSS 上的副本。
  - 如果采集还开着、源文件也还在，删掉 OSS 副本后可能会被再次上传。
- **建议策略（待客户确认）：**
  - 客户从 **30 / 90 / 180 天** 中选一个，从上传成功时开始计算。
  - OSS 过期删除至少每天执行一次。
  - 删除某个人的数据时，先暂停这个人的采集或绑定，再删 OSS 和本地源文件，防止数据又被传上来。

### D02｜Codex 全局界面状态

- **来源：** `.codex/.codex-global-state.json`。
- **内容和用途：** 会话的归档状态、会话名称、工作目录和时间戳。可能暴露项目名称。
- **存在哪里：** 和 D01 一样，在 Windows profile 和 OSS `data_collect` 前缀下。
- **现在怎么保留和删除：** 和 D01 一样，没有到期自动清理。
- **建议策略（待客户确认）：** 原则上和 D01 期限相同。如果客户不需要归档状态，应把它从采集白名单里去掉，并清理已上传的副本。

### D03｜采集控制和去重状态

- **来源：** 管理后台的策略；Agent 记录的文件签名。
- **内容和用途：**
  - 策略：`collectEnabled`（是否开启采集）、起始日期、静默秒数；
  - 文件签名：源文件路径、mtime（最后修改时间）、size（文件大小）。
- **存在哪里：** PostgreSQL `policy_versions`/`policy_current`；Agent 的 `collect-state.json`；策略在 Agent 本地还有缓存。
- **现在怎么保留和删除：** 策略历史和去重文件都没有按时间清理。去重状态不含对话正文，但含本地文件的完整路径。
- **建议策略（待客户确认）：** 关闭采集时停止上传。建议机器注销或重装时清理本地去重文件。策略历史按 D10 审计的期限处理。

### D04｜员工身份和授权

- **来源：** 管理后台的开户、绑定和模型授权操作。
- **内容和用途：** Windows 用户名、姓名/部门/邮箱、Codex 账户备注、机器绑定、模型白名单、预算。
- **存在哪里：** PostgreSQL `employees`、`device_bindings`、`employee_models`、`employee_quotas` 等表。
- **现在怎么保留和删除：**
  - 关户主要是停用。
  - 后台的“删除账号”是软删除，记录和历史都还在。
  - 7 天只是清理提醒。
- **建议策略（待客户确认）：** 业务记录在员工离职后 **30 天** 去标识或清理。账务上必须保留的最少字段另按 D08 处理。例外情况按客户合同和法务意见确定。

### D05｜网关令牌和配置包

- **来源：** 管理后台和 LiteLLM 创建。
- **内容和用途：** 网关 API 令牌（Gateway API token）、模型和网关配置。
- **存在哪里：**
  - PostgreSQL `credential_versions`（加密存储）、`credential_bundles`（ZIP 包）；
  - 员工 Windows profile 里的 Codex 配置；
  - 兼容旧版本期间，OSS 上可能还有 `credentials.zip`。
- **现在怎么保留和删除：**
  - 关户会撤销网关令牌、停用当前凭证，并清理配置包。
  - **已停用的加密凭证版本没有自动删除期限。**
  - 离线 Windows 机器上的文件，要等设备收到撤销指令，或者实例被销毁，才会处理掉。
- **建议策略（待客户确认）：** 撤销立即生效。已停用的加密凭证和旧配置包在 **7–30 天** 内删除。设备离线超过期限时，封禁令牌，并按机器销毁流程处理。要检查 OSS 上兼容旧版本留下的文件。

### D06｜设备身份和状态

- **来源：** Agent 上报。
- **内容和用途：** 主机名、用户、IP 或注册来源、Agent 版本、心跳（定时报到）、策略和凭证状态、错误等。
- **存在哪里：** PostgreSQL `devices`、`device_reported_state`、`device_tokens`、`device_bindings`；Agent 本地的设备令牌。
- **现在怎么保留和删除：**
  - 自己注册、从没绑定过的设备，7 天后由每日任务注销。
  - 已绑定的设备不会到期自动删除。
  - 注销设备会撤销令牌和相关的当前状态，但不会删除审计记录和备份。
- **建议策略（待客户确认）：** 已退役的设备在 **30 天** 内注销，并清理设备令牌和状态，只保留必要的审计引用。由客户确认怎样算机器离线、怎样算退役。

### D07｜Agent 和系统运行日志

- **来源：** Agent、管理后台、网关。
- **内容和用途：** 同步、安装错误、请求状态。错误信息里可能有路径、用户名或供应商的返回内容。
- **存在哪里：**
  - Windows 上的 `C:\ProgramData\AIEnvMgr\agent.log` 和 `.1`；
  - PostgreSQL `devices.log_tail`（只存最近 64 KiB，新的覆盖旧的）；
  - 管理后台和网关的日志发到 SLS `ops`。
- **现在怎么保留和删除：**
  - Agent 本地日志单个文件到 4 MiB 就换新文件（轮转），旧的只留一份。
  - 数据库里的日志尾不断被覆盖，设备注销前一直保留。
  - SLS `ops` 设置的 TTL 是 **30 天**。
- **建议策略（待客户确认）：** 运维日志保留 **30 天**。到期后：SLS 由 TTL 自动删除；数据库日志尾随设备注销一起清除；本地日志随镜像或机器销毁一起清除。不得把会话正文写进运维日志。

### D08｜模型调用和费用记录

- **来源：** LiteLLM 的调用事件。
- **内容和用途：** 员工或令牌别名、模型、时间、token 数（模型计费用的文字单位数量）、费用、状态。用于额度管理和对账。
- **存在哪里：**
  - SLS `audit` 里的 `llm_call` 事件；
  - PostgreSQL `usage_daily`（按天汇总）；
  - LiteLLM 自己的数据库和日志，另外核实。
- **现在怎么保留和删除：**
  - SLS `audit` 设置的 TTL 是 **365 天**。
  - `usage_daily` 不会到期自动删除。
  - LiteLLM 自己是否保留原始请求和回复、保留多久，还没核实。
- **建议策略（待客户确认）：** 调用明细保留 **365 天**，按天的费用汇总保留 **24 个月**。超过期限后先汇总或去标识，再删除。单独核对 AWS/GCP/Azure 和 LiteLLM 在供应商那边的保留期限。

### D09｜业务任务和安装记录

- **来源：** 管理后台的操作；Agent 的回报。
- **内容和用途：** 软件安装、发布、失败信息、重试和执行时间。
- **存在哪里：** PostgreSQL `tasks`、`task_attempts`、`application_tasks`、`release_*`；Windows 上暂存的安装包和安装日志。
- **现在怎么保留和删除：**
  - 任务历史没有统一的自动过期时间。
  - 安装包和发布包放在 OSS `_apps/`、`_agent/`、`_codex/`，目前主要靠管理员手动删除。
- **建议策略（待客户确认）：**
  - 任务明细保留 **90–365 天**。
  - 可执行的安装包只保留正在用的版本，加 **1 个验证过的回滚版本**；退役后 **90 天** 清理。
  - 安装日志保留 **30 天**。
  - 任何清理前，先确认没有正在进行的任务。

### D10｜管理审计

- **来源：** 管理后台、Agent 和 Worker 的操作。
- **内容和用途：** 操作人、操作对象、修改前后的值（已脱敏）、结果、时间、请求 ID。
- **存在哪里：** PostgreSQL `audit_events`/`event_deliveries`；SLS `audit` 里有一份副本。
- **现在怎么保留和删除：**
  - SLS `audit` 设置的 TTL 是 **365 天**。
  - PostgreSQL 里的审计表是正式记录，不会到期自动删除。
  - D12 的备份里也可能有审计副本。
- **建议策略（待客户确认）：** 至少保留 **365 天**，具体由客户合同和适用的要求决定。如果允许删除，按月分区或分批清理，并把删除操作本身记入审计。不能只删 SLS 上的副本。

### D11｜管理员认证数据

- **来源：** 管理后台登录。
- **内容和用途：** 账号、密码哈希（不可还原的加密结果）、MFA（多因素验证）密文和恢复码哈希、会话哈希、登录 IP 和浏览器信息（UA）、登录失败记录。
- **存在哪里：** PostgreSQL `admin_principals`、`admin_sessions`、`admin_login_attempts`。
- **现在怎么保留和删除：** 过期的登录会话由 Worker 清理。管理员账号和登录尝试记录的长期清理周期，还要核实或补上。
- **建议策略（待客户确认）：** 登录失败记录保留 **30–90 天**。停用的管理员账号在业务确认后 **30 天** 清理。撤销权限时，密码和 MFA 同时作废。审计记录另按 D10。

### D12｜数据库备份

- **来源：** 服务器每天运行 `pg_dump` 导出整个数据库。
- **内容和用途：** D03–D11 在某个时间点的副本，可能包含加密凭证、日志和会话尾。不包含 OSS 上的会话文件正文。
- **存在哪里：**
  - 备份过程中，临时的 gzip 压缩文件放在后台服务器上；
  - 上传成功后放在 OSS `agent_workdir/_backup/aienv-YYYYMMDD.sql.gz`。
- **现在怎么保留和删除：**
  - 定时任务默认每天 UTC 02:00 运行。
  - 上传成功后删除服务器上的临时文件。
  - 每次成功上传新备份后，清理 OSS 上超过 **30 天** 的 `.sql.gz` 备份。
- **建议策略（待客户确认）：** 保持 **30 天**，或由客户选别的期限。删除某一个人的数据时，没法马上从已有的整库备份里单独删掉。要向客户说明“备份到期后自然删除”；恢复备份后，还要把删除清单重新执行一遍。

### D13｜模型服务商那边的数据

- **来源：** 经 LiteLLM 转发到 AWS Bedrock、Google Vertex AI、Azure 的请求。
- **内容和用途：** 用户提交的提示词、附件和上下文、模型输出（取决于实际请求）。
- **存在哪里：** 第三方云服务的处理环境；LiteLLM 的转发路径上。
- **现在怎么保留和删除：** **本项目的代码无法证明**云厂商是否存储这些数据、存多久、是否用于训练、是否跨境处理。不能把我们自己 OSS/SLS 的 TTL 当成供应商的承诺。
- **建议策略（待客户确认）：** 按每个客户、每个云账号、每个模型，逐项取得合同、DPA、地域、留存和训练使用说明。客户确认前，不得写“零留存”。

## 建议的删除顺序

1. **停止新增。** 关闭采集，或取消该员工/设备的上传资格。确认在线和离线的机器都不会在恢复后补传。这一步对 D01/D02 尤其重要。
2. **立即撤权。** 撤销 LiteLLM 令牌和设备令牌，作废还没完成的任务。确认管理后台和网关的状态一致。
3. **删除在线副本。** 按员工或设备标识清理以下内容：OSS `data_collect`、兼容旧版本的凭证文件、数据库中可以删的记录、Agent 本地的凭证和采集状态、云电脑磁盘。记录删除的数量、失败项和操作人。
4. **处理衍生数据。** 核对 SLS、按天的费用汇总、审计、发布任务历史，以及 LiteLLM 和云供应商那边的数据。按已确认的例外期限清理或去标识。
5. **处理备份。** 备份没法由一个人直接修改。记录最长还剩 30 天的到期窗口。如果恢复了较早的备份，必须把删除清单重新执行一遍，防止数据“复活”。
6. **复核并留证据。** 确认：OSS 对应前缀已经清空、在线数据库里没有不该留的记录、令牌已失效、机器和本地副本已处理。删除操作本身要记入审计，但证明材料里不要写被删掉的内容。

系统目前**还没有实现**以下能力：跨多个存储位置的一键删除、OSS 会话数据的自动过期、删除回执。所以在这些能力上线并验收之前，客户不能依据本表得到“到期自动删除全部数据”的承诺。

## 需要客户逐项签字确认

| 事项 | 待确定的选项 / 交付前要提供的证据 |
|---|---|
| 是否开启原始会话采集 | 默认关闭。如果开启，要确认：目的、涉及哪些员工、共享机器怎么处理、是否采集 D02、是否允许补传历史数据 |
| 会话保留期限 | D01/D02 从 30 / 90 / 180 天中选，或由客户指定；明确从什么时候开始计算，以及暂停采集和法律保留的例外 |
| 费用和审计的保留期限 | D08/D10 分别确认保存几年、哪些内容要去标识、谁可以查询和导出 |
| 数据地域和所属账号 | 核对 OSS Bucket（存储空间）、SLS Project（日志项目）、PostgreSQL 和备份、LiteLLM 以及 AWS/GCP/Azure 的实际地域和账号归属 |
| 删除时限和备份窗口 | 明确在线副本多久内删除、备份自然到期的 30 天窗口、恢复备份后怎样重新删除 |
| 供应商处理条款 | 逐个供应商确认：请求内容是否留存、是否用于训练、有哪些下游处理方、审计和删除证明。不能凭平台配置推断 |
| 权限和导出 | 确认哪些管理员能看会话原文、导出是否需要审批或加水印、访问日志保存多久 |
