# WorkBuddy 与豆包相关工具采集可行性评估（初稿）

版本：2026-10-19。

**结论先说：** 这是一份基于公开资料的评估，**采集还没有打通**。我们还没拿到目标产品的确切版本、测试账号和样本数据。

下周（2026-10-26 至 10-30）先确认产品、做小范围受控试验，再决定开发什么、什么时候做。对客户能承诺的服务范围见[三种客户服务方案](三种客户服务方案.md)。

## 先认识几个词

| 词 | 意思 |
|---|---|
| 采集 | 把员工使用 AI 工具产生的记录（对话、任务、文件等）收集上来。 |
| Agent | 装在每台云电脑上的管理程序，采集功能就在它里面。 |
| OSS | 阿里云的对象存储，采集到的文件上传到这里。 |
| API | 产品官方提供的程序接口，第三方可以按规定调用它读取数据。 |
| 会话 ID | 一次对话的编号。很多接口要先知道编号才能取消息。 |
| 用量指标 | 统计数字，例如每人对话了多少次。不包含对话内容本身。 |
| 会话原文 | 对话的具体内容：用户输入了什么、AI 回复了什么。 |
| 抓包 | 截获网络传输的数据。这里指不走官方接口、偷偷读取通信内容。 |

## 1. 先确认讨论的是哪个产品

### WorkBuddy

"WorkBuddy"暂时理解为**腾讯 WorkBuddy AI 桌面办公工作台**。它和 CodeBuddy 编程工具、WorkBuddy Enterprise 管理后台是不同的东西，数据要从不同地方取。

官方资料能说明什么：

- [腾讯产品介绍](https://cloud.tencent.com/product/workbuddy)说，桌面版可以处理对话、任务和本地文件。
- [系统设置文档](https://intl.cloud.tencent.com/zh/document/product/1316/84502)说，可以查看存放对话记录的本地缓存目录，以及任务记录保留多久。

这证明**电脑本地确实有相关数据**。但不能证明三件事：缓存的格式稳定；第三方能长期读取；缓存里包含所有云端任务。

### 豆包相关工具

"豆包相关工具"还不能当成一个产品看。至少要在下面几个里确定是哪个：

- 豆包 PC 客户端或浏览器
- 扣子（Coze）智能体
- TRAE 编程工具
- 火山方舟模型 API

它们的数据存放位置、授权方式和接口都不一样。例如[豆包桌面版](https://www.doubao.com/download/desktop)和 [TRAE](https://docs.trae.cn/ide_intro-to-llm) 是两个产品；[扣子消息日志](https://docs.coze.cn/guides_queries)也不等于豆包客户端的聊天记录。

客户需要提供会上说的那个产品的：名称或链接、版本、在哪个端使用、账号类型、想采集哪些字段。**产品没确定之前，不能对外说"支持豆包采集"。**

## 2. 目前能确认的采集途径

| 对象 | 官方资料能确认什么 | 目前判断能不能采集 | 难度和关键缺口 |
|---|---|---|---|
| **WorkBuddy AI 桌面版** | 设置界面能看到本地缓存目录和任务记录保留选项；任务产出的文件放在工作空间里（[官方设置说明](https://intl.cloud.tencent.com/zh/document/product/1316/84502)）。官方的诊断日志可能含对话和设备信息，但它是给故障反馈用的（[官方 FAQ](https://intl.cloud.tencent.com/zh/document/product/1316/84555)）。 | **有条件可行，还没验证。** 先在获得授权的测试机上确认：缓存里能否稳定分出会话、输入、输出、时间和附件。任务产出的文件可以单独按目录采集。不能把诊断用的 ZIP 包当作正式的会话导出接口。 | 中高。文件格式未知，升级后是否兼容未知；不确定是否覆盖云端任务；缓存里可能混有密钥和个人资料。 |
| **WorkBuddy Enterprise（企业版）** | 企业版有按成员统计的对话次数等数据，可以从管理后台导出 Excel。这是用量指标，不是会话原文（[官方明细数据](https://intl.cloud.tencent.com/zh/document/product/1316/84530)）。企业数据处理说明里列出了对话日志包含会话、输入、模型、请求者和时间戳等（[官方协议](https://intl.cloud.tencent.com/zh/document/product/1316/82098)）。 | **用量指标可以导出；会话原文能否自动导出，要找供应商确认。** 协议列出了腾讯会处理哪些数据，不等于公开提供了读取这些字段的 API。 | 用量指标：低到中。会话原文：取决于企业版权限、有没有导出功能或 API、合同怎么约定。 |
| **豆包 PC 客户端或浏览器** | 官方产品包括桌面 AI、网页问答、截图和文件交互。[隐私政策](https://www.doubao.com/legal/privacy)说明不同入口会处理文本、语音、图片、文件和网页内容。 | **没找到可以拿来承诺的、稳定且经授权的全量会话导出 API。** 能不能手动导出、能导出哪些字段，要在指定版本的测试账号上核实。不能把浏览器抓包、绕过登录或非官方插件当作默认方案。 | 高，或者未知。不清楚哪些内容在本地、哪些在云端；版本会变；数据是否完整未知；还要看产品使用条款。 |
| **扣子（Coze）里客户自己建的智能体** | 官方[消息列表 API](https://docs.coze.cn/developer_guides_list_chat_messages) 可以按已知的会话 ID 取消息。[消息日志](https://docs.coze.cn/guides_queries)可以导出 CSV，但受套餐、权限和条数限制，而且官方明确说**暂不支持豆包渠道智能体的消息日志**。 | **有条件可行。** 条件是：客户拥有这个智能体、有 Token（访问令牌）和会话 ID，并且目标渠道和套餐支持。满足时，可以通过授权的 API 或 CSV 采集。不能由此推断能拿到豆包客户端的聊天记录。 | 中。要处理身份验证、找出有哪些会话、分页读取、套餐限制、渠道缺口和字段对应。 |
| **TRAE 或火山方舟** | TRAE 是编程工具，火山方舟是模型服务。它们和豆包 PC、扣子不是一回事。 | **要先确认会上说的是不是它们。** 如果是客户自己通过 API 调用模型，优先在客户的应用或网关那一侧记录经授权的请求元数据（描述请求的基本信息）。客户端自己保存的历史记录另外评估。 | 未定。要先确定目标产品和调用方式，才能估。 |

说明：

- 表中"没找到"只代表这次查官方资料时，没发现能直接对接的公开功能。**不是说产品一定没有这个功能。** 特别是 WorkBuddy 企业版对外开放了什么、豆包客户端里能不能导出，需要用供应商或客户的账号实际测试。
- 对第三方网页或客户端做自动抓取之前，必须核对授权和产品条款。[豆包用户协议](https://www.doubao.com/legal/terms)限制了未经许可的抓取等行为。

## 3. 现有采集程序还差什么

### 现在能采什么

- [Agent 的文件查找逻辑](../go/cmd/agent/collect.go)只采两类文件：`.codex/sessions/**/rollout-*.jsonl` 和 `.codex/.codex-global-state.json`（都是 Codex 的记录）。**不采 WorkBuddy、豆包、扣子或 TRAE。**
- 采集功能默认关闭。
- 打开后，程序按文件的修改时间和大小判断是否已经传过，然后把整个文件上传到 OSS。它不解析里面的字段，也不按单条消息增量上传。
- 按[采集实现代码](../go/internal/agentcore/collect.go)，本地文件被删除时，程序只清掉本机"已上传过"的记录，不会删除 OSS 上已经上传的副本。

### 上线前要先修的两个问题

1. **本地读取范围和允许上传范围对不上。** [同步逻辑](../go/internal/agentcore/sync.go)会扫描机器上所有普通用户的文件，但上传接口只允许上传已绑定员工的数据。在多人共用的机器上，这两个范围不一致。要先限定为批准过的具体账户和工具，再试采集。
2. **采集可能拖慢 Agent 的正常工作。** 现在 `CollectOnce`（执行一轮采集的函数）在每次同步时按顺序读文件、传文件。遇到大文件或网速慢，会拖慢同一轮里的策略下发和状态上报。要改成一个单独的采集任务队列，设好超时和文件大小上限，不让采集影响 Agent 对机器的管理。

### 这意味着什么

即使找到了 WorkBuddy 或豆包的文件，也**不能只把路径加进允许列表就直接上线**。每接入一个新工具，都必须做到：

- 限定数据来源；
- 排除密钥、缓存里不需要的数据；
- 记录每一批是成功还是失败；
- 校验权限；
- 约定保留多久、怎么删除。

现有[数据目录表](数据目录表_客户合规确认_2026-09.md)里的删除周期还没有落实，所以不能承诺到期自动删除。

## 4. 下周的验证安排和开发决定

| 时间 | 要交付什么、怎样算通过 |
|---|---|
| **10 月 26 日前** | 客户或开会的人确认：WorkBuddy 的版本和版型；豆包工具具体是**哪个产品**；要的是用量指标、会话文本、工具调用还是附件。同时确认：测试授权、谁来采集、保留多久、数据交到哪里。缺这些信息，评估只能一直是"待确认"。 |
| **10 月 26–28 日** | 在隔离的测试账号或设备上，生成几条不含真实客户数据的样本。检查官方导出功能、API，或者获得授权的本地目录。逐项核对：时间、用户、会话、输入、输出、附件、删除后会怎样、版本升级后是否还稳定。只读取获得授权的样本，不抓登录令牌，不拦截加密通信。 |
| **10 月 29–30 日** | 按产品分别提交：样本字段表、能覆盖什么和缺什么、权限与合规核对结果、技术难度（低／中／高）、预计要改哪些地方和成本。然后做决定：**可以开发／限定范围试点／暂不支持**。同时更新三种服务方案里能承诺的范围。 |

如果决定开发：

1. **另外新建一个独立的功能分支**再改采集程序。不能在现有工作分支上直接扩大扫描目录。
2. 先修好账户范围问题和"采集拖慢 Agent"问题。
3. 再逐个产品做适配，包括：脱敏、排除密钥、字段测试，以及重复上传、断网、升级、删除等情况的测试。
4. 在测试机上把整个流程跑通验收后，再决定是否发布。

**这一轮只交付方案和可行性初评，不改采集代码，不打包发布。** 后续排期要看测试结果和客户授权。
