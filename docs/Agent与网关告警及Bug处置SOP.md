# Agent 与网关告警及 Bug 处置 SOP

版本：2026-10-20
给谁看：值班同事、后台管理员、Agent 和网关的开发同事。
管哪些东西：云电脑上的 Agent、Codex 的安装和更新、管理后台、AI 模型网关。

## 先认识几个词

| 词 | 意思 |
|---|---|
| Agent | 装在每台云电脑上的管理程序。它接收后台下发的配置、安装软件、上报机器状态。 |
| 网关 | 员工调用 AI 模型时经过的中转服务，用的软件叫 LiteLLM。员工的令牌在这里校验。 |
| 令牌 | 员工调用模型的通行凭证，相当于一把钥匙。 |
| 渠道 | 模型背后实际提供服务的供应商线路，例如 AWS、Google、Azure。同一个模型可能同时挂在几个渠道上。 |
| 管理后台 | 管理员使用的网页，项目名 `windows-control`，服务器上的服务名是 `ai-env-mgr-console`。 |
| AppLocker | Windows 自带的程序白名单。不在名单里的程序不能运行。 |
| CI | 自动构建安装包并上传的流程。 |
| OSS | 存放安装包的云存储。 |
| SHA-256 | 安装包的"指纹"。指纹一致，说明拿到的就是构建出来的那个包，没有被换掉或损坏。 |
| 止损 | 先让损失停下来，根因以后再查。 |

## 总流程

遇到问题按这个顺序走：

1. 确认影响了谁、影响多大。
2. 损失还在扩大时，先止损（见第 3 节）。
3. 建一张内部工单。
4. 找原因、修复。
5. 在测试环境验证修复。
6. 发布；出问题就回退。
7. 确认员工真的能用了，再结单。

**后台显示"任务成功"，不代表员工已经能用了。** 一定要看员工那边的实际情况。

## 1. 接到告警先做的四件事

1. **收集信息。** 在后台依次看"告警""总览""任务中心""机器详情／日志""模型渠道"。记下：问题第一次出现的时间、最后一次正常的时间、哪些员工、哪些机器、哪个模型、任务编号。
2. **问清员工看到了什么。** 是完全用不了、某个模型用不了、软件装不上，还是只看到一条提醒？再判断影响范围：一个人、一台机器，还是很多人。
3. **判断损失是否还在继续。** 下面几种情况要**马上止损**，不用等查清原因（做法见第 3 节）：
   - 密钥可能泄露了；
   - 员工权限已经撤销，令牌却还能调用模型；
   - 费用在异常增长；
   - 错误的策略或版本还在往更多机器上推；
   - 采集了不该采集的数据。
4. **指定一名负责人，建工单。** 如果只是一次短暂波动、已经恢复、确认没有影响，可以不建。其他情况都在"客户工单 → 新建工单 → Bug 提交"建一张内部工单，后续进展都记在这张单上。

**系统自动告警能覆盖什么。** 系统大约每 10 分钟检查一次以下情况：机器离线、发布失败、网关令牌对不上、预算快用完、后台任务放弃执行、离职员工待清理。默认机器离线 24 小时才告警，预算用到 80% 提醒。管理员可以在"设置 → 告警与轮换"里调整这两个值。

**系统自动告警覆盖不到什么。** 机器注册失败、Agent 同步出错、模型调用失败，不一定会马上出现在告警页。所以不能只盯着告警页。

### 怎么定优先级

| 级别 | 什么情况 | 要多快处理 |
|---|---|---|
| P0：马上止损 | 密钥可能泄露；撤权后令牌还能用；错误的采集、策略或版本还在扩散；费用持续异常增长；很多台机器或主要渠道同时不能用。 | 15 分钟内有人接手，30 分钟内止损（自己没权限就找有权限的人）。1 小时内定好修复负责人，之后每 30 分钟更新一次进度。 |
| P1：高优先级 | 好几名员工的主要工作被卡住；撤权、发布、账单或预算出了问题，但暂时没有继续扩大。 | 工作时间 2 小时内接手，当天定好负责人。1 个工作日内给出临时办法或修复计划，至少每天更新一次。 |
| P2：一般 | 单台机器偶尔出问题、能自己恢复的网络波动、不重要的功能出问题。 | 1 个工作日内接手，2 个工作日内给出处理计划。没修好之前至少每周更新一次。 |

补充说明：

- 这些时间是团队内部的目标，系统不会自动计时，也不是对外承诺。
- P1、P2 按工作时间算，P0 按自然时间算（夜里和周末也算）。
- 后台告警上的"严重""提醒"标签和这里的 P0／P1／P2 不是一回事，要按实际影响来定级。
- 预计赶不上时，负责人要在到期前说明原因、找人帮忙，并写下下次更新的时间。

## 2. 去哪里查

| 想确认什么 | 去哪里看 | 看什么 |
|---|---|---|
| 机器是不是真的在线 | "总览 → 机器详情／日志" | 最后一次上报的时间、Agent 版本、绑定的员工、最近的同步错误。按计划关机的机器不算故障。 |
| Agent、Codex 或软件安装是否失败 | "任务中心"。Agent 和 Codex 还要看"软件安装 → 发布任务"和"机器详情 → 版本记录"。 | 任务编号、目标、失败原因，以及机器当前装的版本和应该装的版本是否一致。 |
| 员工能不能调用模型 | 先在"模型渠道"里测试那个模型，再看"员工账号 → 模型下发" | 测试时发了什么、回了什么；渠道是否被暂停；员工有没有这个模型的权限；配置有没有下发到员工和机器上。 |
| 管理后台本身能不能用 | 用浏览器打开后台。有服务器权限的同事再检查 `ai-env-mgr-console` 服务是否在运行，并访问健康检查地址 `/healthz`，能正常返回说明后台程序活着。 | 分清楚是后台坏了、网络或转发服务坏了，还是只是某一台机器的 Agent 离线。 |
| 是否还在异常扣费 | "用量""员工预算"，以及网关上的实际调用记录 | 哪个员工、哪个令牌、哪个模型、哪个渠道还在产生调用。不要只看预算百分比。 |
| 某个操作是谁做的 | "审计"和相关工单 | 最近有没有人关户、暂停渠道、改策略、发版本，以及操作时间。 |

**有后台账号不等于有所有权限。** 服务器、网关、云平台和 CI 的权限是分开的。遇到自己没权限的步骤，马上把以下信息交给对应负责人：哪台机器／哪个员工／哪个渠道、现在影响多大、需要对方做什么。交出去之后，值班人仍要跟到验证完成。

## 3. 必须先止损的四种情况

### 3.1 令牌泄露，或撤权后令牌还能用

1. 找到对应的员工和令牌。在"员工账号 → 员工详情"里关户，或者请网关管理员立刻作废这个令牌。**先不要解绑机器**：保留绑定，Agent 才能把这名员工留在电脑上的凭证清掉。
2. 到网关上确认令牌状态，并实际试一次，确认**旧令牌已经调不通了**。后台显示"已关户"不能证明网关已经拒绝它。
3. 在"任务中心"和机器日志里确认撤权配置已经送到机器上。机器离线时，先确保网关那边已经作废令牌；等机器上线后，再检查本地凭证有没有清掉。
4. 怀疑密钥已经泄露出去时，安排更换密钥，并作废旧密钥。工单里只写密钥的编号和处理结果，**不要贴密钥原文**。

### 3.2 某个模型渠道一直出错，或异常扣费

1. 在"模型渠道"里找到具体是哪个渠道（AWS、Google 还是 Azure），以及影响了哪些模型和员工。同一个模型名可能挂在好几个渠道上，只看模型名会找错。
2. 确认是持续出错或有费用风险后，输入渠道代号，点"暂停渠道"，并记下原因和时间。只是偶尔超时一次，不要把所有渠道都停掉。
3. 在"员工账号 → 模型下发"里逐个看员工的下发结果。需要时找一名测试员工重新同步，再实际调用一次，确认新请求已经不走出故障的渠道。下发失败要继续跟进。**点了按钮不等于止损完成。**
4. 故障解决后，先用测试员工检查凭证、价格和调用结果都正常，再点"恢复渠道"，然后确认所有受影响员工的模型列表都恢复了。

### 3.3 有问题的 Agent 或 Codex 版本还在往外推

1. 到"软件安装 → 版本库与软件"，找到对应产品，点"清除全局"，让还没升级的机器不再升级。也可以把全局目标改回一个验证过的稳定旧版本。
2. 查看"发布任务"和每台受影响机器的"版本记录"。**单独指定过版本的机器，不会因为清除全局而改变**，要一台台改成稳定旧版本，或改成"跟随全局"。
3. **清除全局不会让已经升级的机器自动降级。** 先在一台测试机上装回稳定旧版本，确认没问题后，再分批处理已受影响的机器。
4. 如果是管理后台自己出了故障，交给后台和数据库负责人处理：先停止继续发布，再检查服务是否正常、最近部署了哪个版本、数据库结构有没有变更。**没确认新旧版本的数据库能兼容之前，不要直接退回旧程序，也不要回滚数据库。**

### 3.4 采集了不该采的数据，或安全策略放得太宽

1. 在"设置 → 常规 → 采集开关"里关掉采集，或者在"设置 → 封禁策略"里把程序白名单和网站规则改回原来的样子。
2. 找一台在线的测试机，确认 Agent 已经收到新策略，再检查其他受影响的机器。离线的机器记到待验证名单里。
3. **关掉采集只是不再上传新数据，已经上传的数据、电脑本地的文件和备份都不会删除。** 把已经产生的数据范围和存放位置，连同删除要求一起交给数据负责人，按批准的范围清理，并保留清理凭证。
4. 不要因为某一个软件装不上，就把整个 AppLocker 关掉；也不要放行整个磁盘、员工能随意写入的目录或临时目录。

## 4. 常见现象怎么处理

| 看到什么 | 先查什么 | 下一步 |
|---|---|---|
| 机器离线，很久没有状态 | 云电脑是不是按计划关机了；机器详情里最后一次上报的时间；后台能不能打开；Agent 服务和网络是否正常。 | 只有一台离线，先查这台机器；很多台同时离线，先查后台和网络。如果撤权因此送不到，或者大面积用不了，升到 P0 或 P1。 |
| 报错 `enrolment refused` 或 `the report names another machine`（意思是机器注册被拒，或者机器上报的身份和后台登记的对不上） | 主机名是否改过；云电脑是否用带有旧机器身份的镜像复制出来；这台机器以前是否注册或绑定过。 | 以前注册过的机器，在"机器详情 → 允许注册（24 小时）"之后重试。如果是镜像里残留了旧身份，先修好模板镜像。不要反复新建同名机器。 |
| 拉取策略、凭证或上传状态失败，或者报 `wait: 502`、连接断开（意思是 Agent 没连上后台，502 表示后台或中间的转发服务暂时没响应） | 后台服务、转发服务和网络是否正常；是不是正好在部署重启；下一次同步有没有恢复。 | 只失败一次且已经恢复，记为 P2。连续失败或撤权送不到，升 P1。很多台机器受影响或撤权失效，升 P0。老版本 Agent 走的是另一条经过 OSS 的通道，它报 OSS 相关错误时，要检查那条通道和电脑时间是否准确，不要按这里的方法处理。 |
| 发布失败，或者机器实际版本和目标版本不一致 | 版本库里的版本号和 SHA-256 指纹、发布任务的目标、机器的版本记录、机器上的 Agent 日志。 | 先停止继续推送，在测试机上复现。确认是否有机器单独指定了版本，然后重试失败的机器，或者退回验证过的版本。 |
| 报错 `CreateProcessWithLogonW failed: 1260` 或 `AppLocker would block`（意思是程序被 AppLocker 拦住，不让运行） | 被拦的程序的完整路径；当前生效的白名单规则和 Windows 事件日志；员工是不是用普通员工身份运行的。 | 只给审核过的那个程序开最小范围的放行，并用普通员工账号验证。不要把 AppLocker 整体切换成"只记录、不拦截"的审计模式。很多员工打不开 Codex 时，升 P1 或 P0。 |
| 已经撤销的令牌在网关上还能用 | 哪个员工、什么时候撤的权、网关上令牌的实际状态、后台任务的结果。 | 按 P0 处理：立刻作废令牌，并验证旧令牌调不通，然后再查同步任务。反过来，如果是正常令牌莫名丢了，按"用不了"的故障处理，不要一下子发好几个新令牌。 |
| 后台任务失败，网关返回 4xx 或 5xx 错误码 | 具体错误码、员工权限、员工可用的模型列表、渠道配置、供应商服务状态。 | 401、403 表示身份或权限不对，先查账号和授权；429 表示调用太多或预算用完被限制，先查预算和限流；5xx 或超时表示网关或供应商出了问题，去查网关和供应商。原因没查清之前，不要重复建账号或重复发密钥。 |
| 预算告警，或模型测试失败 | 是不是额度正常用完了；测试时发了什么、回了什么；请求实际走了哪个渠道。 | 正常用完的，按业务流程处理。异常持续扣费的，先止损。主要渠道确实用不了的，升 P1 或 P0。 |

关于告警页的两个按钮：

- **"确认"只表示有人接手了；"关闭"也不会修好问题。** 只要问题还在，下一次检查时可能再次告警。
- 离职员工到期清理的提醒，属于员工、云电脑和数据的清理事项，不是 Agent 故障。

## 5. 一张工单从头跟到尾

1. **建单和分派。** 在"客户工单 → 新建工单 → Bug 提交"填写标题、详细说明、复现步骤、预期结果和实际结果、发生环境和时间。后台管理员建的工单只有后台能看到。进入工单详情，用"分派与关联"指定负责人，并关联相关的员工、机器和后台任务编号。如果客户已经提过工单，保留客户的单，另建一张内部 Bug 单，两张单里互相写上对方的编号。
2. **补全信息。** 在内部备注里写清楚：级别（P0／P1／P2）、影响范围、第一次出现的时间、相关的版本／模型／渠道、去掉敏感信息后的报错、做过哪些止损、当前负责人、下次更新时间。给客户看的回复只写必要的进展，不写密钥、员工隐私或完整的原始日志。
3. **找原因并修复。** Agent 开发同事对照机器本地日志和后台收到的状态；网关开发同事核对请求实际走的路线、令牌状态和供应商的返回。负责人要写清：根因、修复用的代码提交或配置改动、影响范围、怎么测试、怎么回退。如果问题出在供应商或配置上，也要在工单里写下结论，不必硬说成代码 Bug。
4. **在测试环境验证。** 在测试用的 Windows 机器、测试网关或测试账号上，先复现原来的问题，打上修复后再做一遍同样的操作，并检查相关的功能有没有被带坏。例如改了撤权，既要测旧令牌被拒绝，也要测正常令牌还能用；改了安装，要测普通员工真的能打开软件。记下环境、版本、步骤、结果和证据。没有测试环境时，写明风险，经负责人同意后，先在一台机器或一个账号上验证，但这不能叫"已完成测试环境验证"。
5. **发布并观察。**
   - Agent 和 Codex 安装包：CI 把包传到 OSS 后，在"软件安装 → 版本库与软件"点"立即扫描 OSS"，核对版本号、文件大小和 SHA-256 指纹。先用"指定给机器"给测试机装，验收通过后依次点"标记已验收 → 批准稳定 → 设为全局"。之后分批查看发布任务、机器实际版本和员工那边的功能。
   - 网关配置：先用测试员工验证，再扩大范围。
   - 管理后台程序：由有服务器和数据库权限的同事升级，并检查服务运行、登录、任务中心和 Agent 同步是否正常。

   把版本、代码提交、发布范围、发布时间和验证结果写回原工单。
6. **发布后出了新问题（回归）。** 马上停止继续推送。Agent 和 Codex 按 3.3 节退回验证过的版本；网关渠道按 3.2 节暂停或恢复；管理后台程序要先由负责人确认数据库兼容，再退回旧版本。记下哪些已经恢复、哪些还要单独处理。退回旧版本不等于删掉安装包，也不等于关掉告警。
7. **结单。** 值班人和修复负责人一起确认：员工能正常用了、原来的错误不再出现、该作废的令牌已经失效、任务和告警都恢复正常。记录最终影响、根因、修复版本、验证证据、遗留问题和负责人。
   - 问题解决了，把工单设为"已完成"。
   - "关闭"只用于拒绝处理、重复提交或不归我们管的情况，并且要写明原因。
   - 客户能看到的问题，另外给客户一份去掉敏感信息的结果说明。
   - P0 问题要在 2 个工作日内补一份简短复盘，写清以后怎么避免再犯。

**工单不会因为任务成功而自动完成，告警消失也不代表 Bug 已经修好。** 能不能结单，由工单负责人根据员工的实际使用情况来确认。
